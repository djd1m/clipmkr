# ADR-001: Восстанавливать известный checkout отдельным доказательством происхождения

## Статус
`proposed`, terminal-origin delta после последующей read-only сверки. Прежние решения по QCSQ-01, RISK-01/RISK-02, QT-01–QT-04 сохраняются; новый snapshot требует originating verification и актуальных gates, не наследует автоматически допуск предыдущей редакции. Решение обратимо до исполнения recovery; повторно рассматривается при невозможности сохранить исходные identity и журнал.

## Контекст
HTTP201 выведен из pinned c12 guard и preserved request; wire body и точный response_at утрачены. Первоначально read-only доказан pending;06.11.2026 в11:08:37Z тот же provider payment уже canceled/unpaid/expired_on_confirmation без confirmation URL, DB intent остаётся created. Нужны pending recovery при фактическом pending и прямое metadata закрытие именно expired origin без изменения исходного failed результата. Последняя status-сверка не заменяет полный payment/event/grant inventory.

## Драйверы решения
1. D1, высокий: один exact existing intent, без второго POST/ключа/аккаунта и без false success (FR1–FR3).
2. D2, высокий: original failed helper, разные operator/browser keys, execution identity и durable consume-before-action сохраняются (FR2–FR4).
3. D3, высокий: fresh control/health/TEST isolation,24h policy, native writer/cleanup остаются обязательными (FR4).
4. D4, средний: минимальная поправка private QA; исходники canonical executor/launcher/run/native и business code immutable (FR5/NFR).

Выбран A. Новый private `recover-known-checkout.private.py` принимает captured canonical namespace db0 через b9 launcher и exact origin proof; ничего не monkey-patch. Derivative bridge вызывает его для binding известного failed attempt, ограниченного follow-up, terminal metadata reconciliation и explicit caller-held ordinary boundary по05D2. Новые формы находятся в том же original bridge journal, а не в новом namespace. `used[original_open_ticket].state=consumed_unknown` и исходный `completed=false` никогда не становятся success.

Перед recovery тот же journal получает permanent `binding.recovery_protocol` с version/source-set/origin-binding digest; исходные `binding.runtime/execution` сохраняются побайтно в canonical JSON и в create-only snapshot. Actual old812 сравнивает **весь** binding с `{runtime,execution}` до `operate` и потому отказывает после additive fence. Новый bridge понимает обе формы только для одноразовой миграции; после fence обратный переход запрещён. Изменение формы journal binding — явная migration, не переписывание original executor SHA. Все business actions идут через этот bridge; inventory конкретных разрешённых entrypoints и tests их отказов —05B. Произвольное исполнение root собственного Python не входит в эту границу доверия.

Recovery proof имеет `kind=known-checkout-recovery-v1`, `original_response_captured=false`, собственный source/evidence digest, оба разных ключа, original operation/ticket/case/window и отдельно fresh action window. Он **не** создаёт `new_checkout`, **не** ставит `checkout_response_bound=true`, **не** передаётся old `admit` под видом response. Отдельный narrow admission проверяет поля и свежие canonical guards; old admission остаётся прежним. Bound pending разрешает лишь exact предусмотренный TEST follow-up, без нового checkout, relay или paid job.

После exact terminal outcome adapter может выполнить только metadata reconcile: reuse полной `cutover` с24ч от relevant event/upper bound и fresh terminal ledger proof; append original failed attempt + recovery receipt в `business_history`, установить `business=reconciled`/`reconciled_at`, затем снять recovered active_case. Исходные execution/runtime_binding сохраняются; никакого invented original response. Следующий checkout требует новых GO/baseline и explicit derivative boundary05D2 с прежними canonical predicates. Ordinary slots/tickets разделены по05D1a.2/4 (proposed06.11.2026).

Если exact original target уже `canceled/paid=false/expired_on_confirmation`, adapter принимает тот же proof kind с `mode=terminal_from_origin`, source-bound fresh preflight и finite metadata GO. При complete BOTH-store proof допускаются сохранённый DB intent=created/unfulfilled и0target payment/grant; это наблюдаемое расхождение local/provider state, не fabricated DB reconciliation. Прямой путь после полного canonical cutover: B1+recovery `consumed_unknown` → `reconciling_unknown` → operation history/reconciled → journal `terminal_reconciled`. Он никогда не создаёт pending bound/active_case/browser projection и не вызывает callback/session/provider mutation/checkout. Raw DB state, failed origin и original consumed_unknown остаются в provenance; outcome `expired_before_recovery` оставляет decline/manual-cancel NOT VERIFIED. Неизвестная history/identity, иной direct terminal outcome или partial запись → STOP. Pending путь и его action cleanup остаются прежними.

FR1 реализуется в derivative browser через Playwright1.60.0 `route.fetch` с `maxRetries:0,maxRedirects:0` для единственного exact checkout POST, body/request/status fsync до `route.fulfill({response})`. Повтор/redirect/неполное сохранение приводит к STOP без дополнительного запроса. Это инструментированный Chrome, не свидетельство полностью нетронутого network path и не диагноз exact live exception.

## Обоснование
D1/D2 выполняются typed proof вместо семантической подмены response. D3 исполняется reuse canonical code и отдельным fresh preflight под теми же locks; known pending не проходит terminal cutover. A меньше B: не нужна миграция original executor SHA. C не отвечает one-POST; D создаёт ненужный lifecycle. Новый bridge/adapter/helper source set всё равно получает отдельный immutable capture/review binding; старый journal.binding не является доказательством новых source bytes.

R1 уточняет A: просто добавить recovery slot вне binding недостаточно — старый bridge его игнорирует. Permanent binding fence использует существующий отказ old812, удерживает отказ при partial reconcile и оставляет positive ordinary checkout через новый bridge после обеих closure. Known-target exception относится только к pending/terminal самого intent: полный event identity/history/delivery/ACK predicate и24h, isolation/completeness/stability/freshness/no-inflight сохранены явно в05A. Confirmation URL читается fixed read-only source из planned derivative runner; отсутствие доказуемой применимости допускает creation binding, но блокирует follow-up.

Terminal-only branch не требует URL, поскольку никакого browser действия нет. Авторитет provider canceled связывается с exact SQL/original evidence и actual source capture, а не caller booleans; DB created не переписывается и не объявляется provider pending. Все actual relevant events/delivery сохраняют полный predicate/24h. Сам status GET не является webhook event: при доказанно полной истории без actual events новый event/24h от времени GET не изобретается; unknown history или неизвестная bound существующего relevant event запрещают closure. Это небольшой branch существующего adapter/bridge/runner, без нового файла, financial dispatcher или framework.

QCSQ-02 уточняет порядок direct preflight: actual db0 `revalidate` вызывает `persist`, поэтому bridge сохраняет exact pre-revalidation operation/journal bytes как create-only durable provenance **до первого** startup `operate/revalidate/persist`. При тех же locks/source/authority проверках затем допускается canonical health trace, но B1/recovery/business authorization записывается только после полного cutover. Early event/incomplete-history STOP сохраняет исходные bytes в snapshots и допустимую health trace в live operation; trace не является authority и не откатывается. Origin business/attempt/execution и journal B0/used при этом неизменны. Kill/partial persist/snapshot → STOP без автоматического продолжения; порядок и проверка field-level trace заданы в05C/F. Root diagnostic подтвердил только actual `persist` на synthetic data; это не исполненный revalidate fixture.

QT-05 переносит различение historical/current окон именно на direct branch: original ticket/GO уже истекли сейчас, но click/201/creation внутри их исходного окна; отдельно действуют fresh current metadata GO и source-set authorization. Такой P-terminal обязан пройти fullgate и closure без pending/action tickets. Creation вне исторического окна, expired current metadata GO и expired current source-set authorization — разные минимальные отказы с корректными остальными данными и digests, до authorization/closure. Старый pending positive не заменяет эти проверки.

Root сверил [ЮKassa: процесс платежа, Redirect](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process): pending redirect использует confirmation_url; expires_at при waiting_for_capture не задаёт TTL pending формы. Поэтому fresh authenticated GET exact TEST payment и фактическая доступность его формы до submit проверяют текущую применимость, без вымышленного обязательного срока. Это вывод из переданного primary-source результата, не самостоятельная сетевая проверка архитектора и не гарантия будущей доступности URL. A1 задаёт fixed SQL/GET источник внутри одного существующего planned runner target.
