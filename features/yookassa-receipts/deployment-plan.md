# План поставки поддержки чеков на текущий VPS

Это план координатора после принятого source QE, а не выполненная поставка. Source coder не исполняет рабочий SQL. Цель — существующий clipmkr.ru на77.83.87.178, с прежним TEST-магазином, закрытым checkout и прежним персональным тестовым исключением. Боевые ключи и неподтверждённые налоговые значения не подключаются.

1. Заморозить исходники, проверить реальные результаты тестов, связанные с требованиями сценарии и антидрейф. Все originating conditions должны иметь собственную независимую проверку. Закрыть source QE установленным native producer; не считать зелёный build заменой QE.
2. Зафиксировать source commit и проверить одинаковую ревизию во всех трёх Git-зеркалах. Из Git archive точного коммита собрать существующий Dockerfile target web с RELEASE_REVISION; проверить OCI label. Workers не меняются: runtime receipt используется только web, новая nullable колонка не меняет их запросы.
3. Снять фактические runtime IDs/images, закрытый Compose, backup binding и режимы оплаты; убедиться, что они соответствуют известной рабочей копии. Сохранить откат web/config. Запустить свежий штатный backup, проверить success/exit0. Новые секреты не выводить и не добавлять в Git.
4. Применить только принятую additive029 существующим мигратором с временными административными credentials и migration lock. Текущая ограниченная app-роль не используется для DDL. Проверить hash записи _schema_migration, nullable column, CHECK/trigger и существующие права приложения. Ни одна рабочая финансовая строка или receipt не backfill-ится; БД из старой копии не накладывается на новые записи.
5. Под общим backup lock заменить только image web в существующем private Compose и выполнить up --no-deps. Профиль оплаты/почты/БД/Redis/S3, mounts и остальные контейнеры сохраняются. Проверить health с точным source SHA. Обновить в runtime-binding только фактические ID/image web; остальные шесть привязок должны совпасть.
6. Проверить опубликованную версию узкими безопасными сценариями: доступные главная/health/вход, прежние ограничения checkout, чтение статуса/отказ поддельного webhook без финансовых записей. Существующие клипы можно просмотреть/скачать без новой генерации. Реальную покупку или возврат не делать. Запустить штатный backup после миграции/web и подтвердить success.
7. Удалить только свои тестовые БД/роль и временные migration credentials после сохранения доказательств. Зафиксировать actual delivery, source SHA/image, ограничения и инструкцию владельцу в10_delivery.md. Синхронизировать документационный commit во всех зеркалах.

## Возврат

При неуспехе web вернуть сохранённый прежний web/config и обновить backup binding. Новую nullable колонку/ограничения можно оставить: старый web продолжает писать SQL NULL, а immutable trigger допускает прежние операции. Не выполнять destructive down-migration или restore поверх новых пользователей/платежей. Этот возврат допустим только пока реальные чеки и боевые покупки не включены; после их активации потребуется отдельный план совместимости и сверки.

## Что остаётся после поставки кода

Подтверждение НДС/предмета/способа расчёта, настройки боевого merchant webhook, отдельное включение реальных продаж и приёмка настоящей покупки/начисления/чека. Локальная HTTP-фикстура подтверждает отправляемый JSON, не регистрацию фискального чека. Поддержка full_prepayment/закрывающего чека и инициирование частичных возвратов не реализуются этим блоком.
