## GATES и зависимость работ

1. Пригодный интерактивный макет и конкретный diff интерфейса → явное рассмотрение владельцем. Сохранить решение и одобренные hash.
2. Согласованная дельта → OpenSpec path/hash в `01_requirements.md`, проектный dz checkpoint, независимый QCSD и проверка плана.
3. Перед Step 7: K1 применяется коллекцией реально новых команд, модулей или export. По текущему плану коллекция пуста. При её появлении прогнать `npm run dz -- name-check` с заявленными именами. K2 — `node .agents/skills/feature-adr/scripts/check-plan-completeness.mjs features/ux-default-actions --tier=M`. Предварительная структурная проверка закреплённым скриптом на версии плана от 24.11 завершилась с кодом 0: один ADR, пять идентификаторов требований и семь путей, 0 ошибок, предупреждений и пропусков. Перед Step 7 результат привязывается к согласованной ревизии.
4. TASK-1..4 → один стабильный снимок → TASK-5. Правки после целевого сбоя требуют повторить затронутые проверки. Полный дополнительный прогон требуется при широком изменении или незакрытой регрессии.
5. В действующем порядке после локальной проверки развернуть тестовую копию, выполнить E2E принятыми тестовыми аккаунтами и дать владельцу ручную проверку. После ручной приёмки поставить тот же проверенный артефакт в разрешённую владельцем среду, проверить версию и сценарии. Основной production/DNS требуют своей команды, если их переключение понадобится.

## Проверки, source guards и мутационные якоря

Источник проверок — тесты базы `5053cb84d157d3adb3f04dd4a1399bcb3e17f1b1`. В существующих тестах заменить только утверждения об изменённой UI-строке или структуре. Проверки запросов, доступности результата, удержания состояния и условий должны сохранять чувствительность. Следующие инверсии планируются в изолированной копии и охватывают изменяемую логику.
