# ADR-001. Личная квота при отказе доступа

## Decision

Доверяем только HTTP 401/403 типизированной ошибки адаптера при настроенном Cloud.ru.
`authorizeSelection` возвращает московский день списания через локальный результат:
`now` для исходного дебета, `job_attempt.started_at` для резерва `VideoRetryService`,
который передаёт тот же timestamp в обе операции. Схема БД не меняется. Если воркер
исчезает до обработки ответа, точный результат неизвестен и сторож не возвращает квоту.

`failSelection` принимает необязательный подтверждённый день. Условия: актуальный
`FOR UPDATE OF v`, текущая выборка и fence, `llm_dispatched`, ровно одна единица,
`user_llm` именно этого аккаунта и дня, `used > 0`. Если строка отсутствует, транзакция
закрытия и возврата откатывается вместе. Глобальные квоты и журнал попыток сохраняют
факт запроса. Сначала `failTx` завершает статус и `finalizeVideoCreditsTx`
берёт кредитный advisory lock. Затем та же транзакция возвращает квоту.
Штатный повтор другого видео берёт кредитный lock до строки квоты.
Отдельное событие выводится после попытки транзакции и указывает её исход.

## Confirmation

- `tests/selection.integration.test.ts` подтверждает обе ветки дебета, гонку,
  полночь, глобальную квоту, повтор из расшифровки и терминальное состояние.
- `tests/selection-order.test.ts` подтверждает границу 401/403, остальные ошибки,
  исключение секретов и явное состояние при отказе БД.

- `one refund for concurrent completion of the same fence` выполняет два вызова,
  удерживая строку квоты внешней транзакцией. Через `pg_blocking_pids` подтверждает
  реальное перекрытие. Исходный `used=2` падает до 1, один терминальный переход,
  один release резерва, второй вызов stale/no-op. Мутация удаления проверки
  актуального fence/статуса ломает тест.
- `credit lock precedes selecting quota refund` проверяет параллельный повтор
  другого видео того же credits_v1-аккаунта и порядок кредитного lock до квоты.
