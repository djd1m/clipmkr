# Требования

Владелец выбрал «давай тогда реалзуем для каждого входящего сообщения» после объяснения двух вариантов. Существующий бот и закрытая группа проверены отправкой тестового сообщения.

- FR-1. Первое и последующие публичные входящие сообщения контакта приводят к доставке уведомления от существующего бота в настроенный чат. Подписка только на `message.created`.
- FR-2. Исходящие, служебные записи и закрытые заметки игнорируются. Посторонние либо неподписанные запросы отвергаются до обращения к Telegram.
- FR-3. Сотрудник получает ссылку именно на этот диалог. Тело переписки, контактные данные и секреты не передаются и не попадают в логи адаптера.
- FR-4. Отдельный приватный сервис в текущем Docker Compose использует закрытые переменные среды. Отказ Telegram виден по обезличенному результату и не блокирует обработку чата.
- NFR-1. Проверить доставку на реальном виджете и сохранение нормального ответа из панели сотрудника. Политика best effort без очереди и автоматических повторов. Повторная доставка входного события может повторить уведомление.

Дельта OpenSpec `openspec/changes/libredesk-telegram/specs/support-telegram/spec.md`, SHA-256 `2c12db3d936a9978681e9fbbeff46a078c1b021cfded0a1f2be1931853f2d0a9`.

Приёмка использует отдельный синтетический диалог. Отправить первое сообщение и одну реплику, затем ответить из панели сотрудника и увидеть ответ в виджете. Два уведомления подтверждаются двумя реальными ответами Bot API с `ok`, уникальными `message_id`, ожидаемым ID закрытой группы и точным текстом со ссылкой на тот же диалог. После исходящего ответа адаптер фиксирует пропуск без третьего вызова. Проверяющий сравнивает обезличенный результат наблюдения с последовательностью действий браузера. Отдельно отмечается, видел ли получатель уведомления в самом клиенте Telegram. Сбой Telegram и тайм-аут воспроизводятся на локальной управляемой заглушке и проверяют отсутствие ожидания/повтора на стороне чата.
