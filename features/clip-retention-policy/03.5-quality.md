## QL-001 — поздняя запись S3 не закрыта durable протоколом удаления

- Owner: `qcsd-quality`; severity: **HIGH**; classification: **structural**; требования: **FR-5, ADR-002**.
- Scope native snapshot: `features/clip-retention-policy/01_requirements.md`, `features/clip-retention-policy/03_adr/002-claim-media-deletion.md`, `features/clip-retention-policy/05_architecture.md`.
- Доказательство дизайна: ADR-002:22–24 отменяет running/deferred rerender, затем удаляет prefix и завершает `media_deleted_at`; достаточно отклонить stale DB publication. Архитектурный sequence/Data & storage не задаёт durable обработку незавершённых внешних записей.
- Доказательство существующей зависимости: `packages/db/src/render.ts:84` вызывает `await publish()` до fenced SQL acceptance; `apps/worker/src/workers/render.ts:85–90` выполняет PUT mp4/thumb. Компенсация rejected rerender в `packages/db/src/render.ts:101–124` вызывается позже и ошибки удаления только логирует. Поэтому запрет SQL publication сам по себе не запрещает поздний PUT; crash до компенсации оставляет результат вне этой компенсации.
- Сценарий: rerender уже начал PUT → retention commits claim → free/paid/thumb prefix deletion возвращает успех → записан `media_deleted_at` → ранее начатый PUT завершает запись → worker падает до fenced publication/компенсации. Доступ в БД может оставаться закрыт, но вновь появившийся объект не имеет описанного durable пути повторной очистки. Это найденный разрыв дизайна; сценарий не воспроизводился тестом и не объявляется наблюдённым runtime-инцидентом.
- Условие закрытия: **Протокол FR-5 должен учитывать PUT уже начатого renderer после успешной очистки префиксов и падение worker до его компенсации: такой объект не остаётся без durable пути очистки, а terminal deletion marker согласован с этим протоколом. ADR-002 и архитектура должны описать выбранную границу и fault-injection проверку, сохранив отсутствие доступа/resurrection, исходник и историю.** Новая инфраструктура не предписывается; требуется конкретное безопасное разрешение в текущем стеке.

Для QL-001 предложить `retention_late_put_after_delete_crash_is_reconciled`: барьер fake storage удерживает реальный PUT; после claim и prefix delete PUT завершается, worker не выполняет компенсацию; restart/reconciliation достигает описанного безопасного результата.
