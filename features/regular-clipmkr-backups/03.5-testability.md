## Покрытие приёмки

Полнота критериев на уровне **11 из 11 групп FR/NFR (100%)**: для каждой определены
проверяемый результат и подходящий слой доказательства. Это полнота дизайна приёмки,
не автоматизированное покрытие ветвей и не результат runtime испытаний.

| Требование | Измеримый результат / отрицательный случай | Достаточный слой доказательства |
|---|---|---|
| FR-1 | Две актуальные runtime БД, whole-instance RDB, согласованный files/config allowlist и versions в manifest; другой binding/legacy dump отвергнут. | Capture subprocess assertions и read-only сверка реальных bindings/содержимого извлечённого набора. |
| FR-2 | Занятый общий lock не запускает capture/restic/rclone; runtime ограничен менее часа; следующий штатный запуск возможен. | Реальный конкурирующий flock в temp fixture, timeout с дочерним процессом, unit/timer verification и один scheduled run. |
| FR-3 | Один текущий snapshot ID/manifest проверен независимо в двух копиях; отказ или старая copy не обновляет общий success. | Native temp restic + rclone roundtrip, отказ одной copy; затем фактическое чтение обеих offsite copies. |
| FR-4 | Нет global run/forget/prune/чужих hooks/перезапуска; изменяются только разрешённые собственные runtime targets. | Recording command boundary, проверка итогового diff и scoped install evidence. |
| FR-5 | Каждый failed component, stale staging, ENOSPC, timeout оставляет прежний success; незаконченный staging не опубликован. | Fault injection по стадиям, проверка receipt и authoritative include до/после, прав 0700/0600. |
| FR-6 | Из обеих offsite извлечены одинаковые bytes; две БД из одной копии реально восстановлены; recent account/payment/video/support rows и связи совпали; файлы читаются. | Реальный pg_restore с успешным exit и SQL assertions на свежих изолированных destinations; hashes файлов; native RDB checker отдельно от load. |
| FR-7 | Компонентные интервалы отражены, отсутствуют обещания атомарности/RPO0; workers закрыты до reconciliation при DR. | Проверка manifest и recovery procedure; online capture не тестируется как атомарная cross-store транзакция. |
| FR-8 | VPS loss и S3 object loss различены; key list не считается байтами медиа. | Scope matrix/отчёт; S3 object-loss restore не является обещанным acceptance case. |
| NFR-1 | Root-only staging/receipt, encrypted repo; в stdout/stderr/Git нет canary-secret, PII или signed URL. | Permission assertions и secret-canary в fake stderr/ошибке команды плюс обзор итоговых artifacts. |
| NFR-2 | Используются существующие native tools; нет новых daemon/container/dependency, retry storm или остановки приложения. | Diff/command assertions; measured first run duration/size и failure/timeout sequence. |
| NFR-3 | Last success age не обнуляется ошибкой; per-copy age виден; hourly interval и реальные retention ограничения различены. | Два последовательных run (success → failure) с контролируемым временем, review receipt/отчёта. |

Названные в плане `capture_failure_does_not_publish_stale_set`,
`runtime_binding_drift_refuses_before_capture`, `unheld_shared_lock_refuses_capture`,
`hourly_run_never_calls_global_retention_or_foreign_hooks`,
`one_failed_offsite_never_marks_success`, `occupied_shared_lock_runs_no_commands` и
`native_two_copy_roundtrip_restores_exact_bytes` подходят к заявленным свойствам.
На QE проверяется поведение assertions, а не только наличие имён тестов.

Для невакуумного restore oracle при TASK-5 используются уже существующие недавние
тестовая покупка и запись: приватно фиксируются ID, expected fields/relations и
времена наблюдения, затем результат проверяется в восстановленных БД. Старый dump
без этих данных обязан провалить сравнение; обычная проверка числа строк недостаточна.
Это конкретизация существующего FR-6, не требование новой оплаты/нарезки.
Перед pg_restore нужно независимо подтвердить свежий destination и запрет перехода
в live namespace; существующая production БД не может стать допустимой из-за похожего
имени. Здесь проверена тестируемость этого требования, runtime изоляция не проверялась.

`pg_restore --list` пригоден для capture preflight, но не доказывает выполненность FR-6.
Успешный native temp roundtrip доказывает работу adapter с bytes, но не actual offsite
доступ или SQL restore. `redis-check-rdb` доказывает только принятую проверку формата;
если offline load не проводился, итоговый отчёт обязан так и сказать. Полный повторный
UI/E2E прогон оплаты/нарезки для этого scope не требуется.
