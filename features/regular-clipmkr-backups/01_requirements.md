# Регулярные резервные копии Clipmkr

Статус: проект требований для согласования; K1/K2 и независимое QE не заявлены выполненными.
Источники: `docs/operations/2026-11-10-backup-audit.md` (источник root commit `f808cbf`); действующее allocation/read-only подтверждение runtime; уточнения владельца в текущем задании.
OpenSpec ledger: `openspec/changes/regular-clipmkr-backups/{proposal.md,design.md,tasks.md,specs/application-backups/spec.md}`; точные SHA-256 — `requirements-revision.json`. Авторитетный execution plan — `06_implementation_plan.md`.

## Участники

Владелец принимает охват и ограничения; оператор сохраняет/восстанавливает данные; пользователи сохраняют аккаунты, оплату и результаты. UI не меняется; повторная приёмка нарезки/оплаты не нужна этому adapter.

## Функциональные требования

- **FR-1 MUST: фактический production охват.** Given активные runtime bindings, when готовится новый набор, then он содержит свежие `pg_dump -Fc` основной и helpdesk БД, native RDB фактического общего Redis, production uploads, authoritative `model-spend.jsonl`, актуальные private compose/support config с фактическими настройками и версии/дижесты образов. Для spend сохраняется только завершённый валидный JSONL prefix привязанного источника: identity, размер S при открытии, конец prefix B≤S, число записей, исключённые S−B bytes и времена записаны; каждый complete record валиден, незавершённый tail не выдаётся за ledger. Append после S вне среза; подмена/ротация/усечение источника до окончания capture дают non-success. Временные stt/llm/video workfiles классифицируются как rebuildable/in-flight и не доказывают coherent authoritative state. Источник каждого компонента и начало/конец снятия записаны. Живой PGDATA, копии из migration/старые dumps, тестовые профили не заменяют актуальный набор.
- **FR-2 MUST: расписание и сериализация.** Given закончены gates и установка, when наступает почасовой timer, then отдельная bounded задача под общим `/var/lock/corp-backup.lock` создаёт новый набор без остановки web/workers. При занятом lock — явный non-success и следующий штатный запуск; без скрытого concurrency. Timeout < интервала; пропущенный запуск не объявляется успехом.
- **FR-3 MUST: штатные две offsite копии.** Given текущий подготовленный набор, when restic создаёт snapshot с Clipmkr tag, then существующий immutable rclone copy переносит encrypted restic tree в действующие Yandex и Cloud.ru targets; текущая snapshot identity проверена отдельно в каждом. Только локальный успех/общий старый offsite marker недостаточен. Отказ любого шага не обновляет успешный receipt.
- **FR-4 MUST: чужая инфраструктура сохранена.** Given общий backup движок, when запускается адаптер Clipmkr, then он не вызывает общий `backup.sh --service clipmkr --phase run`, `forget`, `prune`, чужие hooks, изменение retention/IAM/таймеров, перезапуск контейнеров или DNS. Общий существующий daily/prune остаётся владельцем local retention; добавляется только собственный manifest и unit/timer.
- **FR-5 MUST: отказ при неопределённости.** Given stale staging, ошибка dump/RDB/files/copy, неверный binding, недостаток места или timeout, when run завершается, then нет нового общего success; receipt указывает failed component, времена, run ID, текущие snapshot/copy identities без секретов. Staging уникален для run, права0700/0600; проверенный набор публикуется атомарно после проверок. Под собственным staging root допускается не более 2 наборов по ≤1 GiB каждый: authoritative completed и один candidate/остаток прерванной замены; после нормального окончания остаётся не более 1 completed. Единственный владелец очистки — capture hook под настоящим shared lock: перед новым capture убирает только доказанно собственные неиспользуемые orphan/superseded наборы, сохраняя authoritative include; при ошибке удаляет свой unpublished candidate. После SIGKILL остаток убирается следующим holder lock до нового candidate. Foreign paths, production mounts, repo/offsite retention не затрагиваются. Прежний success receipt сохраняется независимо от cleanup.
- **FR-6 MUST: восстановимость текущего offsite набора.** Given snapshot после недавней тестовой покупки и новой записи, when он извлечён из каждого offsite, then совпадают manifest/checksums; из одной offsite копии обе БД восстанавливаются в свежие изолированные назначения существующего PostgreSQL, проверяются выбранные account/payment/video/support строки и связи, файлы читаются и hash совпадает. Никаких production overwrite, новых контейнеров, повторной оплаты/нарезки. Архив Redis проверяется native checker; проба загрузки требует отдельного безопасного offline destination и не выполняется на живом shared daemon.
- **FR-7 MUST: честная граница DR.** Given online снимки разных компонентов, when описывается restore, then указана неатомарность между БД/Redis/files/S3, времена каждого компонента и восстановление только с закрытыми workers с reconciliation очередей/БД/объектов. Не обещать RPO0 или автоматическую замену текущих данных frozen migration комплектом.
- **FR-8 MUST: отдельная судьба медиа.** Given VPS потерян, then внешние S3 объекты доступны только при сохранности исходного сервиса/bucket/прав; сохранённые metadata/config/ключи позволяют их найти. Потеря/удаление самих S3 объектов независимой копией не покрыто; key manifest не называется копией видео. Перед расширением охвата — отдельное решение владельца.

## Нефункциональные требования

Граница FR-1: production uploads, config и `model-spend.jsonl` обязательны. Известные scratch/workfiles в stt/llm/video roots явно **исключены** как rebuildable/in-flight, с категориями/исключениями в manifest. Они не расходуют capture budget и не считаются восстановленным authoritative state; обычный длительный STT/video processing сам по себе не должен исчерпывать backup cap. Это явная дельта охвата до повторного ideation review.

- **NFR-1:** Секреты/PII/дампы остаются в root-only staging и existing encrypted restic. В Git только код, обезличенная конфигурация/schema и документы. Никакого stdout env, DB URL, signed URL, содержимого медиа.
- **NFR-2:** Установленные restic0.16.4/rclone, PostgreSQL/Redis CLI, systemd переиспользуются. Новых daemon/container/dependency нет. После безопасной очистки и до bulk capture доступное место на filesystem staging и local repo должно быть ≥8 GiB (одинаковый filesystem проверяется один раз): 1 GiB capture budget + 2 GiB headroom local snapshot/cache + 5 GiB минимальный резерв приложения. Read-only sizing должен помещаться в capture budget; фактическая запись каждого набора ограничена 1 GiB, превышение/неизвестный sizing — non-success без publication. Перед local snapshot место проверяется снова: ≥7 GiB на repo filesystem. Это admission guard от нагрузки данного run, не filesystem reservation от конкурентной записи приложения; доступное место/размер/длительность первого run измеряются. Busy lock/диск/timeout не запускают retry storm.
- **NFR-3:** Почасовой интервал — настройка, не доказанный RPO. Отчёт показывает actual age успешных компонентов и двух offsite copies; краткая локальная история ограничена существующим daily retention (`KEEP_HOURLY=0` по умолчанию), удалённая история append-only без новой гарантии срока хранения.

## Ограничения и границы

Разрешение владельца продолжить после аудита не заменяет настоящих native checkpoints и independent cross-model QE. Никакой live оплаты; существующий тестовый режим не переключается. Чужой coding-workspaces FAIL не чинится и не скрывается. Свежие ручные PG-копии уже переданы на прежний сервер; сейчас не повторяются. Поддержка VPS catastrophe ограничена внешним S3 и наличием секретов расшифрования по действующей escrow процедуре.

## Открытые условия перед реализацией/активацией

Подтвердить точный allowlist файлов/runtime bindings при реализации; закрыть QCSD, требования/ADR/план native checkpoints и K1/K2. Перед реальным restore drill доказать изоляцию PG destination и доступный offline Redis checker; если безопасной загрузки RDB нет, прямо записать границу проверки. Проверить фактический канал уведомления: audit зафиксировал недоставку Alertmanager; не заявлять действующее оповещение без наблюдения.
