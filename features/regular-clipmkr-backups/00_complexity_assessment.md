# Регулярные копии после переноса: оценка

Дата: 10.11.2026. Статус: предложение для checkpoint 0, не успешный gate.
Task kind: tooling

Тир **M**, ограниченная интеграция существующего движка резервирования; не новая подсистема DR.

| Измерение | Балл | Основание |
|---|---:|---|
| Файлы | 2 | Шесть конкретных code/config/test targets |
| Домены | 2 | Эксплуатация Clipmkr и существующее резервирование; бизнес-модели не меняются |
| Интеграции | 2 | Один адаптер к уже установленному restic/rclone/systemd |
| Несовместимость | 1 | Нет изменений API, схем, production bindings |
| Модели данных | 1 | Только служебный receipt состава snapshot, без новой БД |
| Сквозные аспекты | 2 | Один аспект: сохранность данных; confidentiality и сигнализация входят в него |

Сумма 10. XL-измерений, breaking changes и миграции данных в этом изменении нет.
Высокий ущерб неверного восстановления требует сильной проверки, но не превращает bounded adapter в новую DR платформу.
При расширении на копирование самих S3 объектов, изменение чужой инфраструктуры или автоматический restore — reroute до кода.
Этапы: 0 → 1 → 3 → 3.5 → 5(light) → 6 → K1/K2 → 7 → 8; 2/4/9 не обязательны по M.
Режим reference с pinned QE протоколами; AQE runtime не устанавливается. Оценка бюджета после закрытия planning условий: 45–90 минут реализации и focused QE; не SLA.

## Источники и recall

Аудит `docs/operations/2026-11-10-backup-audit.md` из root worktree; коммит источника `f808cbf` (координатор подтвердил), runtime allocation прочитан только из private файла.
Настоящий `npm run dz -- recall ... --project /home/clipmkr --json --limit 5` с Node22.23.4 вернул 5 результатов.
Применимы `teach:462ac78506d4ce16`: привязывать БД к реальному runtime/DNS, восстановление не равно полному DR; `teach:ee20a38d1bb5bf9e`: копирование отдельно от внешней оплаты; `teach:e5d999347879b0cf`: при foreign drift остановиться, не откатывать чужое состояние.
Первая попытка на Node24 получила unreadable SQLite/ABI и пустой JSON fallback; она не объявляется успешным recall.
