## Условия

- **TST-1, HIGH, structural.** Добавить в измеряемый ADR/архитектуру исполнимый протокол детерминированных PG гонок: реальный конкурентный INSERT в отдельной test schema с наблюдением блокировки/loser path и двумя разными паролями; отдельные барьеры после чтения credential и до настоящего fenced session insert с commit reset/erasure до продолжения. Контрольные утверждения должны доказывать, что события произошли в нужном порядке; таймаут — только предельная ошибка, `sleep`/один `Promise.all` не являются барьером. Дополнительно rollback fault до commit и проверка состояния снаружи транзакции. Область: ADR Confirmation и architecture/PG; FR-4/FR-5.
- **TST-2, HIGH, structural.** Зафиксировать исполнимый real Next HTTPS fixture: локальный TLS origin с согласованным `N5_PUBLIC_ORIGIN`, тестовым сертификатом/доверенной конфигурацией browser и чистым cookie jar, настоящим Next handler, isolated PG `*_test` и Redis. Из browser проверить принятый `__Host` cookie (атрибуты и отсутствие Domain), запрос защищённой страницы, full reload и повторный запрос без ручной подстановки cookie. Исключить skip как успех; безопасно завершить только созданные ресурсы. Текущий Next fixture использует `http` и сам вводит Cookie, поэтому не подтверждает требуемый браузерный контракт. Область: architecture/browser; FR-1/FR-2/FR-6.
- **TST-3, HIGH, structural.** В architecture связать named browser check с измеримым действием: у existing account заранее создать ненулевую attribution и частично использованный/зарезервированный trial; подать другой явный partner code и referral cookie, перехватить фактические `code.apply` запросы и signup-сигнал, сравнить полные значимые значения PG до/после. Проверить created и обычный login как положительные контроли соответствующего instrumentation, иначе ноль side effects может быть вакуумным. Выполнить real Next переход, а не только подменённый router; применить разные поддержанные pathname+query и reload. Область: architecture/browser и ADR Confirmation; FR-2/FR-4/FR-7.

1. `tests/auth.test.ts` — **`repeat registration authenticates only an active matching password`**: создать контролируемые created/existing/wrong/missing/erasing/unknown/store-false/store-throw исходы; проверить HTTP code/body, настоящую авторизацию выданного токена на success и отсутствие нового Set-Cookie на отказах. 2. `tests/database.integration.test.ts` — **`concurrent repeat registration grants once and authenticates only the winner password`**: два реальных PG клиента и подтверждённый барьер конфликта unique INSERT; при одинаковом пароле created и existing дают работающие разные сессии; при разных — created и conflict, действует только пароль победителя. Проверить rollback fault и что commit реально предшествует success; снаружи transactions не осталось account/grant/session после аварии.
3. `tests/browser/public-entry-cabinet.test.ts` — **`repeat registration conflict preserves email and switches to login`**: настоящий завершённый React render/effect, email остаётся, пароль пуст, alert виден и доступен, Enter/login/forgot работают; retry после 429/403/503/offline/bad JSON и объектов `null`, массива, пустого либо unknown outcome не выполняет redirect, RPC, signup и освобождает submit.
