## Условия для исправления

**RISK-01 — HIGH, structural.** FR-4 требует сохранять attribution и не отправлять signup при повторе, без исключения для старой вкладки. По ADR новый endpoint возвращает 200 и настоящую сессию для `existing`; нынешний `apps/web/src/app/AuthForm.tsx:63-72` после любого 2xx помечает регистрацию pending и вызывает `code.apply`, а `:43-45` отправляет signup после успешного RPC. `apps/web/src/server/partner.ts:23-33,65-101` допускает замену cookie/guest attribution на explicit и вставку attribution при её отсутствии. ADR явно принимает старый UI и предлагает проверить только новый browser context; это не закрывает уже открытую старую вкладку после выкладки. Требуется спроектировать согласованный со старыми клиентами контракт/переход, который сохраняет данные и signup-инвариант, либо получить явное изменение этого требования у владельца. Подтверждение — проверка старого реально существующего клиента против нового сервера с синтетическим аккаунтом и пригодным заменяющим кодом: нет изменения attribution и signup для existing; отдельно новый клиент/новый сервер created/existing и новый клиент/старый сервер, с честной обработкой несовместимости. Не предполагать, что требование реализовано простым HTTP 200 и новым UI.

**RISK-02 — HIGH, structural.** FR-6 запрещает запись пароля в logs. Существующий `apps/web/src/server/auth-handler.ts:63-68` логирует целиком произвольное исключение из пути, передающего пароль в auth/bcrypt; ADR и архитектура добавляют этот путь и проброс ошибок, но не определяют безопасную обработку содержимого исключения. Фактическая утечка текущим bcrypt/PG не установлена; нарушение гарантии воспроизводимо в модели при исключении зависимости, содержащем пароль в message/объекте. Зафиксировать ограниченный формат auth-логирования без raw exceptions/credentials и тест с искусственным исключением с маркером пароля в message и вложенных полях; для register и затронутого shared login пути 503 и журнал без маркера, без изменения приватного контракта login/forgot. Требование не подразумевает добавление credential-bearing телеметрии.

Выборочная проверка архитектуры: предложенный `FOR SHARE` + повторная проверка status/hash соответствует блокировке account до session в существующих reset/erasure; исход операции зависит от порядка сериализации, а после более позднего reset/erasure сессия должна быть отозвана. Это аргумент дизайна, не доказательство выполненного конкурентного теста. Регистрационный unique INSERT и атомарные grant/session также требуют реальной PG проверки, включая rollback. Успешный bcrypt compare без fenced session insert не является аутентификацией.
