# AUTH-001: понятная повторная регистрация

## Источник и статус

10.11.2026 владелец возобновил пункт1 ближайшего плана: «давай начнем с п1». Объём — AUTH-001 из docs/BACKLOG.md. Требуемое поведение ранее сформулировано прямо: существующий аккаунт обозначить пользователю и выполнить вход с правильным паролем. Макет новых состояний ещё требует согласования; приложение не менялось. Точные OpenSpec paths/hashes: requirements-revision.json.

## Заинтересованные стороны

Пользователь, возвращающийся в Clipmkr; владелец сервиса; блогер, чей реферальный источник должен сохраняться. Для всех ролей одинаковая парольная проверка; роль не назначается через регистрацию.

## Функциональные требования

- FR-1 MUST — новый нормализованный email: один аккаунт, действительная защищённая сессия, обычный переход в кабинет или разрешённый next. Пробный бонус выдаётся только при реальном создании аккаунта, по текущей политике.
- FR-2 MUST — существующий active аккаунт и верный текущий пароль: настоящая сессия через существующую парольную проверку; понятное сообщение «Аккаунт уже существует. Вы вошли» и автоматический переход без лишнего клика. Сообщение должно быть заметно и после перехода; не полагаться на мгновенно исчезающий текст.
- FR-3 MUST — существующий active аккаунт и неверный пароль: «Этот аккаунт уже существует. Войдите с прежним паролем или восстановите доступ». Форма предлагает «Войти» и «Забыли пароль?», сохраняет email. Нет новой сессии/cookie успеха, пароль аккаунта не меняется.
- FR-4 MUST — повторная и конкурентная регистрация не создаёт второй аккаунт, не повторяет пробный бонус, не меняет баланс/роль/пароль/источник привлечения. Реальный проигрыш INSERT-конфликта обрабатывается так же, как уже существующий адрес; предварительный SELECT не заменяет атомарность. Событие signup только для фактического создания, не для входа через register.
- FR-5 MUST — erasing/неизвестный статус/сбой session creation не дают входа. Статус удаления не раскрывается сообщением. Login сохраняет прежний одинаковый отказ для unknown/wrong/erasing; forgot/reset сохраняют прежние контракты.
- FR-6 MUST — сохраняются проверка Origin, ограничение частоты до чтения тела, максимальный размер тела и bcrypt-границы, безопасный next и __Host HttpOnly Secure SameSite cookie. Сетевой/серверный/непригодный ответ не создаёт на клиенте состояние «Вы вошли». Пароль не записывается в logs/URL/storage.
- FR-7 MUST — текущий внешний вид/светлая и тёмная темы, мобильная и desktop ширина. Сообщения доступны screenreader; клавиатурой доступны вход и восстановление; блокировка двойного submit и возврат после ошибки сохраняются.

## Явное изменение прежнего требования

Исторический FR-AUTH-001 docs/Specification.md:378 скрывал занятый email при регистрации. Прямое решение владельца AUTH-001 разрешает различимое сообщение только для повторной регистрации active аккаунта. Это сознательное ослабление сокрытия факта регистрации, не разрешение входа без пароля. Login и восстановление сохраняют прежнюю антиэнумерацию; IP rate-limit остаётся. Эту дельту требуется отразить ADR, OpenSpec и точной ссылкой в действующей документации до поставки, не скрывать конфликт текстов.

## Проверяемые сценарии

| Сценарий | Наблюдаемый результат |
|---|---|
| Новый email | Один account/session/trial grant, кабинет после reload |
| Повтор с правильным паролем | Тот же account, настоящий cookie, сообщение, без signup/bonus/referral rewrite |
| Повтор с неверным паролем | Понятный конфликт, нет новой сессии, email сохранён, вход/forgot работают |
| Два одновременных запроса с одним email | Один account/trial grant, второй исход корректен, пароли не переписаны |
| Старт erasure/reset между чтением и session insert | Session не принимается со старым hash/неactive status |
| 429/403/503/непригодный JSON/offline | Нет ложного успеха, можно повторить; guard до чтения тела |
| 390/1440px, обе темы, Tab/Enter/reload | Нет overflow/disabled trap, история состояния понятна |

## Переиспользование и границы

Существующие AuthService/PgAuthStore, bcrypt, session creation под повторной проверкой active/hash, SQL unique email, grantTrialTx, AuthForm, safeNextPath, штатный forgot и RPC attribution. Без новой БД/таблиц/провайдера/зависимостей. Настоящие аккаунты и платежи не нужны для тестов: только синтетические данные в отдельном *_test контуре текущего VPS. Cloud.ru/DNS в этот выпуск не входят.

## Авторизация и открытые вопросы

Бизнес-поведение согласовано прямыми сообщениями владельца; старое «отложено» заменено командой начать10.11. Решение реализации/макета не объявляется успешным gate. Единственное обязательное внешнее уточнение перед кодом — утверждение конкретного макета текущего пакета. Инженерные варианты выбираются по reuse/ADR и независимому QCSD.
