## Условия

**Q-01 — HIGH, structural.** FR-4 запрещает изменение источника и signup при повторной регистрации. ADR специально возвращает существующему клиенту 200/`ok:true` для authenticated existing и признаёт, что старый UI продолжит attribution/signup. Фактический `apps/web/src/app/AuthForm.tsx` считает любой 2xx объект успешным, при операции register ставит `pendingRegistration`, вызывает `code.apply`, а затем `observeSignup`; `apps/web/src/server/partner.ts` действительно позволяет замену cookie/guest attribution на explicit, а также запись новой attribution, когда её не было. Следовательно, открытая до обновления старая вкладка со старым JS после выкладки может нарушить оба FR-4 инварианта; проверка только нового browser context не закрывает этот обычный deployment seam. Требуется согласовать архитектурное обеспечение FR-4 для старого клиента при новом сервере либо получить явное решение владельца об изменении самого требования и ограничений. Подтверждение на реализации: воспроизводимый проход старого клиента с новым backend при существующем и отсутствующем источнике, проверка состояния attribution и signup, плюс сохранение разрешённого поведения обычного login. Риск изменения здесь следует из чтения исходного кода; новый backend ещё не реализован.

**Q-02 — HIGH, structural.** В утверждённом HTML обработчик `forgot-link` копирует введённый email в форму восстановления (`docs/design/2026-11-10-repeat-registration.html`, строка 23). Архитектура § «UI после перехода» прямо исключает prefill; действующий `RecoveryForm` не получает предзаполнение, а ссылка ведёт на отдельный `/forgot`. Следовательно, согласованный переход после неправильного пароля и проектируемый UX различаются. Нужно привести ADR/архитектуру и критерии к согласованному макету, сохраняя ограничение на передачу email без URL/storage, либо получить явно согласованное изменение макета. Подтверждение на реализации: конфликт → «Забыли пароль?» → тот же email в форме и рабочий возврат, без утечки в URL/storage.

**Q-03 — WARNING, structural.** Утверждённый HTML при успешном новом аккаунте показывает закрываемое сообщение «Аккаунт создан. Вы вошли.» (`showCabinet(false)`, строки 19 и 23); архитектура задаёт уведомление только для existing (§ UI после перехода), а описание пакета говорит лишь о прежней регистрации и переходе. Налицо неоднозначность между работающим конкретным макетом и описанным объёмом. Нужна явная увязка сценария нового аккаунта с согласованным пакетом либо конкретное подтверждение изменения, с проверкой созданного и существующего сценариев по отдельности. Это не утверждение о действующем runtime.
