# Независимое ревью оплаты и кабинетов

Дата: 02.11.2026. Репозиторий: `/home/clipmkr`. Проверка выполнена в отдельной сессии по требованиям, затем по коду и исходникам тестов. Старые reviews, 08*_report, docs/measurements, выводы incident и приватные конфигурации не читались. БД, серверы, ключи и внешние платёжные API не использовались; исходники не менялись.

## Подтверждённая находка

### P2 — тестовые оплаты ЮKassa становятся неотличимы от реальной выручки и увеличивают оценку вознаграждения

Основное место: `apps/web/src/server/payments/yookassa.ts:170–179` — нормализация теряет проверенный `raw.test`. Далее `apps/web/src/server/billing-handler.ts:222–225` передаёт платёж без признака среды; `packages/db/src/payments.ts:100–103` сохраняет финансовый факт без этого признака. `packages/db/src/blogger-report.ts:68–77` и `apps/web/src/server/partner.ts:129–138` включают любой подходящий `provider='yookassa'` в выручку. UI владельца называет её подтверждёнными оплатами пакетов, а `estimate()` вычисляет 20/30% от этой суммы.

Требование: core-cjm §2 требует явно различать реальную и тестовую среды; FR-4/FR-5 и ADR-001 требуют подтверждённую выручку и предварительную оценку от неё. Наличие `provider='yookassa'` отличает реальный адаптер от fake, но не настоящий денежный платёж от тестовой операции того же адаптера.

Воспроизводимый сценарий: настроить отдельный разрешённый тестовый магазин с `YOOKASSA_TEST_MODE=true`; привлечённый аккаунт с `credits_v1` покупает `start_v1` за условные 990 ₽; провайдер возвращает `test:true`, `succeeded`, уведомление проходит проверку. После обработки запись платежа и успешное исполненное намерение удовлетворяют SQL отчёта. Владелец получает 990 ₽ «выручки» и 198/297 ₽ оценки при ставке 20/30, хотя реального поступления денег не было. Если затем использовать ту же БД с боевым магазином, исторические тестовые суммы останутся неотличимыми от боевых. Даже при отдельной БД текущий UI отчёта не обозначает тестовую среду.

Локальное доказательство без сети/БД: реальный `createYooKassaProvider` вызван с `testMode:true` и локальным `fetchImpl`, возвращающим корректный JSON платежа с `test:true`. `verifyNotification()` вернул `kind='payment_succeeded'`, `provider.name='yookassa'`, `amountMinor=99000`; `Object.hasOwn(result.payment,'test') === false`. Далее потеря среды и попадание в отчёт установлены чтением SQL, а не фактической записью в БД.

Рекомендация: хранить среду на финансовом факте/намерении, передавать её через нормализацию и обработчик; исключать тестовые факты из реальной выручки и финансовых оценок либо показывать отдельный явно тестовый отчёт. Отдельно маркировать тестовый режим в платёжном UI.

## Проверенное и ограничения

Локально запущены только безопасные тесты без инфраструктурных адресов:

`env -u DATABASE_URL -u REDIS_URL -u S3_ENDPOINT node node_modules/vitest/vitest.mjs run tests/billing.unit.test.ts tests/partner.test.ts tests/blogger-policy.test.ts tests/payments-guards.test.ts --pool=forks --maxWorkers=1`

Результат: 4 файла, 72 теста, все прошли. Это не подтверждение работающего магазина.

Чтение кода не выявило дополнительных подтверждённых дефектов в доступе владельца, изоляции чужих кодов, идемпотентности успешного платежа, независимых агрегатах владельца, подсчёте уникальных плательщиков/активных людей, nullable 20/30 и отсутствии автоматических выплат. Владелец проверяется внутри транзакции изменения, audit атомарен; отчёт использует проверку владельца и единый снимок REPEATABLE READ. Платежи с несовпадающей идентичностью/суммой, needs_review и возвраты исключаются из отчёта. Отсутствие автоматического снятия прав после возврата задано существующей реализацией как разбор оператором; само по себе не объявлено дефектом.

Остаются пробелами доказательства, а не найденными дефектами: реальный checkout с настроенным магазином, подтверждение/отказ/повтор/возврат через настоящий провайдер, оплаченная нарезка после повторного входа, три браузерных контекста и совпадение кабинетов после полного CJM. Исходники интеграционных тестов просмотрены, но PostgreSQL/Redis/S3 и браузерный E2E в этом ревью не запускались. Реальная финансовая интеграция по этому ревью не получает PASS.
