## Подтверждённая находка

### P2 — повтор завершения после потери ответа перестаёт восстанавливаться, как только началась обработка

Файл: `apps/web/src/server/video.ts:132–136` (основная строка 136). Связанный клиент: `apps/web/src/app/upload/Uploader.tsx:51–61`.

Сценарий:
1. Все PUT приняты; форма сохраняет `current.parts` и отправляет complete.
2. Сервер склеивает файл и публикует задание, но успешный ответ complete теряется в сети либо пользователь нажимает «Приостановить» до получения ответа.
3. Воркер успевает перевести видео из queued в transcribing/selecting/rendering/done.
4. Пользователь нажимает продолжение с исходным файлом. Сохранённые parts заставляют форму пропустить create/PUT и снова отправить complete.
5. Сервер допускает повтор только при queued; для перечисленных последующих состояний строка 136 даёт 409 «Загрузка уже завершена». Клиент трактует это как ошибку, сохраняет ключ и parts, не делает предусмотренный переход. Все дальнейшие продолжения дают тот же результат.

Это подтверждённый дефект восстановления в проверенной реализации, а не утверждение, что его ввели рассматриваемые изменения. Он мешает общему обязательному сценарию прерывания/продолжения из `docs/acceptance/core-cjm.md`; ограниченная дельта навигации сама по себе не обязана менять серверный API.

Проверено локальным вызовом настоящего VideoService.complete с подставленным read-only результатом Pool.query, без БД, хранилища и очереди: queued → успех; transcribing/selecting/rendering/done → 409. Клиентский путь подтверждён чтением исходника. Полный сетевой сбой в опубликованном браузере не воспроизводился. Обработка и клипы при этом могут успешно завершиться; находка касается восстановления формы, не потери файла.

Исправление по смыслу: различать принятую передачу и дальнейшую стадию обработки при повторном complete; безопасно подтверждать уже принятую собственную запись без повторной постановки задания и без повторного расхода.

## Что проверено без дополнительных находок

- Серверный create использует только политику аккаунта из БД; strict schema не принимает клиентскую роль или лимит.
- Снимок 5400/7200/индивидуального лимита сохраняется в транзакции создания. Повтор ключа возвращает исходную запись. Изменение профиля не перезаписывает снимок.
- fileFailure проверяет границу включительно, acceptProbe повторяет проверку снимка до reserveVideoCreditsTx и минутной квоты. Технические helpers допускают до 86400 секунд, не оставляя прежнего скрытого барьера 5400.
- Миграция 026 добавляет defaults/CHECK; прежние видео получают 5400, а поля профиля по умолчанию не назначают блогера. Проверка миграции здесь статическая; реально миграция не запускалась.
- Прослежены публикация после COMMIT, ensureInitialAttempt, recovery/watchdog, снимок при retry и продолжение уже списанной transcribing-записи. Нового подтверждённого нарушения очереди не найдено.
- В Uploader идентификатор — обычный code без перехода; автоматический переход остаётся после успешного complete. Все PUT ожидаются в uploadParts через Promise.allSettled.
