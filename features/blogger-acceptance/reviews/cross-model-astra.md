## 1. P2 — потеря ответа завершения делает продолжение загрузки неуспешным после запуска обработки

Основное место: `apps/web/src/server/video.ts:132–136`. Связанный клиент: `apps/web/src/app/upload/Uploader.tsx:47–61`.

Сценарий:

1. Все PUT завершились; клиент сохранил `videoId` и `parts` в данных продолжения.
2. `/api/upload/complete` принял файл, записал `queued` и поставил задачу. Ответ до браузера не дошёл либо пользователь приостановил запрос после его принятия сервером.
3. Worker перевёл видео в `transcribing`, `selecting`, `rendering` либо `done`.
4. Пользователь выбирает тот же файл и нажимает продолжение. Поскольку `current.parts` уже есть, Uploader повторяет только complete.
5. Сервер поддерживает повтор только для `queued`; любое перечисленное дальнейшее состояние возвращает 409 «Загрузка уже завершена». Клиент трактует ответ как ошибку, не очищает resume и не выполняет переход. Каждый следующий повтор имеет тот же результат.

Это нарушает обязательный сценарий прерывания/продолжения из core-cjm и требование сохранять повторную передачу с прежним ключом. Сам файл не теряется, и карточку можно найти через список записей, но штатное продолжение не завершает пользовательский путь. Удаление ранней ссылки не создаёт дефект в сервере, однако и не устраняет его.

Доказательство: самостоятельно выполнены четыре изолированных теста настоящего `VideoService.complete`, по одному на каждое последующее состояние. Подменён только `Pool.query`; БД, S3 и очередь не вызываются. Все четыре воспроизвели 409. Тесты `/tmp/clipmkr-astra-repro.test.ts` специально утверждают **текущее ошибочное поведение**; их зелёный результат не означает исправления.

Нужное исправление: повтор уже принятого завершения должен возвращать возможность открыть ту же запись после перехода к обработке, без повторной постановки и без ослабления проверки владельца/удаления. Нужен регрессионный сценарий «ответ потерян → worker продвинул состояние → продолжение».

## 2. P2 — смена разрешённого реферального источника удаляет прежнюю подтверждённую выручку из отчётов исходного блогера

Основное место: `packages/db/src/blogger-report.ts:70–76`. Такое же поведение собственного кабинета: `apps/web/src/server/partner.ts:129–138`. Изменение источника: `apps/web/src/server/partner.ts:75–83`.

Сценарий:

1. Клиент зарегистрировался по cookie-ссылке блогера A, купил пакет; подтверждённая оплата отображается у A.
2. При следующем входе клиент вводит явный код блогера B. Это действующий пользовательский путь: `AuthForm.tsx:28–35` вызывает `code.apply` и при входе. `replacementAllowed` разрешает cookie → explicit даже для `activated`.
3. `PartnerService.apply` меняет единственную `attribution` клиента на код B и обновляет `assigned_at`. Идентификатор прежнего кода в самой атрибуции не сохраняется; `replaced_source` хранит лишь тип источника.
4. Отчёт соединяет payment исключительно с **текущей** атрибуцией. У A больше нет связанной атрибуции — прежняя оплата исчезает. У B оплата также не учитывается, потому что время её создания/оплаты раньше нового `assigned_at`.
5. Подтверждённая выручка и предварительные 20/30% за уже выбранный прошлый месяц уменьшаются у A без возврата или отмены платежа.

OpenSpec, сценарий «Проверенный платёж и повторное уведомление», требует, чтобы подтверждённый платёж относился к исходному блогеру и учитывался один раз. AM-3 дополнительно запрещает перенос старого платежа новому источнику. Реализация выполняет запрет переноса, но теряет первоначальную принадлежность совсем.

Доказательство: прямой путь по коду изменения атрибуции и обеим SQL-выборкам. Существующий `tests/blogger-report.integration.test.ts`, тест `replacement cannot move historical payments to the new source`, прямо ожидает `result.bloggers.every(row => row.counters.revenue_minor === 0)` после замены — тем самым фиксирует исчезновение, а не сохранение исходной принадлежности. Этот PostgreSQL-тест **не запускался** в рамках read-only ревью; статическое доказательство и фактический интеграционный прогон здесь разделены.

Нужное исправление: сохранять принадлежность подтверждённого финансового факта исходной ссылке либо историю атрибуции, позволяющую однозначно восстановить источник на момент платежа. Проверка должна ожидать старую выручку у A и отсутствие старой выручки у B после разрешённой смены кода. Обычную разрешённую замену источника не следует молча запрещать вместо решения финансовой принадлежности.

### Genuine finding C-1: P2 — один плательщик считается дважды в сводке блогера после смены его ссылки

Файл кандидата: `packages/db/src/blogger-report.ts:100–102`; первичная группировка — строки 68–78.

В AM-13 финансовые факты отвязаны от текущей attribution. Поэтому один клиент теперь правомерно может иметь две оплаты, исторически относящиеся к разным ссылкам **того же блогера**: первая по cookie-ссылке A, вторая после разрешённого ввода explicit-кода B. Для каждой ссылки `count(DISTINCT p.account_id)=1` верен. Но JavaScript суммирует оба значения в `blogger.counters.paying_users`, выдавая 2 платящих пользователя вместо 1.

Комментарий `attribution.account_id UNIQUE` больше не обосновывает сложение финансовых DISTINCT: снимки находятся в разных payment_intent и не обязаны ссылаться на одну текущую ссылку. Это новая регрессия именно при переходе на исторические снимки и нарушение FR-4 / AM-3: люди должны считаться отдельно от количества платежей. Сумма выручки и число платежей в этом сценарии остаются корректными.

Самостоятельное воспроизведение:

1. Создан отдельный одноразовый PostgreSQL 16 из уже имеющегося image, с `--network none`, без volume/bind main и без публикации порта.
2. В новую синтетическую БД применены все SQL-миграции кандидата, включая 027.
3. Созданы один блогер, две его ссылки, один клиент и два подтверждённых платежа по 99 000 копеек с разными снимками ссылок. Текущая attribution клиента указывает на вторую ссылку.
4. **Настоящий SQL из bloggerReport кандидата**, без переписывания условий, вернул две строки: `paying_users=1, payments=1, revenue_minor=99000` для каждой ссылки.
5. Настоящая функция `bloggerReport` кандидата получила эти PostgreSQL-строки через адаптер Pool и вернула `paying_users=2, payments=2, revenue_minor=198000` для одного блогера. Применён реальный код агрегации; подмена не вычисляла результат за функцию.

Артефакты: `/tmp/clipmkr-astra-am13-schema.sql`, `/tmp/clipmkr-astra-am13-fixture.sql`, `/tmp/clipmkr-astra-am13-query.sql`, `/tmp/clipmkr-astra-am13-rows.jsonl`, `/tmp/clipmkr-astra-am13-check.cjs`. Отдельный контейнер и его анонимный volume удалены после проверки.

Исправление должно считать DISTINCT плательщиков на уровне блогера независимо от DISTINCT по ссылкам. Нужна проверка одного клиента с двумя подтверждёнными оплатами по двум ссылкам одного блогера: сводка 1 человек / 2 платежа, по каждой ссылке 1 человек / 1 платёж. Простое суммирование допустимо для платежей и выручки, но не для этого множества людей.

### Что подтвердилось в кандидате

- Прежнее исчезновение выручки при смене attribution исправлено по выбранному плану: финансовые JOIN используют `payment_intent.referral_partner_code_id`. В синтетическом PostgreSQL первая ссылка сохранила свои 99 000 копеек при текущей attribution на второй ссылке.
- Снимок создаётся при первой вставке намерения в транзакции под SHARE-lock аккаунта. `PartnerService.apply` берёт конфликтующий NO KEY UPDATE-lock того же аккаунта, поэтому смена источника сериализуется с созданием. Повтор ключа читает старое намерение и не пересчитывает снимок. Это проверено по коду; конкурентный прогон create/apply в этой сессии не выполнялся.
- Backfill не переносит старые платежи новой attribution, если её `assigned_at` позже intent.created_at; неизвестная принадлежность остаётся NULL. Проверены SQL и тест backfill; полная цепочка миграций реально применена на пустой синтетической БД. Сценарий upgrade наполненной БД отдельно не запускался.
- Обе сводки сохраняют фильтры `yookassa`, `succeeded`, `needs_review=false`, совпадение account/provider ID/amount с intent, успешное fulfillment, разрешённые SKU и исключение self-referral. Временной фильтр использует момент сохранённого намерения вместо изменяемого assigned_at. У владельца сохраняются границы московского месяца. Настоящий refund в синтетической таблице исключил первую оплату: первая ссылка стала 0/0, вторая сохранила 1/99000.
- `ON DELETE SET NULL` не конфликтует с прежним immutable-trigger, который контролирует другие поля. В синтетической БД удаление первой partner_code успешно завершилось и обнулило только соответствующий snapshot. Это проверяет новый FK; полный retention с S3 не запускался.
- AM-14: общий layout показывает явную учебную маркировку при `payments.mode='live' && payments.testMode`. Самостоятельно выполнен новый unit-тест **кандидата** `test payment environment is explicitly labelled`: **1 passed**, остальные 24 теста файла намеренно отфильтрованы. Проверены test=true, test=false и mode=off. Команда использовала `/tmp/clipmkr-astra-am14.config.mjs`; исходники кандидата не изменялись.
