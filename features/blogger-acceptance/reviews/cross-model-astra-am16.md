# Независимое ревью AM-16

Дата: 02.11.2026. Репозиторий: `/home/clipmkr`. Сессия: `/root/cross_model_astra`, только reviewer, без coding-контекста автора. Модель ревьюера по spawn metadata, сообщённым координатором: **gpt-6-astra**, новая сессия `fork_turns=none`. Это точный ID запрошенной модели инструмента, не независимая runtime attestation. Автор AM-16 по тем же metadata: `gpt-6.1-terra`.

**Результат: доказанных дефектов узкого изменения AM-16 не обнаружено. Требуемое поведение подтверждено собственным изолированным PostgreSQL-прогоном. Полный продуктовый PASS не выставляется.**

Сначала прочитаны AM-16 согласованного плана `features/blogger-acceptance/06_implementation_plan.md`, ADR-001 с AM-13 и OpenSpec blogger-cabinet. Ожидаемое поведение: убрать сравнение часов `payment.paid_at >= payment_intent.created_at`, сохранить месячную принадлежность по paid_at провайдера, финансовые проверки и неизменный снимок источника; NULL snapshot не связывать с появившейся позднее attribution. Авторские отчёты и заявления о тестах не использовались.

После этого найдены и проверены:

- `packages/db/src/blogger-report.ts`: из `verified_sales` удалено только межсистемное сравнение времени; обе агрегации используют этот общий отфильтрованный набор. Границы месяца по Москве остались на `payment.paid_at`.
- `apps/web/src/server/partner.ts`: финансовая сводка native-кабинета также больше не сравнивает часы приложения и провайдера.
- В обеих выборках сохранены provider=yookassa, succeeded, needs_review=false, совпадение account_id / provider_payment_id / суммы с intent, успешный intent и fulfilled_at, разрешённые SKU, исключение self-referral, JOIN по `referral_partner_code_id` без fallback на текущую attribution.
- `packages/db/src/payments.ts`: снимок по-прежнему создаётся при первой вставке под account-lock; повтор idempotency_key не меняет его. Изменение AM-16 не затрагивает создание/проверку платежа.
- Новые тесты clock-skew и NULL snapshot в двух integration-файлах прочитаны; результаты их выполнения автором не приняты за доказательство.

## Собственная проверка

Создан отдельный одноразовый PostgreSQL 16 из локального image, с `--network none`, без публикации портов и подключения main volumes. В пустую синтетическую БД применены актуальные SQL-миграции. Использовались только вымышленные аккаунты и платежи.

Реальный SQL owner-отчёта исполнялся в PostgreSQL, а настоящая `bloggerReport` из проверяемого дерева обрабатывала его строки через адаптер Pool. Финансовый SQL native `PartnerService.dashboard` извлечён из актуального исходника и также исполнен в PostgreSQL без изменения условий. Адаптер не заменял финансовую логику, но не воспроизводил единую клиентскую транзакцию и конкурентные блокировки; эти свойства не являются предметом AM-16.

Успешно выполнены следующие самостоятельные сценарии:

1. `intent.created_at = 2026-11-10T00:00:14Z`, provider `paid_at = 2026-11-10T00:00:00Z`: обе сводки учитывают платёж, несмотря на отставание часов на 14 секунд.
2. Один клиент, две ссылки одного блогера, два подтверждённых платежа: owner возвращает 1 плательщика / 2 платежа / 198 000 копеек; каждая ссылка сохраняет свой платёж на 99 000 копеек. Текущая attribution клиента находится у второй ссылки.
3. По отдельности проверены семь отрицательных финансовых контролей **в обеих выборках**: refunded, needs_review, fake-provider, несовпадение amount, отсутствие fulfilled_at, canceled-intent, несовпадение provider_payment_id. Каждый исключает только соответствующий платёж; остаются 1 платёж / 99 000 копеек.
4. Оплата вне выбранного месяца исключается owner-отчётом. Native кабинет намеренно считает весь период, поэтому месячный фильтр к нему не применяется.
5. Удаление текущей attribution не меняет финансовые суммы и исходные ссылки: отчёты используют snapshot.
6. NULL snapshot исключается. После создания новой текущей attribution исходный NULL-платёж не приписывается ей ретроактивно: обе сводки остаются на 1 платеже / 99 000 копеек.

Self-referral, SKU и совпадение account_id дополнительно сверены по SQL; отдельные новые синтетические сценарии на эти неизменённые условия в данном узком прогоне не создавались.

Артефакты: `/tmp/clipmkr-astra-am16-schema.sql`, `/tmp/clipmkr-astra-am16-check.cjs`, `/tmp/clipmkr-astra-am16-null-check.cjs`; синтетическая базовая фикстура — `/tmp/clipmkr-astra-am13-fixture.sql`. Команды собственных проверок: `node /tmp/clipmkr-astra-am16-check.cjs` и `node /tmp/clipmkr-astra-am16-null-check.cjs`. Оба завершились с exit 0. Одноразовый контейнер и его анонимный volume удалены. Код, main БД и существующие сервисы не менялись.
