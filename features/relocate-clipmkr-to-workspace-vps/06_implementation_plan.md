# Предварительный план переноса

Статус: DRAFT; K1/K2, независимая проверка и разрешение на cutover ещё не получены. Не инструкция к немедленной записи.

1. Read-only inventory источника и цели: домен, контейнеры/образы/digests, Compose labels/mounts, схема и все хранилища, активные задания/передачи, disk/RAM, внешние сервисы.
2. Зафиксировать точный исходный релиз; подготовить ADR единственного writer и rollback, модель границ PostgreSQL/Redis/S3/support; проверить требования и риски отдельными ролями.
3. Сохранить локальные данные и конфигурацию; получить исходный backup, проверить restore в существующем PostgreSQL и полную сверку; исходная работа продолжается. Только после плановых gates готовить runtime.
4. Подготовить существующий локальный стек той же версии. До приёмки: без обработки скопированных очередей, scheduler, истечения хранения и финансовых действий на оригиналах; проверочные данные/медиа в отдельной тестовой области настоящего S3. Сохранять оригинальные ссылки.
5. Проверить целевой HTTPS и origin до DNS-перехода; выполнить UI E2E, почту, S3, тестовую оплату в согласованном контуре; дать владельцу ссылку/способ ручной проверки. Не считать IP-origin полной проверкой cookie/CORS/callback для домена.
6. После приёмки согласовать окно и DNS. На источнике временно закрыть регистрации, загрузки, checkout и остальные записи, обработать очередь и платежи/поздние webhook по явному протоколу; получить финальный согласованный срез PostgreSQL/Redis, проверить равенство. Нулевой размер очереди не доказывает отсутствие активного задания.
7. После отдельного разрешения переключить вход; старый IP проксирует на новый upstream либо обслуживает только maintenance. Writers только на одной цели. Проверить домен/TLS/сессии/webhook/получение письма/клип; мониторить ошибки/ресурсы.
8. Сохранить старый сервер и backup; откат до новых записей и после них выполнять по разным проверенным процедурам. Не терять новые регистрации/платежи при возврате DNS.

## Команда и инструменты
Координатор: факты, требования, сохранность и публикация. Архитектор gpt-6-astra xhigh: читающий разбор существующих средств. Автор исполняемых изменений gpt-6.1-sol high после gates; независимый reviewer gpt-6-astra xhigh в новой сессии без coding-контекста. Если артефакт написан Astra — reviewer Terra. Фактические сессии/результаты фиксировать отдельно; модель запроса не доказывает обслуживающую модель.
Используем feature-adr, закреплённые dz/OpenSpec, существующий Docker Compose/Caddy, pg_dump/pg_restore, штатный S3 SDK, Playwright. studio-extended-qe применяется как метод требований/рисков/anti-drift, с протоколами Clipmkr; инфраструктуру и команды Product Studio сюда не переносить.

## Состояние
Выполнены read-only inventory основных БД обоих серверов, предварительные backup основной/helpdesk/локальной БД с exit0/PGDMP/SHA-256 и отдельная архитектурная консультация. Backup restore, deploy, freeze, DNS, финансовые изменения и E2E NOT RUN.

Дополнение архитектурного разбора: локальную n5 сохраняем; для импорта проектируется отдельная БД существующего PG, конкретная роль/имя ещё не определены. Точный Redis binding требует inventory. Поддержка входит в перенос целиком: после проверки её PG/Redis/uploads и identity/inbox также переносим действующий Libredesk и маршрут на этот VPS. На переходе старый сервис сохраняется, старый сервер не выключается. Полный перенос не принимается, пока зависимость от старой поддержки не устранена. Прямой restored web с исходным S3 не запускать из-за немедленного retention/watchdog.


## Обязательные уточнения раннего независимого ревью
Проверка документов Terra xhigh выявила следующие условия до исполнения; это открытые условия, не закрытый native QCSD:
- Точный список всех writers/direct endpoints/cron и исполнимые команды fence/drain с проверкой активных транзакций, workers, multipart. Поздние webhook должны надёжно доставляться/повторяться и сверяться с provider; закрытие checkout не завершает старые оплаты.
- Инвентаризация старого backend TEST webhook: он использует отдельную n5_referral_paytest_test/Redis9. Его данные и маршруты сохраняются, не объединяются с основной БД и не чинятся во время переноса. Read-only snapshot6accounts/4video/10clip/6payments; backup восстановлен отдельно.
- Полная сверка исходного согласованного snapshot со всеми строками/связями, Redis persistence, S3 whitelist/целостностью и multipart; preliminary live counts не являются финальной сверкой.
- Изоляция E2E должна быть технической: запрет оригинальных финансовых действий, рассылок, paid-model вызовов и удаления/перезаписи пользовательского S3; разрешённые TEST действия только в действующем ограничении.
- Приёмка HTTPS основного имени до DNS: реальная cookie/CORS/callback/XFF цепь. Конкретные TTL, права DNS и механизм TLS ещё не установлены.
- Измерить запас диска/CPU/scratch и время restore+проверки; условие окна — отсутствие потери подтверждённых записей при управляемом переключении.
- Для отката после новых записей сохранить актуальное состояние вне целевого VPS и проверить обратный restore. При недоступности нового VPS и отсутствии актуальной доступной копии гарантировать нулевую потерю невозможно; миграционный rollback не объявляется готовой системой аварийного восстановления.
