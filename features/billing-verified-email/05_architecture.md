# Архитектура BILLING-001

1. Auth → `/api/checkout` → `createPaymentIntent` под блокировкой аккаунта →
   допуск подтверждённого email и снимок адреса → прежний адаптер ЮKassa.
2. Подлинный webhook/сверка → один платёж и начисление → одна строка квитанции.
3. Web watchdog → проверка адреса и подтверждённой оплаты → lease/freeze →
   прежний Resend-адаптер и его ограниченный таймаут → фиксация исхода.
4. `readPaymentIntent` и экран возврата читают исход покупки и статус письма.
   Проверка почты использует существующий recovery flow и allowlist SKU.
5. Erasure очищает адреса и письма в транзакции удаления. Состояние
   оплаты, начисления и задачи сохраняет прежнюю границу восстановления.

## Граница интерфейса

- Страница пакетов читает текущий подтверждённый адрес из существующего аккаунта;
  одинаковое правило действует в транзакции независимо от интерфейса.
- Ссылка подтверждения переносит только известный идентификатор пакета. Токен
  остаётся в fragment; `sku` влияет на предложение и ссылку возврата, сервер всё
  равно проверяет каталог и доступ. После подтверждения показывается явный возврат.
- Для запроса интерфейса непрозрачный HMAC идентификатора аккаунта связывает
  показанную форму с текущей сессией, устаревшая форма завершается без checkout.
  Ключ попытки хранится в `sessionStorage` по аккаунту и SKU до достоверного
  результата; потеря ответа и перезагрузка вкладки сохраняют попытку.
- На экране результата квитанция показывается при подтверждённом начислении.
  Короткий ограниченный опрос до получения итогового статуса использует имеющийся
  owner-only API. Отказ почты не меняет исход оплаченной покупки.

- Прямой checkout остаётся доступен по API с подтверждённым текущим адресом.
  Для формы кабинета обязателен её собственный непрозрачный контекст. Перед
  переходом к ранее полученной форме провайдера клиент подтверждает владение
  намерением существующим GET с действующей cookie, без новой операции у
  провайдера. Перемонтирование отменяет асинхронный обработчик.
- После отказа отправить подтверждение сохраняется пакет и доступен повтор.
  В новой сессии действует существующий контракт токена. Если старый токен
  неприменим, заново запросить письмо из вошедшего аккаунта с тем же SKU.
  Старый неизвестный платёж показывает путь к поддержке и оставляет ключ попытки.
- При неопределённой доставке интерфейс сообщает о необходимости проверки.
  Покупка остаётся подтверждённой, повторное открытие результата обновляет статус.
  Выделенная область статуса не меняет фокус при фоновом обновлении.
- TEST и неизвестная идентичность не направляют письмо реальному адресату даже
  при включённом боевом транспорте. Сверяем идентичность связанного платежа.
  Перед каждым claim проверяем подтверждённый адрес, возврат и активность аккаунта.
  Отказ записи квитанции откатывает само начисление. Устаревшее завершение
  проверяет собственную версию lease и не восстанавливает очищенный payload.

QT-1 привязывает асинхронный эффект к наблюдаемому порядку транзакций:
PG-барьер доказывает перекрытие начислений, управляемые часы и отложенный mail
ответ доказывают отклонение старого lease после повторного claim или erasure.
Точные oracle и контрольные мутации описаны в ADR-001.
