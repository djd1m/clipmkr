## Находки

**QL-01 — HIGH, structural. Конкурентный provider-оракул может быть неверным.** План 06 TASK-3 требует последовательный/конкурентный одинаковый key и один intent, но сам по себе один intent не доказывает один платёж у provider. В `tests/fixtures/fake-yookassa-server.ts:66` lookup ключа происходит до `await readBody` (строка 69), а запись в map — после await (строка 74): два перекрывающихся запроса могут оба не увидеть ключ и создать разные платежи. Существующий `tests/billing.integration.test.ts` AC-2 проверяет один provider payment на последовательном повторе. Это подтверждённый разрыв дизайна теста и возможная гонка фикстуры по чтению кода, не доказанный runtime дефект. Уточнить confirmation: контролируемо достигнуть параллельного create, использовать локальный provider-двойник с атомарной идемпотентностью, проверить один intent, один provider payment/идентичность idempotence key и отсутствие двойного grant; тест должен падать при неверном ключе или повторном создании. Указывать границу двойника: настоящую ЮKassa и её временное окно он не доказывает.

**QL-02 — HIGH, structural. Нет конкретного отрицательного оракула `payment.test` на webhook после отзыва.** FR-6 и архитектура 05 требуют сохранить проверку `payment.test`, а 06 TASK-3 описывает verified duplicate webhook и live mismatch в guard, TASK-5 — инверсию testMode preflight/predicate. Они не задают отрицательный webhook с реальным адаптером, где provider requery возвращает `test=false` при конфигурации TEST, и не требуют показать отсутствие записи/grant. В `apps/web/src/server/payments/yookassa.ts:152` проверка есть сейчас; найденный `billing.integration.test.ts` использует fixture с `test=true` по умолчанию и не содержит негативного сценария mismatch. Это пробел доказательства сохранения, а не утверждение, что проверка в существующем коде не работает. Уточнить confirmation: создать TEST intent локально, отозвать исключение при сохранении TEST provider, подать уведомление с provider requery `test=false`, требовать rejection и нулевые новые event/payment/grant, затем корректный `test=true` применить ровно один раз и повторить без нового grant. Тест должен краснеть при удалении проверки `raw.test`.

## Ограничения и handoff

Нет runtime-изменений, реализации тестов фичи, выполнения тестов, мутаций, провайдера, контейнеров, SSH или Cloud; никаких PASS по коду не заявлено. Анализ гонки статический: конкретное чередование следует воспроизвести на изолированном fixture. Возможность local fixture с атомарным ключом и фактическую связку config → runtime → handler → PG необходимо подтвердить при implementation/QE. Документальный anti-drift: hash дельты совпадает; code/spec anti-drift не применим до реализации. Условия принадлежат qcsd-quality; собственную проверку исправлений на новой измеренной ревизии выполняет эта же исходная роль. Другие QCSD-роли, gate, K1/K2 и ручная приёмка не подменяются этим отчётом.
