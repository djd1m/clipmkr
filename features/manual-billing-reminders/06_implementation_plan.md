## Модули и псевдокод

Два новых production-модуля, разные basename для глобального K1; каждый ≤500 строк без сжатия ради лимита. `packages/db/src/billing-notice-ledger.ts` владеет facts reader и SQL lifecycle; `apps/web/src/server/billing-notices.ts` — контентом, bounded dispatch и per-pool cursor. DB не импортирует web. Existing `credits.ts`, `plan.ts`, `payments.ts`, `support/mail.ts` не растут. Общий mail framework, новый сервис/queue/routes/UI/payment flow не нужны. Native retention journal служит образцом, таблицы не смешиваются.

DB exports в `K1names.json`: `readBillingNoticeEligibility`, `prepareBillingNoticeBatch`, `claimBillingNotice`, `completeBillingNotice`, типы `BillingNoticeEligibility`, `BillingNoticePayload`, `BillingNoticeClaim`; `index.ts` только re-exports. `BillingNoticePayload` — структурный контракт пяти полей from/to/subject/text/html, совместимый с existing `RetentionNoticeMessage`; транспорт не дублируется. В existing enums добавить только `BILLING_NOTICE_STATE` и `BillingNoticeState`; offset SQL_ENUMS — string literals ['1','3'], без нового parser/framework. WEB export только `billingNoticesTick`.

1. `readBillingNoticeEligibility(db,accountId,now)` читает права отдельно от proof: все фактические source=payment base/addon intervals с валидными start/end, включая TEST/unknown/remaining0, затем sorted union с next.start<=end и компонентой start<=now<end. Не фильтровать rights по revenue/SKU/proof и не подменять DB error отсутствующим interval. Trial/recovery/bonus/disconnected future исключены. Account payment legacy end учитывается как фактическое текущее право без выдуманного start; если точная связь участвующего legacy окна с payment identity не доказана — send=false, права не сокращаются.
2. Для найденной компоненты отдельно вычислить наличие хотя бы одного verified LIVE через accepted030 shared helper (включая смежный future LIVE), и relevant review/refund у current/future интервалов этой компоненты. Отсутствие proof у TEST/unknown хвоста само по себе не отменяет уже доказанный LIVE в той же компоненте. Старый несвязанный/истёкший refund не является account-wide veto; проверять active/credits_v1/verified recipient/owner+operator exclusion/checkout. Reader возвращает full end и отдельные qualification facts, а не сокращённый LIVE end.
3. `prepareBillingNoticeBatch` выполняет bounded lease recovery/discovery/due selection ≤100, с cursor и проверкой monotonic admission между DB операциями. Key — SHA256(account|exact UTC end|offset), UNIQUE(account,end,offset), INSERT ON CONFLICT DO NOTHING. Не заменять existing terminal tombstone; не ограничивать discovery только платежами LIVE так, чтобы потерять продолжение TEST/unknown tail. Повторный проход должен находить уже созданные pending/failed/unknown для revalidation, даже пока proof временно недоступен. Leases recovery использует актуальный state/lease predicate после concurrent completion, не перезаписывает accepted/new lease.
4. `claimBillingNotice` использует native transaction и LOCAL lock_timeout100ms/statement_timeout1s: узнать account без lock → account FOR NO KEY UPDATE → creditAccountLock → notice FOR UPDATE; затем повторно сверить ownership/facts/fresh wall clock и monotonic admission перед commit. Не брать payment-advisory lock. SQL ошибки/lock timeout означают defer/rollback, не fictitious NULL-rights. Busy не расходует attempt; DB outage останавливает волну.
5. Изменённый known tail/offset, реально отсутствующая current компонента, expired/exhausted или недопустимый status/recipient → superseded; erasure — FK CASCADE. При сохранённых правах и временном relevant review/неполной LIVE qualification сохранить pending/failed/unknown без HTTP/attempt/new key и без изменения frozen bytes/timestamps. После reconcile требуется тот же end/offset/window и полная eligibility. Accepted/superseded не открывать; hypothetical restore deleted rights не входит в этот контракт (см. уточнение origin RISK-01).
6. До first attempt payload является кандидатом; финальный claim строит его заново из актуального verified recipient/subject/МСК end, затем атомарно freezes payload/hash/key, first timestamp, increments attempts, sets sending/lease2min. Pure synchronous content builder из WEB допускается параметром DB claim, без I/O. Wire hash использует тот же порядок полей и to:[email], что `SupportMailer.sendRetention`; после attempts>0 exact bytes/key/recipient/first timestamp неизменны, last timestamp меняется только новым claim. Max3, пауза1h и 0<=now-first<23h сохраняются; backward now<first/last→no send, новый key не создаётся.
7. После commit непосредственно `sendRetention`; HTTP никогда не внутри TX и claimed event не откладывается в другую очередь. `completeBillingNotice` CAS(id,state=sending,attempt,last_attempt_at); stale completion0. Потеря response/completion оставляет unknown/lease recovery, accepted≠delivered. Aggregate finite reasons, без recipient/payload/key/raw exception/provider body.
8. `billingNoticesTick` после media использует monotonic20s admission до claim и после locks, ≤4 попытки HTTP, ≤2 simultaneous (две волны) и existing shared mail cap4; in-flight8s дожидается, без fire-and-forget. Per-pool WeakMap cursor использует native watchdog pattern; busy первый account не удерживает backlog. 20s — admission, не обещание времени всего watchdog. Flag false/missing sender/недоступный checkout не вызывает payment или mail; ошибки новой ветки локальны.
