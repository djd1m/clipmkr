## Протокол доступа Cloud-ВМ к собственному HTTPS

Наблюдение: с controller публичный HTTPS отвечает 200, а из самой Cloud-ВМ
обращение к собственному публичному адресу завершается timeout. TLS через
loopback с правильным SNI и проверкой сертификата отвечает 200. Исходный
маршрут к собственному публичному IPv4 шёл через внешний gateway.

В таблицу local только этой тестовой ВМ добавлен временный маршрут к её
подтверждённому собственному публичному IPv4. После этого штатный urllib HTTPS
из ВМ и внешняя проверка с controller получили 200. Все семь контейнеров
сохранили IDs/StartedAt/state/restart counts. Постоянная конфигурация сети,
публичный DNS, proxy configuration и production не менялись.

Параметр берётся из закрытой привязки именно этой ВМ, а не из произвольного ввода:

```bash
sudo -n ip route add local "$CLOUD_SELF_IPV4/32" dev lo table local
ip -j route get "$CLOUD_SELF_IPV4"
# Откат только добавленного этим оператором маршрута:
sudo -n ip route del local "$CLOUD_SELF_IPV4/32" dev lo table local
```

Маршрут непостоянный; после reboot его требуется заново проверить и, при
сохранении этой сетевой особенности, восстановить. Точные адреса, before/after,
привязки и квитанции хранятся вне Git. Это установленный обход наблюдаемого
маршрута; причина поведения облачной сети на стороне провайдера не утверждается.
