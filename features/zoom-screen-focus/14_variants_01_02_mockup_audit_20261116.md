## Сопоставление геометрии

Для наглядности значения ниже приведены к вертикальному кадру360×640. Макет — его CSS проценты без декоративной рамки; округление/рамка меньше2px не объясняют крупные расхождения. Фактические browser measurements исходного HTML тоже сохранены приватно.

| Элемент | Исходный макет | Настоящий результат |
|---|---|---|
|01: экран|Примерно x0,y173,360×213|x0,y160,360×213; весь выбранный browser сохранён|
|01: камера|Справа поверх screen: x259,y320,90×51|По центру над screen: x156,y133,47×27; примерно в1,9раза меньше по ширине|
|02: экран с исходным ROI|x0,y179,360×273; вся ширина|x57,y133,247×187; боковые поля и ширина примерно на31% меньше|
|02: камера|Справа сверху: x223,y64,115×65|По центру снизу: x113,y325,133×75; другой порядок и положение|
|02: простое переключение номера|В макете показан отдельный увеличенный рабочий ROI|Сохраняется прежний широкий screen; исходная рабочая область02 автоматически не выбирается|

### Почему поздние документы не доказывают соответствие оригиналу

В [ADR-001](03_adr/001-compose-confirmed-source-regions.md) текущая политика уже описана иначе: для01 camera не пересекает screen; для02 экран в зонеy400–960 из1920, camera ниже вy976–1200. Реализация соответствует этой поздней геометрии, но **сама эта геометрия расходится с исходным макетом**.

[Согласование selector](ui-approval.md) подтверждает закрытые дополнительные настройки,03 по умолчанию, доступность01/02 и явную пересборку. Оно не является доказательством отдельного согласования перестановки camera/screen и уменьшения экрана в01/02. Схематичный selector и исходные реальные композиции — разные артефакты; считать совпадение подписи варианта визуальной приёмкой нельзя.

UI действительно подписывает01 как «камера в свободной области», а02 как «Экран сверху, камера снизу». Поэтому проблема не ограничена итоговым FFmpeg: новая компоновка закреплена в shared planner, предпросмотре и тексте UI.

### Дополнительное ограничение настройки ROI

По чтению `ClipLayoutChoice.regionChange`: radio меняет только variant; screen ROI не выбирается отдельно для каждого варианта. У screen естьx/y/width, а height пересчитывается пропорционально прежнему размеру. Для контрольного screen1496×886 смена ширины сама по себе не даёт исходное соотношение сторон930×704 макета02. Это ограничение штатных controls, не доказательство невозможности задать такую ROI через API — для MP402-original-roi она была явно передана поддерживаемому renderer.

Сообщение «Выделенная область экрана увеличена» зависит от ненулевого focus и может оставаться для01/02, хотя planner использует focus только в03. Это подтверждено исходниками, но отдельный живой browser-тест этих controls в данном аудите не запускался.
