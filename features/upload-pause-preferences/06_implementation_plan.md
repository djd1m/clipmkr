# План UPLOAD-001 — продолжение с изменёнными настройками

Макет согласован владельцем, допуск к реализации фиксируется отдельно. Цель — один проход от паузы до готового клипа.
Требования и варианты решения изложены в 01 и ADR-001. OpenSpec хранит [дельту требований](../../openspec/changes/upload-pause-preferences/specs/upload-resume/spec.md).

Inputs read: `01_requirements.md`, `02_reuse_inventory.md`, `03_adr/001-upload-final-settings.md`, `05_architecture.md` и базовый код Uploader/VideoService.

1. Согласовать [конкретный макет](mockup.html) для FR-1 и FR-2. Закрыть адресный QCSD по трём
   перспективам и запустить K2 и admission закреплённого feature-adr. K1 проверяет
   новые имена, если они появляются. До кода сделать фактические записи этапов.
2. FR-1 и FR-2. В `Uploader.tsx` оставить уже проверенный File на явной паузе в пределах
   текущей вкладки. При восстановлении заполнить настройки из сохранённой записи один
   раз; повторный выбор файла сохраняет текущий черновик. Прежние AbortController,
   полный SHA-256, владение и явное действие остаются. Согласованный snapshot
   сохраняется до сетевого вызова; недоступный storage прекращает операцию.
3. FR-4, ADR-001. В `upload-resume.ts` сделать дополнительные данные обратно совместимыми.
   Исходные параметры create неизменны. Последние настройки продолжения хранятся
   локально. Вместе с полным manifest сохранить точный итоговый набор. Старый
   полный manifest без новых полей повторяет старый Complete.
4. FR-3 и FR-4, ADR-001. В `upload-contract.ts` и `video.ts` принять необязательный полный снимок
   настроек, переиспользовать `parseCtaTarget` и обновить поля в той же операции,
   что статус queued под существующим FOR UPDATE. Отказ/чужой доступ, старые клиенты
   и конфликт устаревшего снимка не переписывают состояние. Повтор после queued
   использует прежнее идемпотентное enqueue. Нет миграции БД.
5. FR-1…FR-5, ADR-001. Расширить существующие проверки. В браузере — пауза, изменение группы полей,
   повтор/перезагрузка, тот же ключ, запрет нового запроса до явного действия,
   прежние проверки SHA и смены аккаунта. На настоящем S3 и PostgreSQL —
   подтверждённая первая часть, применение последних настроек и один слот.
   Для одновременных и повторных Complete проверить один итоговый набор и
   отсутствие повторной постановки/резерва. Точечный RED до реализации.
6. Автор `gpt-6.2-sol high`, отдельный проверяющий `gpt-6-astra xhigh`, чистая
   сессия с входными документами. Один набор целевых тестов и типизация,
   адресное повторение только при ошибке или изменении. Сверить фактический diff
   с требованиями и отметить ограничения проверок.
7. FR-5. Подготовить безопасную поставку текущего VPS и один поток через
   опубликованный интерфейс до готового клипа с реальным S3. Использовать
   тестовый аккаунт, синтетическое медиа и принадлежащие тесту ключи,
   сверить квоты/состояние и дать владельцу ссылку для ручной приёмки.
