# ADR-001 — итоговые настройки фиксируются при завершении передачи

Статус: предложено для QCSD и согласования UX.

Старый ключ связывает размер и первоначальные настройки. Если изменить тело
повтора `video.create`, действующий сервер вернёт конфликт. Пользователь должен
сохранить те же multipart-части и применить отдельно изменённые параметры.

## Decision

Рассмотрены сохранение настроек через отдельный PATCH и один финальный снимок
в `upload/complete`. Первый вариант требует ещё одного независимого запроса и
разрешения гонки между изменением и запуском обработки. Выбран второй:
`video.create` получает неизменяемый исходный snapshot; отдельный локальный
снимок сохраняет введённые параметры; `complete` получает необязательные финальные
параметры. БД принимает их только один раз при переходе из uploading в queued
под существующей блокировкой. Проверки файла и parseCtaTarget предшествуют
запуску обработки. Старый запрос без нового поля работает по прежнему контракту.

При неизвестном Complete повторяет точный сохранённый запрос с тем же файлом
и манифестом. Вкладка не редактирует этот набор. Конкурирующий или поздний
повтор с другим набором не переписывает запись. Сервер сообщает конфликт
настроек при отличии от фактически принятого состояния; интерфейс предлагает
открыть запись. Отсутствие доступа не раскрывает состояние чужой записи.
После явной паузы на этапе передачи в текущей вкладке разрешено сохранить
только проверенный File с совпавшим digest, при уходе нужна повторная проверка.

## Confirmation

- `tests/browser/upload-lifecycle.test.ts` воспроизводит сброс правок и проверяет
  продолжение с тем же ключом и новым итоговым набором.
- `tests/upload.integration.test.ts` подтверждает повтор с частью в реальном S3,
  гонку Complete в PostgreSQL, потерянный ответ, совместимость старого запроса
  и запреты для чужой или уже обработанной записи.
- `tests/upload-resume.test.ts` проверяет старый и новый манифест и отказ при
  повреждённых локальных данных.

Перед кодом нужны настоящий K2 и согласованный макет.
