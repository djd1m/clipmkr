# Clipmkr — постоянные требования владельца

Перед дальнейшими продуктовыми изменениями прочитать `CLAUDE.md`, применимые локальные правила
и **`docs/acceptance/core-cjm.md`**. Последний документ содержит актуальную обязательную приёмку,
уточнённую владельцем 2 ноября 2026; прежние противоречащие уточнения длительности заменены.

- Главные сценарии: полноценная загрузка и нарезка с просмотром/скачиванием; оплата тарифа;
  кабинет блогера со своей реферальной ссылкой и статистикой для него и владельца.
- Обычный пользователь: до 90 минут на запись. Блогер: 120 минут по умолчанию; владелец может
  назначить индивидуальный лимит конкретному блогеру. Лимит проверяется сервером.
- До разработки — feature-adr, требования, инвентаризация переиспользования, соответствующие
  уровню ADR/план и настоящие checkpoints/K1/K2. Использовать закреплённый проектный dz;
  закреплён в package.json: harness-cli 0.8.58, skills-feature-adr 1.5.25. Не имитировать успешные receipts.
- OpenSpec хранит дельты требований. После кода — реальные тесты, расширенный QE, независимое
  ревью по применимым правилам и code/spec anti-drift.
- Сначала переиспользовать действующие блоки Clipmkr и подходящий код проектов 1–8, затем
  поддерживаемые OSS-компоненты. Сохранять единый стек, модульность и иерархию.
- Документы вести по-русски. Делать небольшие проверенные коммиты и своевременно пушить
  одинаковые SHA в GitHub `djd1m/clipmkr`, GitLab `jechkov.dmitriy/clipmkr` и GitVerse
  `dzhechkov/clipmkr` (уточнение владельца 04.11.2026). Порядок и статус авторизации:
  `docs/operations/git-mirrors.md`. Частичный успех push не считать полной синхронизацией.
  Секреты, приватное медиа и подписанные URL в Git не помещать.
- Перед реализацией изменений интерфейса показывать владельцу конкретные макеты и
  согласовывать их. Поручение автономно завершить продукт не заменяет это согласование
  (прямое уточнение владельца 04.11.2026). Сначала пользовательский путь и действия,
  затем код; использовать заданные владельцем референсы и существующие OSS-блоки.
- Перед новым блоком работ сообщать подробный план: состав и роли команды, модели,
  режим независимой проверки, навыки, инструменты, проверки и ожидаемые артефакты
  (уточнение владельца 04.11.2026).
- Порядок поставки, установленный владельцем 04.11.2026: согласованный макет → изменение
  и развёртывание тестовой копии на VPS с рабочим каталогом `/home/clipmkr` → E2E UI/UX

  приложения на Cloud.ru не выкладывать. Основной production/DNS переключается только
  по отдельной явной команде. Не путать этот VPS и сервер существующего `n5.clipmkr.ru`:
  фактическое размещение проверяется перед операциями и указывается в плане.

## Принятые замечания владельца: обязательный цикл обучения

Уточнение владельца 04.11.2026: каждый раз, когда владелец указывает на недостаток
и исполнитель принимает замечание, выполнить проектным закреплённым dz:

1. `dz recall` по теме до исправления; прочитать фактический результат.
2. Зафиксировать наблюдение, доказательства и корректирующее действие. Гипотезу
   не выдавать за подтверждённый дефект или установленную причину.
3. `dz teach ... --project /home/clipmkr --no-mirror` для подтверждённого урока.
4. Проверить фактический ответ teach и выполнить повторный recall: не считать
   сохранение/извлечение успешным без результата команды.
5. Применить урок в плане, реализации и проверке; при переходах checkpoint повторять
   релевантный recall. Перед завершением записать code/spec anti-drift и ограничения.

Использовать `npm run dz -- ...` из рабочей копии с закреплённой версией. Общий
проектный store — `/home/clipmkr/.dz`, он не коммитится. Ошибка или отсутствие
совпадений recall не заменяются выдуманной записью. Обучение не заменяет согласование
макета, реальное исполнение этапа или независимое QE.

## Временное правило независимого ревью — решение владельца02.11.2026

Пока Claude Code недоступен, вместо cross-family применяется **cross-model**:
код проверяют модели, которые его не писали, в новых сессиях без контекста кодирования.
Проверяющий сначала получает только согласованные требования, ADR, архитектуру и план;
затем самостоятельно находит код и тесты. Прежние отчёты и выводы автора не подаются
как исходный контекст. Для каждого ревью фиксируются точный ID модели, отдельная сессия,
входные документы, найденные нарушения и ограничения доказательства. Независимая сессия
той же модели сама по себе не называется cross-model. Подробности: `docs/review-policy.md`.

Матрица новых запусков: `docs/model-matrix.md` (уточнение владельца 04.11.2026).
Автор — `gpt-6.1-sol high`; независимое ревью/QE — `gpt-6-astra xhigh` в новой сессии.
Исторические квитанции сохраняют фактические модели прошлых запусков.
