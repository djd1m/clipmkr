# dz CLI, feature-adr и OpenSpec: памятка участнику курса

На примере Clipmkr: как описать изменение, подготовить его реализацию и проверить результат.
Срез источников и команд — 05.11.2026. Примеры ниже иллюстрируют процесс;
они не обещают готовность автоссылки, регистрации или переноса приложения.

## Краткое сравнение

| Инструмент | Когда полезен | Что получаем | Ограничение |
|---|---|---|---|
| **dz CLI** | Нужно выбрать маршрут работы, выполнить gate, проверить допуск или извлечь урок | Результаты команд, проверки артефактов, checkpoints, recall/teach | Машинная проверка не создаёт согласование владельца и не заменяет E2E |
| **feature-adr** | Нужно превратить запрос в проверяемую реализацию | Требования, reuse, решения ADR, QCSD, архитектура, план, QE по уровню сложности | Документы и протоколы требуют исполнения; наличие плана не означает готовность |
| **OpenSpec** | Нужно видеть изменение поведения и согласованный срез по capabilities между задачами | Дельта требований со сценариями, связь с основными specs, архив изменений | Валидация проверяет описание, а не работу приложения; ledger надо поддерживать |

feature-adr уже хранит требования в `features/<slug>/01_requirements.md` и способен
работать **без OpenSpec**. Совместное использование в Clipmkr — выбранный процесс,
закреплённый в [AGENTS.md](../../AGENTS.md), а не техническая необходимость feature-adr.

## Когда полезен dz CLI

Это исполнитель команд процесса, а не только память. В связке с feature-adr он
поддерживает маршрутизацию по сложности, gates, checkpoints и допуск к следующему этапу.
Например, K2 проверяет комплектность плана перед реализацией; допуск относится
к конкретным входам и целям, а не разрешает любые последующие изменения.

`recall` помогает перед работой прочитать прошлые уроки. `teach` сохраняет подтверждённый
урок с наблюдением и корректирующим действием. Пустой recall означает отсутствие найденных
совпадений, а не успешное применение знания. Ответ teach и повторный recall надо прочитать.
Общий проектный store Clipmkr — `/home/clipmkr/.dz`; он не коммитится.

CLI полезен, когда ответ должен опираться на фактический результат команды:
какие входы проверены, какой gate прошёл, что пропущено и почему. Статус панели,
успешный exit code или запись checkpoint сами по себе не подтверждают качество продукта.

## Когда полезен feature-adr

feature-adr — протокол работы агента над изменением, не отдельная замена требованиям.
Он начинает с уровня сложности и требований, инвентаризирует переиспользование,
связывает решения и риски с планом, затем требует проверок и честного QE.
QCSD — ранний разбор рисков качества и тестируемости, до реализации.

В `features/<slug>/` остаются `01_requirements.md`, план `06_implementation_plan.md`,
применимые ADR, материалы QCSD, архитектура и `08_qe_report.md`.
Состав зависит от уровня: небольшой S не требует всего комплекта L/XL.
В Clipmkr reuse явно фиксируется; для этой памятки это `02_reuse_inventory.md`.

Такой комплект отвечает на вопросы «что требуется?», «почему выбрали это решение?»,
«что переиспользуем?», «какими шагами делаем?» и «чем проверили?».
Режим reference означает применение справочных протоколов доступными средствами;
он не доказывает запуск AQE runtime или независимых агентов.

## Что OpenSpec добавляет к feature-adr

**Пересечение реальное:** оба подхода могут хранить требования, сценарии, предложение
изменения и задачи. Неверно говорить, что feature-adr содержит только план, а требования
появляются лишь с OpenSpec. Второй комплект файлов сам по себе не улучшает проверку.

Дополнительная польза OpenSpec появляется при последовательных изменениях одной области:

- `openspec/specs/<capability>/spec.md` может хранить согласованное поведение capability
  — например, регистрации или кабинета блогера — поверх границ отдельных feature-папок.
- `openspec/changes/<change>/specs/<capability>/spec.md` описывает дельту:
  `ADDED`, `MODIFIED`, `REMOVED` и применимые сценарии вместо переписывания всего продукта.
- Синхронизация переносит принятую дельту в основные specs; архив сохраняет историю
  изменения, чтобы следующий исполнитель понимал происхождение актуального поведения.

feature-adr удобен для истории **выполнения конкретного изменения**; OpenSpec добавляет
организованный по capabilities срез поведения **между изменениями**. Этот срез можно
поддерживать и другим способом; OpenSpec даёт структуру и команды для такого процесса.

**Цена:** нужно выбирать границы capabilities, разрешать конфликты параллельных дельт,
поддерживать FR mapping, проверять ссылки и hash, делать sync/archive и ревью согласованности.
Если одну норму свободно редактировать в двух местах, появятся две несовместимые версии.
Для небольшой разовой задачи отдельный ledger может стоить больше, чем дать пользы;
в Clipmkr его ведут по принятому правилу, не объявляя универсальным обязательным условием.

**Факт проекта:** в этой рабочей копии на 05.11.2026 каталог `openspec/specs` отсутствует;
есть дельты в `openspec/changes`, включая [дельту памятки](../../openspec/changes/course-toolchain-guide/specs/course-guide/spec.md).
Поэтому OpenSpec здесь нельзя называть полным актуальным источником всех требований Clipmkr.
Возможность инструмента хранить основной срез не означает, что проект уже его заполнил.
Действующая [приёмка CJM](../acceptance/core-cjm.md) и требования конкретной задачи остаются обязательными входами.

### Как не вести две независимые копии требований

1. Одну владельческую дельту формулируем и согласуем один раз. В Clipmkr её нормативное
   изменение поведения фиксируем в OpenSpec; `01_requirements.md` содержит FR, ограничения,
   критерии проверки и точную привязку к этой дельте, а не свободный пересказ нормы.
2. Привязка содержит путь, точный заголовок requirement/scenario, ревизию или SHA-256
   файла и соответствие FR → spec. Hash фиксирует байты версии, а не её одобрение.
3. Уточнение владельца меняет дельту и связанные FR согласованно; пересчитываем hash,
   проверяем mapping, план и проверки. Расхождение блокирует переход, а не решается догадкой.
4. После acceptance сверяем реализованное поведение с дельтой и FR, согласуем sync/archive,
   проверяем diff основных specs и обновляем ссылки на архив. Историю feature-adr сохраняем.

Минимальная реальная привязка для этой памятки:

```text
change: course-toolchain-guide
spec: openspec/changes/course-toolchain-guide/specs/course-guide/spec.md
requirement: Разделение инструментов для участников курса
scenario: Выбор инструмента
sha256: a9cdc21f30095eabe55a0a3f71dc3253481b7a84d71e4474f7170360ac8e8af5
FR-1..FR-6: features/course-toolchain-guide/01_requirements.md
```

Здесь все шесть FR уточняют один общий requirement/scenario: FR-1 — сравнение,
FR-2 — связь и границы, FR-3 — примеры, FR-4 — команды, FR-5 — порядок и проверка,
FR-6 — overlap, цена и защита от drift. Это соответствие «многие к одному»;
в самой дельте нет шести отдельных требований. Детализацию читаем по точной ссылке
на [FR памятки](../../features/course-toolchain-guide/01_requirements.md), не приписываем её тексту spec.

## Три примера Clipmkr

### 1. Автоссылка блогера

Контекст [приёмки](../acceptance/core-cjm.md): у блогера своя ссылка и статистика,
владелец видит привлечённых пользователей и подтверждённые оплаты.
Если владелец просит выдавать ссылку автоматически, сначала уточняем момент создания,
поведение для уже назначенного блогера и повторного входа. Это предлагаемая дельта,
а не утверждение, что автоссылка уже реализована или согласована во всех деталях.

OpenSpec фиксирует изменение поведения кабинета и сценарий повторного входа без дубля.
feature-adr связывает FR с дельтой, исследует существующий PartnerService и attribution,
описывает решение и проверки вместо создания второго реферального сервиса.
dz помогает извлечь уроки и пройти применимые gates.
Доказательство результата — реальный путь «блогер → ссылка → клиент → статистика
блогера и владельца», включая запрет доступа к чужим данным. Макет ссылки этого не доказывает.

### 2. Повторная регистрация

Если человек снова проходит регистрацию с тем же идентификатором, сначала выясняем
ожидаемый ответ: вход, восстановление доступа или понятный отказ; нельзя выбрать его
за владельца и выдать за принятое требование. Отдельно уточняем судьбу прежней атрибуции.

OpenSpec полезен для согласованного поведения capability регистрации при повторе.
feature-adr добавляет FR на обычный повтор и конкурентные запросы, reuse действующей
авторизации, решение о целостности и план интеграционных проверок.
dz фиксирует фактические результаты gates и подтверждённый урок, если он появился.
Проверяем отсутствие лишнего аккаунта и двойного начисления статистики согласно принятой
дельте; чтение `UNIQUE` в схеме — основание для гипотезы, не результат такого теста.

### 3. Перенос уже работающего приложения на Cloud.ru

Это изменение окружения существующего Clipmkr, с сохранением данных и поведения.
[Требования переноса](../../features/cloudru-release-parity/01_requirements.md) дают предмет
для анализа; их наличие не означает, что перенос принят или разрешено переключение production.

OpenSpec описывает дельту требований к поставке и сохраняемым сценариям.
feature-adr нужен для inventory окружений, reuse работающего стека, рисков данных,
ADR по применимости, плана проверки версии, восстановления и полного CJM.
dz проверяет процессные условия допуска; совместимость Cloud и сохранность данных
доказываются отдельными фактическими проверками, а не validation Markdown.

По [правилам владельца](../../AGENTS.md): согласованный макет для изменения UI →
изменение и тестовая копия на VPS с рабочим каталогом `/home/clipmkr` → E2E UI/UX →
ссылка и инструкция владельцу → его ручная приёмка → тот же проверенный артефакт
на Cloud.ru → контроль. Фактическое размещение VPS проверяется отдельно от сервера
существующего сайта. Production/DNS переключается только по отдельной явной команде.
На уроке команды доставки, операции с БД и инфраструктурой не выполняем.

## Короткая последовательность работы

1. Прочитать правила, актуальную приёмку и recall; назвать роли, модели, навыки и проверки.
2. Описать владельческую дельту и FR mapping; исследовать reuse, определить сложность.
3. Подготовить применимые ADR/QCSD/архитектуру и план; получить необходимые согласования
   и реальные K1/K2/checkpoints. UI реализуется после согласования конкретного макета.
4. Выполнить допущенный план, реальные тесты, расширенный QE и независимое ревью.
5. Сопоставить FR → spec → реализацию → доказательства; записать ограничения.
6. Пройти установленную acceptance; согласованно синхронизировать и архивировать дельту.

OpenSpec apply — инструкции выполнения задач изменения, не обход feature-adr,
согласования макета или gates. В CLI 1.15.0 нет отдельной верхнеуровневой команды `apply`;
workflow и CLI нельзя смешивать. Sync/archive меняют ledger и не доказывают acceptance.

### Команды: синтаксис проверен на закреплённых версиях

В подготовленной копии проекта с установленными закреплёнными зависимостями:

```bash
npm run dz -- --version                     # 0.8.58
npm run dz -- recall --help
npm run dz -- teach --help
npm run openspec -- --version               # 1.15.0
npm run openspec -- list --changes --json
npm run openspec -- list --specs --json
npm run openspec -- show course-toolchain-guide --type change --json
npm run openspec -- status --change course-toolchain-guide --json
npm run openspec -- validate course-toolchain-guide --type change --strict --no-interactive
```

feature-adr закреплён пакетом `@dzhechkov/skills-feature-adr` версии **1.5.25**:
это навык, не подкоманда `dz feature-adr`. `show` показывает описание,
`status` — комплектность артефактов схемы, `list` — инвентарь, `validate` — структуру
и правила спецификации. Ни один из этих ответов не означает «продукт работает».
На этом guide change `validate` прошёл, но `show` вернул `Change must have a Why section`;
`status` показал `isComplete: false` и отсутствие design/tasks, `list --specs` — пустой список.
Это наблюдения о документах и схеме, не результаты проверки приложения.

Следующий блок — образец цикла обучения, **не команда для исполнения на уроке**.
Teach записывает данные; текст в угловых скобках заменяется подтверждённым наблюдением.

```bash
npm run dz -- recall "повторная регистрация" --project /home/clipmkr --limit 3
npm run dz -- teach "<наблюдение; доказательство; корректирующее действие>" --type lesson-learned --project /home/clipmkr --no-mirror
npm run dz -- recall "повторная регистрация" --project /home/clipmkr --limit 3
```

Проверить фактические ответы и извлечение урока; `--no-mirror` не является доказательством
сохранения. Гипотезу о причине не записывать как установленный дефект.
Не копировать в документы реальные email, секреты, приватные адреса и подписанные URL.

## Что проверки не доказывают; типовые ошибки

- Зелёный `validate` не подтверждает серверные лимиты, оплату, просмотр или скачивание.
- Checkpoint подтверждает зафиксированный результат этапа в пределах его проверки;
  предупреждения, skips и N/A нужно читать, а не превращать в «всё проверено».
- Файл `approval` и галочки задач не создают человеческого согласования. Нужна реальная
  привязка решения владельца к показанному макету/плану и его версии.
- Архивирование не означает приёмку; возможность archive не даёт права преждевременно
  объявить дельту действующим поведением. После sync нужно проверять содержимое ledger.
- Ссылки без версии и два самостоятельно редактируемых текста требований создают drift.
- Авторская самопроверка не заменяет независимое ревью. По [матрице моделей](../model-matrix.md)
  автор — `gpt-6.1-sol high`, проверяющий — `gpt-6-astra xhigh` в новой сессии без истории
  кодирования; один model ID с разным effort не считается cross-model.
