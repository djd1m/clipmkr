# Открытый бэклог и предложения пользователей: первичная оценка

Дата: 11.11.2026. Основание — запрос владельца; задача
[FEEDBACK-001](../../BACKLOG.md#feedback-001--открытый-бэклог-и-прямой-запрос-новой-функции).
Прочитан репозиторий на `58e72ab7f2b24e3574d56ddb561cf9b074ed6b73` и открытые первичные
источники. Это контекст для будущей приоритизации, без реализации, изменения настроек,
чтения пользовательской переписки или создания обращений.

## Что можно переиспользовать

| Вариант | Основание | Ограничение и решение для следующего этапа |
|---|---|---|
| Существующий Libredesk | [Исследование доступа](../support-access/README.md), `apps/web/src/app/support/SupportPanel.tsx`, `apps/web/src/lib/support-client.ts`; [ops-рецепт](../../libredesk-operations.md) закрепляет v2.9.0. Официальный [README v2.9.0](https://raw.githubusercontent.com/abhinavxd/libredesk/v2.9.0/README.md) описывает чат, email, теги, пользовательские статусы и атрибуты. | Подходит как кандидат на закрытый приём и разбор предложений. Работающий публичный roadmap на установленном экземпляре не подтверждён. Форма feature request, реальная настройка почты и доставка здесь не проверены; наличие канала в upstream не доказывает его подключение. |
| Вручную публикуемый список | Уже есть [репозиторный бэклог](../../BACKLOG.md); публичные карточки можно готовить вручную после очистки текста. | Предлагаемый минимальный вариант: Libredesk → модерация владельца → отдельная публичная карточка. Определить понятный доступ из кабинета и обновление статуса; не открывать операторский inbox пользователям. |
| GitHub Issues | Можно рассмотреть как внутренний рабочий реестр решений и публичных очищенных задач. | Обязательный GitHub-аккаунт для предложения повышает порог входа для клиентов продукта; такой путь не выбран. Не переносить частные обращения в публичные issues автоматически. |

[Документация записей](https://docs.fider.io/api/posts/) описывает статусы, дубли и модерацию; ожидающие модерации записи доступны автору и сотрудникам. | Рассматривать, если существующий вход и ручной список не закрывают согласованный сценарий. Перед выбором проверить текущую поддержку, закрепить ревизию, оценить лицензию, вход Clipmkr, спам и эксплуатацию. Отдельный сервис сейчас не требуется и не выбран; встроенные голоса/подписки не становятся требованиями Clipmkr. |

Оценка: сначала проверить вариант с существующим Libredesk и ручным публичным списком.
Это рекомендация для будущего планирования, а не утверждённая архитектура. Публичную
карточку создавать из согласованного краткого описания; исходное закрытое обращение
с его контактами, перепиской и вложениями не превращать в публичный объект.

## Что остаётся определить

- Обычный пользователь и блогер: действие из кабинета, подтверждение приёма и способ
  узнать статус собственного запроса. Владелец: разбор, публикация, дубли и статусы.
  Использовать существующие роли; не вводить новую роль «автор предложения» заранее.
- В [SUPPORT-001](../../BACKLOG.md#support-001--история-обращений-и-отложенные-ответы-у-пользователя)
  остаются история и безопасная identity. Наблюдавшийся `identifiedEnabled=false`
  не позволяет обещать личный список предложений только на основании входа в Clipmkr.
- Возможности установленной версии проверить на синтетических данных: текущий чат,
  маркировка «предложение», доступ владельца, история/отложенный ответ; затем отдельно
  оценить штатную форму и почтовый вход, если они нужны. В этом исследовании настройки
  живого Libredesk не читались и не менялись.
- Согласовать связь и хранение частного запроса и публичной карточки, сроки хранения,
  удаление/обезличивание, авторизацию, антиспам и модерацию. Публичный просмотр не даёт
  права читать частные обращения. Публикация email автора и автоматические уведомления
  по умолчанию не требуются; голоса и ранжирование — отдельная опция.

Дальнейшая реализация требует обычного feature-adr/dz/OpenSpec процесса и согласования
конкретного UI. Предварительная оценка M зависит от reuse; фактический tier определяет
будущий router. Эта заметка не создаёт receipts, разрешений или результатов QE.
