ветка `research/referral-registration-ux-20261111`.

**Статус: исследование, конкретный макет для согласования владельцем.**
Приложение не изменялось и не развёртывалось. Согласование интерфейса,

Рекомендуется один основной вариант: после перехода по действительной ссылке
форма регистрации сразу содержит **раскрытое редактируемое поле «Код партнёра»**
с эффективным кодом из приглашения. Никакого копирования частей URL.
Рядом короткое уведомление «Код из приглашения заполнен. Вводить его не нужно» и
уточнение: «Код заполнен из приглашения. Проверим привязку после создания
нового аккаунта». Это сообщение о принятом приглашении, а не о состоявшейся
регистрации или успешном начислении.

В макете показан публичный код из обращения `hlqwboSVynWB`; личные данные
пользователя и автора не нужны. Поле можно изменить; ограничение readonly
не предлагается. Без приглашения блок остаётся необязательным и свёрнутым.
Сохранены палитра кабинета, бренд, системный стек шрифтов из `globals.css`,
основные регистрационные поля и переход к существующему кабинету. Изображения,
новые библиотеки и внешний сетевой контент не нужны. Левый блок служит
контекстом экрана; отдельное изменение лендингового маркетинга не запрашивается.

## Почему текущий путь вызывает проблему

Пользователь открыл `https://clipmkr.ru/r/hlqwboSVynWB`, затем сам извлёк код
из URL, нашёл свёрнутый optional-блок и ввёл его. Ссылка передаёт источник
на сервер, но форма не показывает, что произошло. Пользователь вынужден
разбираться в устройстве ссылки и повторять уже выполненное действие.
Отсутствует видимая обратная связь, которая отличала бы сохранённое приглашение
от обычного входа на сайт.

Причина пустого поля подтверждается чтением кода на указанной базе:

| Участок | Наблюдаемое поведение |
|---|---|
| `apps/web/src/app/r/[code]/route.ts`, `server/partner-landing.ts` | Проверка ссылки, запись перехода, подписанная HttpOnly-cookie и фиксированный 302 на `/` |
| `apps/web/src/lib/partner-referral.ts` | Проверка подписи и TTL 14 дней; first-touch, приоритет guest-link; cookie HttpOnly/Secure/SameSite=Lax |
| `apps/web/src/app/page.tsx` | В Landing передаются только `creditMode` и `theme` |
| `apps/web/src/app/Landing.tsx` | В единственную AuthForm не передаётся приглашение |
| `apps/web/src/app/AuthForm.tsx:114` | `<details>` без `open`, поле без `value`/`defaultValue` |
| `apps/web/src/app/AuthForm.tsx:95` | После auth вызывается `code.apply`: ручной код либо `{}` для cookie fallback; `registration=existing` пропускает apply |
| `apps/web/src/server/partner.ts` | Сервер определяет source, проверяет активность и ограничения замены, сохраняет атрибуцию |

**Пустой UI не доказывает потерю атрибуции.** Предоставленная актуальная
read-only проверка обращения подтвердила регистрацию и принадлежность
нужной ссылке, а каноническая проекция кабинета — одну регистрацию.
Это отдельное доказательство по серверным данным. В этой работе нет новой
регистрации, браузерного входа, проверки пикселей живого кабинета или полного
живого E2E. Личные адреса, UUID, cookies и подключения сюда не переносились.

## Необходимый пользовательский путь

1. Человек открывает реферальную ссылку. Сервер сохраняет допустимое приглашение
   по действующей политике и возвращает страницу регистрации.
2. Видит раскрытый блок с уже заполненным **эффективным** кодом и уведомление,
   что вводить его не требуется. Заполняет только почту и пароль.
3. Создаёт аккаунт. Сервер регистрации и применения источника подтверждает
   реальный результат; двойной клик/повтор не создаёт лишние события.
4. Входит в кабинет. Только при реально подтверждённой привязке видит
   «Аккаунт создан. Приглашение применено» с публичным кодом.
5. Переходит к основной задаче — загрузке записи. Это регистрация, а не первый
   выпуск, оплата или обещание бонусов.

В mockup submit для неизменённого образца переключает **локальную имитацию**
результата; почта/пароль никуда не отправляются. Изменённый код, обычный вход
и прочие сценарии не изображают успешную привязку.

## Состояния и границы политики

| Состояние | Предложение в макете / обязательное ограничение |
|---|---|
| Действительное приглашение | Раскрытое поле с кодом, без ручного ввода |
| Без приглашения | Свёрнутый optional-блок, пустое поле |
| Ручное изменение | Поле редактируемое; прежнее зелёное уведомление убирается, новый код ещё не подтверждён |
| Повторная регистрация existing | Макет показывает вариант 409/неверного пароля: вход в существующий аккаунт; не обещать новую регистрацию/перепривязку. Сохранять существующий skip apply для outcome existing |
| Обычный вход | Сохранять существующий вызов apply и правила source; не путать с outcome existing. Макет вкладки не является новой политикой входа |
| Недействительный / истёкший код | Не показывать зелёное подтверждение; можно исправить код либо зарегистрироваться без него. Точная доступность этого состояния из SSR требует проектирования |
| A → затем ссылка B | При действительной cookie A обычная B её не заменяет. Показать A. В макете A — синтетический `DEMOFIRST1`; выбор другого кода только ручной и по действующему explicit policy |
| Успешная привязка | Только подтверждённый результат `pending`/`activated`, без self/rejected/конфликта; HTTP 200 с null сам по себе недостаточен |

При correct-password повторной регистрации существующий аккаунт автоматически
получает `registration=existing` и входит без нового apply; макет предупреждения
демонстрирует отдельный вариант 409/неверного пароля.

Текущий `/r` для неизвестной/заблокированной ссылки возвращает 404, а не форму
с сообщением. Состояние «Код недействителен» — предлагаемый вариант обратной
связи для будущей feature, не описание опубликованного поведения. Истёкшая
cookie может уже отсутствовать в запросе и неотличима от отсутствия приглашения.
Без дополнительного проверенного контекста нельзя утверждать, что срок истёк.

После `/r/B` → `/` сервер имеет эффективную cookie A, но не факт второго B.
Поэтому макет показывает сохранённую A без заявления «вы открыли B».
Менять first-touch на last-touch этим макетом не предлагается. Если владелец
ожидает, что любая новая ссылка автоматически заменит предыдущую, это отдельное
решение о политике и статистике, а не побочный эффект autofill.

## Контракты будущей реализации

Переиспользовать `readReferral`, проверку активности кода и владельца,
единственную `AuthForm` и текущий `code.apply`, не создавать второй тракт
регистрации. SSR проверяет подпись/TTL и актуальное состояние кода/владельца;
передаёт в Landing/AuthForm только безопасный публичный код и минимальный
display-state. К персонализированному SSR применим запрет общего кэширования.
Нельзя читать HttpOnly-cookie через browser JS, делать её доступной клиенту,
передавать подпись, токен или session secret. Не вызывать `recordView` при
display-проверке: рендер/refresh не должны увеличивать переходы.

Критическая деталь: **неизменённый autofill отправляет `code.apply({})`,
ручной выбор — `{code}`**, сервер остаётся владельцем source. Текущая форма
считает любое непустое поле явным кодом. Простая установка `defaultValue`
без различения изменённости опасна: после истечения/утраты cookie между SSR
и submit этот код стал бы `explicit`, меняя приоритеты ADR-007. Отсутствующий
при submit источник не следует заменять молчаливым explicit; нужно честно
обработать результат. Client-supplied source сервер не принимает.

Сохранить приоритет guest-link, first-touch обычных ссылок, ограничения
explicit replacement, self-referral, blocked/rejected/partner_deleted,
повторную регистрацию existing и текущую обработку ошибки apply после auth.
Очищение видимого поля не равно отказу от cookie: сейчас пустой payload
снова использует cookie. Явное продолжение без применения кода уже имеет
отдельный `discard_referral`; не приписывать очистке поля новую семантику.

`tests/partner.test.ts` (source, TTL, guest, replacement),
`tests/partner-route.test.ts` (transport/identity),
`tests/browser/public-entry-cabinet.test.ts` и
`tests/browser/repeat-registration-next.test.ts` (auth/apply/repeat).
Эти продуктовые тесты в исследовании не запускались. Отдельного native UI
оракула «настоящий `/r` → непустое раскрытое поле» в прочитанных anchors нет.

После согласования, в изолированном контуре будущей feature нужен цельный
настоящий браузерный путь `/r` → cookie → SSR/DOM → новый auth → apply →
серверная принадлежность → кабинет/статистика. Дополнительно: A→B, guest
priority, ручной override, expiry между SSR и submit, inactive/blocked/self,
повторная existing-регистрация против обычного login, ошибка/повтор apply,
refresh/дубли без лишних событий и утечек. Точный набор тестов и source guards
определить в feature-adr до кода; не создавать mutation receipts заранее.
