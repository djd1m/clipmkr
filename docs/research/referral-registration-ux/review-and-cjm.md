# Регистрация по приглашению: CJM и проверка предложения

11 ноября 2026 года. Исследование и ревью макета; приложение не изменено. Это не независимый code-QE, выполненный feature-adr gate или разрешение на реализацию.

**Вывод:** приглашение сохраняется сервером, но интерфейс его не показывает. Для пришедшего по действительной ссылке нужно сразу раскрыть «Код партнёра», заполнить эффективным кодом и объяснить, что переносить его вручную не нужно. Для посетителя без приглашения оставить необязательное свёрнутое поле. Обычный путь требует только email, пароля и кнопки «Создать аккаунт» — **ноль дополнительных действий с кодом**.

Пустой блок «Есть код партнёра? Необязательно» не сообщает, что приглашение уже сохранено. ## Карта пути трёх ролей

| Этап | Приглашённый пользователь | Блогер | Владелец |
|---|---|---|---|
| Приглашение | Открывает `/r/…` и сразу видит регистрацию с заполненным полем | Копирует свою ссылку из кабинета и распространяет | Назначает блогера и проверяет принадлежность ссылки |
| Новый аккаунт | Вводит email и пароль; создаёт аккаунт без действий с кодом. После серверного применения открывается кабинет | Видит привлечённого пользователя в «Регистрациях» | Видит того же привлечённого пользователя в отчёте соответствующего автора |
| Уже есть аккаунт | Повторная регистрация с верным паролем сообщает «Аккаунт уже существует. Вы вошли», сохраняет источник. Обычный «Войти» — отдельная ветка с существующей политикой применения кода | Повторная регистрация не становится новым привлечением | Не получает повторного бонуса/аккаунта/новой регистрации из этого повтора |
| Пользование | Загружает запись, получает, смотрит и скачивает клипы | Видит начало использования; `pending` переходит в `activated` при завершении обработки с готовым клипом | Сверяет статистику использования |
| Оплата | Выбирает пакет и оплачивает в разрешённом контуре | Видит подтверждённые покупки и выручку | Видит месячный расчёт по назначенной ставке; источник платежа фиксируется при создании намерения оплаты |

Это карта требуемого полного CJM из core-cjm, а не утверждение о его новом прохождении. Счётчик «Регистрации» сейчас считает действующие атрибуции, а не исключительно события создания аккаунта. Этот UI-фикс не меняет его смысл, финансовые правила или историю платежей.

## Минимальная рекомендация и границы

Переиспользовать единственную цепочку `page → Landing → AuthForm`, [readReferral](../../../apps/web/src/lib/partner-referral.ts) и существующее применение кода. При SSR проверить подпись и TTL cookie, затем актуальную доступность кода и его владельца; передать форме только публичный код и необходимое состояние отображения. Сохранить HttpOnly, не отдавать подпись, raw Cookie header, session secret или идентификаторы аккаунтов. URL и клиентский JS не являются доказательством приглашения. Рендер должен учитывать конкретный запрос, без общего кэша приглашения между посетителями.

До создания аккаунта достаточно текста: **«Код из приглашения заполнен. Вводить его не нужно.»** Ниже: «Применим после создания нового аккаунта». Итоговую привязку подтверждать только результатом сервера: HTTP 200 сам по себе недостаточен — `apply` может вернуть `null` или `rejected`. Успех регистрации и успех применения приглашения — разные состояния. При ошибке применения сохранять действующую сессию, предложить повтор и существующее «Продолжить без применения кода»; не требовать снова регистрироваться.

**Сохранить происхождение кода:** неизменённое автоматическое заполнение должно отправлять `{}`, а сознательный ввод другого кода — `{code}`. Если просто сериализовать заполненный input, истёкшая между SSR и submit cookie превратит его в `explicit`, изменив приоритет источника. Сейчас сервер сохраняет `cookie/guest_link` для совпадающего кода только пока cookie действительна. Очистка поля сама по себе также не означает отказ от приглашения: нынешний `{}` использует cookie. Отдельное действие отказа должно иметь явную семантику и согласование, если его добавят до регистрации.

| Контекст | Фактическое правило текущего исходника | Следствие для предложения |
|---|---|---|
| Чистый посетитель с действительной ссылкой | `/r` сохраняет подписанную cookie на 14 дней и делает 302 на `/`; переход сам не привязывает аккаунт | Поле раскрыто и заполнено; без кнопки «Применить» до регистрации |
| Сначала A, затем обычная ссылка B | Действующая cookie A сохраняется и не продлевается; `guest_link` сильнее обычной ссылки | Показывать эффективный A. Не подставлять B автоматически. После redirect факт второго B не сохраняется: отдельное пояснение о B потребует нового проверенного контекста; это не часть минимального diff |
| Недействительная/заблокированная ссылка | Сам `/r` отвечает 404, без новой cookie; отдельного срока жизни самой обычной ссылки нет | Не показывать «Приглашение учтено». Дружелюбная error-page — отдельный вариант, а не уже существующее состояние формы |
| Просрочена/подделана cookie, код заблокирован после открытия | Парсер отвергает cookie; apply повторно проверяет код и владельца | Не выдавать stale prefill за пригодное приглашение; не повышать его автоматически до explicit. «Истекло приглашение» не смешивать с блокировкой кода |
| Собственная ссылка | У опознанного владельца нет нового визита/cookie. Применение без прежней атрибуции даёт `rejected/self_referral`; с прежней — 409 без замены | Не показывать успешную привязку по одному HTTP 200. Анонимно владельца распознать нельзя |
| Повторная регистрация, верный пароль | `registration=existing` пропускает apply и signup, сохраняет аккаунт, бонус и источник | Сообщение о входе; не обещать применения показанного нового приглашения |
| Повторная регистрация, неверный пароль | 409, переход к входу/восстановлению с сохранённым email, без новой сессии | Сохранить понятную ошибку и доступ к восстановлению |
| Обычный вход | Вызывает apply: может связать аккаунт без источника либо заменить слабый согласно ADR-007; равный/сильный источник даёт 409 | Нельзя общей фразой утверждать, что любой вход всегда сохраняет источник. Изменение этой политики требует отдельного решения |

## Будущая приёмка до реализации

Сначала согласованный макет, feature-adr/dz, требования с точным OpenSpec path/hash, reuse/ADR/план и реальные K1/K2. До правки зафиксировать ревизию и затронутые контракты. Исторический frozen Specification SHA `3ac09f3dcccc354f292ac0ed0452de0e7f14f8bafd68b6f8e54354e303407532` и fixture старой формы из `c97515db90e704b44da0644c9ac92a8cd22e6343`, SHA-256 `6b97da09ffc9c34dda5bcd814a188f964979fc75499e3518fbe93a3b6e9d2a77`, не переписывать ради нового отображения.

Переиспользовать [partner-landing.test.ts](../../../tests/partner-landing.test.ts), [partner.test.ts](../../../tests/partner.test.ts), [partner.integration.test.ts](../../../tests/partner.integration.test.ts), [public-entry-cabinet.test.ts](../../../tests/browser/public-entry-cabinet.test.ts), [repeat-registration-next.test.ts](../../../tests/browser/repeat-registration-next.test.ts). Они уже описывают transport, источники и repeat-registration; единого oracle реального `/r → SSR → видимое поле → auth → attribution` сейчас нет. В браузерных тестах есть предположение о закрытом `summary`; обновлять лишь применимые fixtures. В [test-partner-mutations.mjs](../../../scripts/test-partner-mutations.mjs) точные уникальные anchors защищают invalid-no-fallback, explicit-immutable, guest-over-cookie и self-referral; проверять их применимость до изменения service. Наличие этих файлов не является PASS.

| Given / When | Then: обязательный наблюдаемый результат |
|---|---|
| Чистый HTTPS-контекст → реальный `/r/A` → регистрация нового синтетического аккаунта | Уже при SSR поле открыто и равно A; без ручного ввода/добавочного клика; после auth точная атрибуция A, source cookie, одна регистрация в проекции автора и владельца |
| Прямой заход без приглашения | Необязательный блок закрыт, нет ложного подтверждения; обычная регистрация доступна |
| Cookie A → `/r/B`; отдельно guest A → `/r/B` | Поле и итог соответствуют эффективному A, приоритет и TTL не меняются |
| Приглашение показано, затем cookie истекла/удалена до submit | Неизменённый prefill не становится explicit; нет ложного сообщения о привязке |
| Ручное изменение на другой действительный/недействительный код | Действует текущий explicit policy; недействительный код не откатывается к cookie |
| Existing register с верным/неверным паролем; отдельно ordinary login | Сохранены соответствующие ветки таблицы выше; нет лишнего аккаунта, бонуса или signup |
| Свой/заблокированный/подделанный код, ошибка apply после auth | Нет ложного успеха; сессия не теряется, retry/discard не повторяют auth |
| 390/1440 px, обе темы, Tab/Enter и screenreader | Читаются код и статус; поля/основное действие доступны, нет горизонтального overflow; раскрытие не скрывает ошибку |

Будущие отрицательные проверки должны ловить удаление SSR-передачи кода, закрытое/пустое поле после действительной ссылки, auto-prefill→explicit при истечении cookie, снятие existing-skip и ложный успех на `null/rejected`. Проверки выполняются на стабильном снимке и синтетических данных изолированного контура. После необходимого общего прогона повторяются только затронутые проверки, если новых рисков нет. Настоящие результаты, независимое QE и anti-drift записываются после исполнения, не в этом исследовании.
