Для Clipmkr сначала сравнить **действующий согласованный UI** с критериями core-CJM, а не строить новый вариант ради банковской аналогии. Зафиксировать SHA/UI revision, роль, данные, права, браузер/ОС, ширину, тему и состояние. Для сравнения будущего кандидата нужны отдельно согласованный макет и одинаковая постановка задачи. Банковский экран не является контрольной группой Clipmkr.

## Базовая линия → гипотеза → задача → критерий

Ниже **план**, а не выполненные тесты. Критерии — предлагаемые правила проверки гипотез; новые продуктовые thresholds должны быть согласованы отдельно. Участнику не называют кнопку, раздел или «advanced»: это подсказало бы ответ. Подход — [GOV.UK moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing).

|---|---|---|

## План раунда и границы измерения

Сначала короткий модерируемый качественный раунд: например 5 обычных пользователей, 3 блогера и 1 реальный владелец/уполномоченный оператор. Это **предложение**, набор не запускался; доступные участники и потребности определяются отдельно. По [методике планирования GOV.UK](https://www.gov.uk/service-manual/user-research/plan-user-research-for-your-service) вопросы/группы важнее числа ради отчёта. Малое N, особенно единичный владелец, обнаруживает конкретные затруднения, а не даёт достоверный процент популярности.

Для каждой роли сначала релевантные ей задачи; не просить обычного пользователя оценивать чужой owner workflow. Собирать исход, помощь модератора, ошибки/возвраты, время с явным start/stop и дословное объяснение состояния. Не объявлять улучшение по одному быстрому участнику; на повторном сравнении менять порядок вариантов и учитывать обучение.

Критическая ошибка с деньгами/правами/потерей файла — основание исправить проблему и повторить затронутый сценарий, а не усреднить её в высоком балле удобства. UMUX-Lite/SUS возможны только с реальными ответами и прозрачной формулой; этот пакет их не содержит.

## Платформы и доступность Clipmkr

Планировать реальные Chrome/Windows с мышью и клавиатурой, Android Chrome, iOS Safari; эмуляция viewport не доказывает real-device поведение. Минимально покрыть320/390 CSS px и desktop 1440, большую высоту/короткий viewport, обе существующие темы/компоновки, увеличенный текст и reload. Конкретные границы сверять с действующим CSS и acceptance oracle, не применять desktop ceiling безусловно к mobile.

Для web target size применять [WCAG 2.2 SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum):24×24 CSS px либо его исключения/spacing. Native44pt/48dp не равны CSSpx и не являются доказательством нашего pass. Проверять реальные labels, порядок focus, status announcement, контраст, reflow; привлекать пользователей соответствующих assistive tech. Банковское заявление о доступности и тёмная тема этого не заменяют.

## Отдельные уровни доказательства

1. Этот desk research подтверждает существование публичного паттерна с ограничениями источника.
2. Экспертный разбор кадров выявляет возможную проблему обнаружения; пользовательского поведения в нём нет.
3. Moderated task test покажет конкретные затруднения/успех на Clipmkr; пока NOT RUN.
4. Функциональные/интеграционные/E2E проверки докажут серверные права, сохранность и payment/recovery контракт; исследование их не выполняло.
5. Независимое review проверит источники/выводы; ручная приёмка владельца и выпуск продукта остаются отдельными gates.

Ни один уровень не объявляется выполненным по наличию документа следующего уровня. Согласование новых решений требуется только при появлении конкретной предлагаемой UI-дельты; подготовленное исследование не блокирует согласованный макет.
