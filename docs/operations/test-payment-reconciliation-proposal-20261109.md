# Предложение: сверка одного старого TEST-платежа

09.11.2026. Статус: **отложенное предложение; только read-only выводы, начисление не выполнялось**.

Последнее решение владельца: сначала перенести все требуемые БД на новый VPS, включая main/support и отдельную legacy history; тестировать оплату после готовности данных. Историческое расхождение не блокирует копирование. Финансовое согласование сейчас не запрашивается. DNS остаётся отдельным последующим решением.

Повторная сверка исторических тестовых оплат выявила старый успешный платёж990₽, которому в основной базе соответствует неприменённое намерение пакета «Старт»:18000 секунд, то есть300 минут. Это существующий аккаунт; разрешение на новую QA покупку не разрешает менять его баланс. Причина исходного расхождения не установлена.

В закрытых материалах05–06.11 тот же платёж уже отмечен в другом хранилище как `unknown_intent`. Свежая read-only сверка09.11 подтвердила: основная база имеет intent без payment/event; legacy имеет unbound payment/event с NULL account/intent и записью на разборе; Cloud не имеет этой пары. Grants по payment_ref конкретной legacy payment row отсутствуют; отсутствие всех возможных начислений этим не доказывается. Перед будущей записью после переноса обязательна новая сверка всех хранилищ данного магазина. Штатная идемпотентность действует внутри одной БД и не переносит такую запись между базами. Если она сохранилась, source-only начисление с сохранением прежней записи на разборе требует отдельного явного решения; чужое начисление, возврат или спорное владение останавливают операцию.

## Что предлагается

1. После готовности перенесённых данных заново привязать план к единственной authoritative main БД нового VPS и отдельно сохранённой legacy history. Сохранить согласованные creator fences и callback режим, повторно подтвердить точные host/image/DB, intent/account/provider linkage, ledger и cross-store состояние; сохранить закрытый снимок до операции. Первоначальное предложение source-вызова до переноса отложено.
2. Настоящим authenticated GET через существующий `createYooKassaProvider(...testMode:true).getPayment(exactId)` проверить TEST магазин, recipient, ID, `succeeded/paid`,990.00RUB, metadata.order_id и непустое время captured_at. Проверить сведения о возвратах; неизвестность не считать отсутствием возврата.
3. После отдельного разрешения владельца и допуска точного инструмента вызвать существующий `@clipmaker/db.applyVerifiedPayment` для ровно одного намерения. Сохранить canonical event key, привязки, комиссию из ответа провайдера и исходное время платежа. Закрытый receipt явно называет действие операторской сверкой по API; hash GET ответа не выдаётся за hash доставленного webhook. HTTP callback и IP провайдера не подделываются.
4. Проверить одну новую source запись payment/event/grant, правильный intent и неизменность остальных финансовых строк. Один согласованный повтор того же canonical вызова должен дать duplicate без второго начисления. При неожиданном исходе — остановка и чтение фактического ledger.

## Какой период получит аккаунт

Существующая логика выдаёт300 минут и30-дневный базовый период от большего из исходного времени платежа, конца уже назначенных базовых пакетов и применимого оплаченного legacy срока. Дата сегодняшней сверки не начинает период заново. Фактические начало/конец рассчитываются по свежим данным до применения; они могут относиться к прошлому или будущему. Ручное продление и изменение billing policy не предлагаются.

## Переиспользование и ограничения

Canonical provider GET и транзакционный DB consumer существуют. Read-only локальная проверка подтвердила DB export, но не идентичность compiled кода в live source. Готовой штатной reconciliation CLI не найдено; provider доступен как TypeScript source и внутренний Next bundle. Перед исполнением нужны проверенный импорт/компиляция неизменённого canonical provider, точные private invocation bytes/hashes и применимые feature-adr/dz gates с независимым QE. Внутренние идентификаторы модулей Next не являются подходящим API. Это план, а не готовый допущенный runner.

Прочитаны `features/recover-known-checkout-response/01_requirements.md`, `02_reuse_inventory.md`, `06_implementation_plan.md`, `07_code_changes.md`, `08_qe_report.md`. Старый инструмент восстановления потерянного checkout response имеет QE2 NO-GO и незакрытые условия; он не принимается повторно этим предложением. Его operator-relay требует уже применённый платёж и синтетический IP, поэтому для этой сверки непригоден. Сохранение прежних файлов не означает одобрения или закрытия gates.

Транзакционное исключение откатывает canonical запись. Отрицательный результат функции может сохранить event/запись на разбор; неизвестный SSH исход сначала проверяется чтением. После commit автоматического удаления начисления или восстановления всей live БД не предусматривается. Любая компенсация требует отдельного решения.

Новые платежи, provider POST, capture/cancel/refund, ручные финансовые SQL, другие аккаунты, legacy/c/Cloud изменения, merchant переназначение и DNS в область не входят. Успешная сверка не заменяет настоящее webhook E2E, платную нарезку и приёмку CJM.

[Официальная документация ЮKassa](https://yookassa.ru/developers/using-api/webhooks), прочитана09.11.2026, описывает автоматические повторы non200 в течение24часов от события; ручная кнопка повторной отправки на этой странице не документирована. Возврат callback сам по себе не доказывает повтор старого события.

## Отложенное решение после готовности данных

Возможный будущий scope, который потребуется заново предъявить владельцу после переноса: после свежей сверки и проверки точного инструмента **операторскую сверку одного старого успешного TEST-платежа990₽ и штатное начисление300 минут на связанный существующий аккаунт с исходным временем оплаты и действующими правилами периода**, включая один duplicate-check. Если сохранилась запись unknown_intent в другом хранилище, отдельное согласование её сохранения на разборе при source-only начислении требуется до записи.

Разрешение требуется из `features/relocate-clipmkr-to-workspace-vps/01_requirements.md` и `06_implementation_plan.md`: финансовые аномалии сохраняются при переносе, их исправление не входит в авторизованную подготовку. До такого решения, проверки инструмента и закрытия фактических gates — **STOP перед финансовыми записями**. Это не блокирует разрешённое копирование БД с сохранением обеих историй и не является текущим запросом согласования.

Полные IDs, account context, исходные ответы, привязки и hashes остаются только в закрытом `payment-window/reconciliation-proposal.private.md`. Секреты и персональные данные не публикуются.
