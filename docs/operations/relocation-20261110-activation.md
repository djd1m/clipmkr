# Запуск перенесённого Clipmkr без смены DNS

## Разрешение владельца

10.11.2026 владелец ответил «действуй» на следующий конкретный план: закончить комплект запуска, выполнить повторную финальную синхронизацию и запуск приложения на77.83.87.178 в одном окне, направить старый сервер194.85.249.105 на новый через relay, проверить приложение и затем тестовую оплату, предъявить ручную проверку. DNS меняется только по последующей отдельной команде. Это разрешение backend-переключения и relay; c.clipmkr.ru, legacy n5 и посторонние сайты сохраняются.

Ранее выполненный [срез](relocation-20261110-final-sync.md) сохранён; источник после него работал, поэтому срез не принимается за актуальные данные. На новом шаге не открываем техническое окно до готовности всего комплекта. После первого запуска нового writer старые source DB не включаются: неизвестный исход старта означает R2_REQUIRED и сохранение обслуживания до выяснения актуального состояния.

## Команда и методы

- Подготовка операций и привязок: gpt-6.1-sol high, отдельная задача activation_prepare.
- Независимое review точных артефактов: gpt-6-astra xhigh, новая сессия activation_review без контекста автора.
- Узкий диагностический маршрут relay/XFF/TLS: gpt-6.1-sol high, relay_probe_prepare; проверяется независимо до применения.
- Runtime операции выполняет последовательно координатор. Новых контейнеров БД/Redis/пробника не создаётся.

Используются текущие feature-adr требования/ADR/план, project-pinned dz recall, OpenSpec как журнал требований, расширенный QE по применимым протоколам. Семь ранее проверенных code targets не меняются; новый native closure не выдумывается. Документ фиксирует разрешение и порядок операций, а не результаты ещё не исполненных проверок.

## Порядок

1. Подготовить конкретные Compose/config, app roles/grants, каталоги, полный runbook и восстановление. Проверить исходные immutable образы, сохранение бизнес-настроек и только нужные привязки. Команда Compose запускает только приложения с --no-deps, не пересоздаёт существующие DB/Redis.
2. До freeze проверить реальный peer, HTTPS/SNI и нормализацию XFF временным защищённым echo-маршрутом в существующем прокси. Probe не возвращает секреты, затем удаляется; чужие маршруты сохраняются. Отдельно проверить ограниченность доступа к app ports.
3. Maintenance всех main/support входов; завершение in-flight/очередей и истечение ранее выданных partURL; две полные сверки multipart; stop всех writers и проверка клиентов.
4. Новый frozen срез main/support, scoped Redis и всех локальных файлов; legacy отдельно. Восстановление в новые назначения без перезаписи прошлых копий, сверка данных/структуры/sequence/TTL/files, off-host копии и требуемая проверка восстановления.
5. Применить app grants и bindings, записать устойчивый маркер попытки старта, запустить source-canonical образы за закрытым входом. При неизвестном результате — R2_REQUIRED; старые writers не возобновлять.
6. Проверить вход/сессии/существующие клипы/поддержку, затем открыть целевой ingress и переключить old edge на HTTPS relay без fallback к старым DB. На обоих адресах работает единственный target backend; DNS прежний.
7. Проверить загрузку и нарезку, роли/кабинеты, почту и настоящий TEST-платёж после данных. Старое платёжное расхождение сохраняется без финансового исправления; настоящие списания не включаются. Предъявить результаты и ограничения владельцу.

Точные private файлы: `/root/.config/clipmkr/relocate-workspace-20261109/activation-20261110/`. Там сохраняются конфигурации, hashes, operator logs, evidence и независимое review. Секреты, signed URLs и персональное медиа в Git не помещаются.
