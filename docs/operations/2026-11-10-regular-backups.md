# Регулярное резервирование Clipmkr на новом VPS

Состояние на 10.11.2026: **почасовой timer включён**, первый реальный запуск его service и восстановление данных проверены на VPS 77.83.87.178. Основной сайт — https://clipmkr.ru; приложение не останавливалось.

## Что сохраняется

- Свежие native PostgreSQL dumps основной БД и Libredesk, метаданные выбранных ролей.
- Native RDB выделенной инстанции Redis: все её логические БД, включая рабочие 2/6. Это не разрешение накладывать весь RDB на живую инстанцию.
- Файлы поддержки, корректный завершённый префикс журнала расходов моделей, действующие private compose/config, версии образов.
- Зашифрованный restic snapshot копируется в существующие Yandex S3 и Cloud.ru S3; его identity и manifest проверяются в обоих хранилищах.

Сами видео и клипы остаются в исходном S3. Независимая копия их байтов в этот охват не входит. Временные файлы распознавания/монтажа исключены как восстанавливаемые из исходников; при аварийном восстановлении очереди сверяются с БД/S3 до запуска workers.

## Как сопровождать

```sh
systemctl status clipmkr-backup.timer
systemctl show clipmkr-backup.service -p Result -p ExecMainStatus
journalctl -u clipmkr-backup.service -n 30 --no-pager
sudo python3 -m json.tool /var/lib/clipmkr-backup/last-success.json
sudo python3 -m json.tool /var/lib/clipmkr-backup/last-attempt.json
```

После успешной oneshot-задачи `inactive (dead)` — нормальное состояние service. Проверять нужно Result/ExecMainStatus, last-success и возраст копии. Для внеочередного запуска: `systemctl start clipmkr-backup.service`.

Собственные настройки: `/etc/clipmkr/backup/`; scripts: `/opt/clipmkr/backup/`; staging/receipt: `/var/lib/clipmkr-backup/`; unit и canonical-lock drop-in: `/etc/systemd/system/clipmkr-backup.service*`. Секреты не печатать и не переносить в Git. После пересоздания контейнеров сверить и обновить закрытый runtime-binding по фактическим ID/images/connections/mounts: при несовпадении задача намеренно отказывает.

Используются прежние restic/rclone, cloud profiles и общий lock. Новый descriptor не регистрируется в corp registry: его схема не допускает имя clipmkr. Чужие hooks, таймеры, IAM и retention не изменялись. При занятом общем lock часовой запуск завершится отказом, а возраст предыдущей успешной копии продолжит расти. Staging ограничен двумя наборами до 1 GiB каждый и запасом свободного места; общий срок хранения local/offsite остаётся прежним. Часовой интервал — настройка, не доказанная гарантия RPO.

## Восстановление и границы результата

Извлекать выбранный snapshot в закрытый каталог, сверять manifest/checksums, восстанавливать PostgreSQL только в новые изолированные назначения. Перед запуском восстановленного приложения нужны роли/config, доступ к S3, доступные образы соответствующих версий и сверка очередей с БД/медиа. Онлайн-срез нескольких хранилищ не является общей атомарной точкой.

Проверены cloud extraction и PostgreSQL restore; полный аварийный запуск приложения на новом сервере, загрузка RDB в изолированный Redis, фактическое получение escrow-ключа вне потерянного VPS и доставка уведомления о сбое не проверялись. Существующая escrow attestation не заменяет такую проверку. Общий прогон app tests остановлен и остаётся INCOMPLETE; общий typecheck имеет ограничения окружения. Это не заявка о прохождении всей регрессии продукта.

Закрытые доказательства: `/root/.config/clipmkr/backup-audit-20261110/`; содержат реальные данные/настройки и в Git не публикуются. В публичных документах только команды, пути, результаты и ограничения.

Независимая runtime-проверка `gpt-6-astra xhigh` подтвердила копии, контрольные суммы и данные восстановленных БД. После неё удалены только две специально созданные БД проверки; их отсутствие подтверждено. Рабочие БД не изменялись.
