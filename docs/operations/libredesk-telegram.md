# Уведомления о сообщениях поддержки Clipmkr

Один входящий публичный ответ клиента создаёт уведомление в закрытой группе со ссылкой на диалог Libredesk. Первый текст нового диалога тоже входит в `message.created`. В группу поступает только фиксированный текст и URL диалога. Больше контекста сотрудник видит в Libredesk после входа.

## Выкладка на VPS

1. Обязательные проверки перед выпуском — `npm run test:support-telegram` и `docker compose ... config --quiet` с параметрами ниже. Сверить локальный digest образа Node из `ops/libredesk/telegram.compose.yml`, файлы проверенной ревизии и имя сети работающего Libredesk. Сервис подключается к этой сети без публикации host-порта. Выпуск извлекается в стабильный каталог ревизии. Для публичного `ops/libredesk/telegram-adapter.mjs` выставить режим 0644, чтобы его мог читать пользователь контейнера `node`. Закрытые env-файлы сохраняются с 0600.
2. Использовать закрытый профиль `telegram-support.env` с `TELEGRAM_BOT_TOKEN` и числовым `TELEGRAM_SUPPORT_CHAT_ID`. В отдельном файле `libredesk-relay.env` с правами 0600 задать `CLIPMKR_SUPPORT_NETWORK`, свободный фиксированный IPv4 этой сети `CLIPMKR_SUPPORT_RELAY_IP` и независимый случайный `LIBREDESK_TELEGRAM_WEBHOOK_SECRET`. Токен бота остаётся в профиле.
3. Из корня проверенного рабочего каталога выполнить:

   ```bash
   docker compose -p clipmkr-telegram \
     --env-file /root/.config/clipmkr/telegram-support/telegram-support.env \
     --env-file /root/.config/clipmkr/telegram-support/libredesk-relay.env \
     -f ops/libredesk/telegram.compose.yml up -d --no-deps --wait
   ```

4. При включённой SSRF-защите Libredesk сохранить исходный закрытый TOML и добавить в действующий `ssrf.allowed_cidrs` только адрес контейнера адаптера с маской `/32`. Сохранить `ssrf.enabled=true` и существующие исключения, если они есть. Перезапустить только Libredesk, проверить его health и точный IP здорового адаптера. Провести контроль с синтетическим `webhook.test` на другом локальном адресе без исключения и подтвердить явный отказ защиты. [Настройки Libredesk](https://support.libredesk.io/en/articles/ssrf-protection)
5. В Libredesk открыть **Admin → Integrations → Webhooks**. Имя **Clipmkr Telegram — входящие сообщения**. URL `http://libredesk-telegram:8080/libredesk`. Выбрать только **Message created**. В **Secret** задать тот же секрет подписи. Создать подписку выключенной и выполнить **Send test**. В журнале Libredesk проверить HTTP 204 от адаптера, затем включить подписку.
6. Проверить первое и последующее сообщения в синтетическом диалоге. Ссылка открывает оба события в одном диалоге. Ответ сотрудника отображается в виджете без дополнительного уведомления.

## Поддержка и откат

Логи сервиса содержат `telegram_delivered` с ID сообщения Telegram, `telegram_skipped` или `telegram_failed` с кодом причины. Невалидный ввод отмечается `webhook_rejected` и кодом причины без тела и подписи. HTTP 204 подтверждает приём события. Фактическую доставку подтверждает запись `telegram_delivered`. Telegram получает одну попытку на принятое событие. При сбое чат продолжает работать. Внешняя повторная доставка того же события может повторить уведомление.

Для отката сначала отключить конкретный вебхук, затем остановить только сервис проекта `clipmkr-telegram` с теми же Compose-аргументами. Убрать добавленное исключение `/32` из Libredesk и перезапустить только helpdesk. При замене закрытых переменных пересоздать только этот сервис. Смена секрета подписи требует обновить поле **Secret** той же подписки.
