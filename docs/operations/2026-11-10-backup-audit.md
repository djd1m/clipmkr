# Проверка регулярных резервных копий Clipmkr

## Результат

10 ноября2026 после переноса и тестовой оплаты проверена система резервирования VPS77.83.87.178. **Регулярная резервная копия рабочих данных Clipmkr не настроена.** Само наличие ежедневного systemd timer и успешной отправки в S3 не подтверждает охват приложения.

Установленная общая система использует restic, systemd, реестр manifest и pre/post hooks. Ежедневный основной запуск около03:00UTC; отдельная отправка во второе хранилище около05:45UTC, еженедельная проверка и месячная очистка. Используются основной Yandex S3 и второй Cloud.ru S3. По текущему state обе отправки завершились успешно10.11, но общий backup запуск завершился ошибкой.

Реестр включает platform, observability и coding-workspaces. Последний hook сохраняет только committed HEAD репозиториев в каталогах codexworker/claudeworker и SQLite ledger; он не сохраняет PostgreSQL, Redis или production mounts Clipmkr. Manifest платформы тоже не включает новые рабочие хранилища Clipmkr. Общий FAIL связан с отказом pre-hook coding-workspaces; в журнале также есть недоставленное уведомление Alertmanager. Точная внутренняя причина отказа чужого hook в этом аудите не установлена и не исправлялась. Сбой общей задачи и отсутствие охвата Clipmkr — разные проблемы.

## Немедленное сохранение новых данных

В07:26UTC без остановки приложения выполнены штатные pg_dump -Fc двух действующих БД: основной и поддержки, включая состояние после тестовой покупки. Архивы сохранены на новом VPS и переданы по проверенному SSH на прежний сервер194.85.249.105. SHA-256 обеих копий совпали; pg_restore --list успешно прочитал оба архива.

Закрытые файлы на новом VPS: `/root/.config/clipmkr/backup-audit-20261110/postgres-20261110T072617Z/`.
На втором сервере: `/root/.config/clipmkr/post-dns-backup-20261110/postgres-20261110T072617Z/`.

Это ручная мера, **не расписание и не полная DR-копия**. Каждый pg_dump согласован внутри собственной БД; общая атомарность между двумя БД, Redis, файлами и S3 не заявляется. Для этих свежих архивов выполнена проверка структуры архива, не новый полный restore drill. Полный проверенный frozen комплект переноса остаётся сохранённым отдельно; он предшествует новой оплате и новой нарезке.

## Минимальное исправление

Переиспользовать существующие restic, облачные профили, systemd, метрики и manifest hooks. Не создавать второй движок backup и не копировать живой каталог PostgreSQL как обычные файлы.

1. Добавить отдельный manifest Clipmkr и адаптер подготовки набора: две реальные БД по проверенным runtime bindings; native Redis snapshot; uploads/config приложения поддержки; модельный расход и нужные рабочие файлы; точные версии образов/профили запуска. Секреты — только в закрытой локальной подготовке и зашифрованном restic, не в Git.
2. Запускать отдельную ограниченную задачу Clipmkr каждый час, используя общий lock системы backup; сохранять сведения о времени каждого компонента и отказывать при неопределённых bindings/ошибке выгрузки. Час — предлагаемый интервал, а не уже действующий RPO.
3. Передавать успешный снимок в оба уже настроенных хранилища. Нельзя обозначать успехом снимок только кода или ранее созданные stale dump-файлы. Чужой coding-workspaces hook не должен блокировать scoped запуск Clipmkr; чужие retention/приложения не менять.
4. Различать аварию VPS и потерю объектов S3. Для первой сохраняются ссылки/метаданные и существующее внешнее хранилище медиа. Независимая копия самих исходников/клипов и её retention требуют отдельного явного охвата; список ключей не выдаётся за копию видео.
5. Приёмка ровно этого изменения: один успешный scheduled/scoped snapshot с новым payment и новой записью; offsite snapshot identity; извлечение и восстановление в изолированные назначения существующего PostgreSQL; проверка выбранных строк, Redis и файлов. Рабочие данные не заменять, тесты нарезки/оплаты повторно не запускать. Восстановление очередей — с остановленными workers и сверкой состояния, без обещания атомарного online snapshot разных хранилищ.

До кода подключения — feature-adr требования/инвентаризация/ADR и план, OpenSpec дельта, настоящие K1/K2 и независимое ревью по правилам проекта. Этот документ — результат аудита и предложение реализации; receipts, готовность автоматизации и гарантия восстановления новых данных не имитируются.

## Закрытие обнаруженного пробела 10.11.2026

Установлено отдельное почасовое резервирование Clipmkr без изменения чужого registry/hooks. Первый реальный запуск service сохранил данные в двух offsite; восстановление двух изолированных БД подтверждено независимо. Timer включён, его первое автоматическое срабатывание на момент закрытия ещё не наблюдалось. [Протокол и ограничения](2026-11-10-regular-backups.md). Исходные результаты аудита выше сохранены как история.
