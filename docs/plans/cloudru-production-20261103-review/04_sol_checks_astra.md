## Дополнения для итогового плана

### SESSION_SECRET защищает больше, чем session

`apps/web/src/lib/partner-referral.ts` подписывает cookie через HMAC с префиксом `referral:`. `upload-runtime.ts` передаёт sessionSecret PartnerService; guest-page использует referralSecret. `screen-runtime.ts` передаёт sessionSecret как guestSecret, `guest-file.ts` подписывает JSON `guest-file-v1` HMAC. Значит ротация при миграции одновременно инвалидирует прежние session cookie, ещё действующие referral cookie и guest-file tickets. Сами guest/short codes в БД могут остаться исправными, а уже выданный ticket — перестать работать; свежая загрузка страницы генерирует новый ticket, это другой сценарий.

Добавить проверку сохранённой referral cookie и ещё действующей guest-file ссылки отдельно от открытия guest landing/short link. Guest ticket по исходнику действует не более 900000мс, поэтому проверка должна укладываться в TTL; провал естественно истёкшей ссылки не означает потерю данных. Для n5 иной SESSION_SECRET обязателен, production секрет в stage не клонировать. Аналогично старые S3 presigned URL при отзыве ключа могут перестать действовать — последовательность ротации и TTL учитывать отдельно, значения/URL в отчёт не помещать.

### Полнота PostgreSQL и Redis подготовки

Compose использует `postgres:16.4-alpine`, роль/БД `n5`, env POSTGRES_PASSWORD, named pgdata. Env инициализации PostgreSQL не меняет пароль уже существующей роли в восстановленном physical volume. План должен различать logical restore в новую инициализированную БД и physical restore совместимого cluster; явно проверить roles/ownership/grants/extensions, actual version, migration journal и право приложения работать после restore, не выводя credentials. Обычный pg_dump одной БД не сохраняет cluster roles. Для этого проекта нельзя молча требовать superuser restore под новым случайным паролем и считать POSTGRES_PASSWORD доказательством готовности.

Redis `redis:7.4-alpine` настроен AOF и password. Нужен корректный persistence artifact выбранного способа (включая состав multi-part AOF, если применимо), version/volume mapping, restore без старого процесса, проверка AUTH и выбранной DB, сопоставление DB attempt↔job identity. Копирование одного предполагаемого appendonly.aof без инвентаризации реальных файлов не является проверенной процедурой. Полный Redis restore может включать rate-limit ключи и иное состояние: стратегия должна объяснять их сохранение/сброс отдельно от jobs. Эти детали не требуют сейчас чтения секретов или запуска инфраструктуры, но обязательны для будущего runbook.
