## Находки

### OPS-01 — High: предварительный запуск клона может удалить production-медиа

План предлагает восстановленную базу и проверку на Cloud.ru до переключения. `apps/web/src/instrumentation.ts` при запуске включает `startQueueWatchdog`; `server/queue-runtime.ts` передаёт реальные S3 delete/erase; `server/watchdog.ts:76` запускает retention. Старый снимок основной БД + основной бакет + работающий web уже являются независимым писателем/удалителем, даже без DNS и открытых новых загрузок. Позже оставленный VPS с production-клоном тоже способен удалять те же объекты.

Добавить обязательный запрет запускать такой клон с правом удаления production-объектов. При rehearsal — отдельная копия нужных объектов в stage-бакете и отдельные ключи с проверкой отказа доступа к production. До запуска старого VPS как test сменить бакет/ключи и очистить либо заменить его production-БД и очереди по отдельному утверждённому порядку. Факт «разные бакеты» должен включать проверку IAM, а не только имени в env.

### OPS-02 — High: сохранение IP клиента противоречит наивному старый→новый proxy

`ops/cloudru/Caddyfile.managed` безусловно переписывает X-Forwarded-For в `remote.host, 127.0.0.1`. При старый VPS→Cloud.ru он сохранит адрес VPS, а не посетителя/ЮKassa. `server/ip.ts` выбирает адрес по числу hops, webhook проверяет его по allowlist ЮKassa (`billing-handler.ts:198–200`). Итог: webhook может отвергаться, общий rate limit будет применяться ко всем посетителям как одному IP. В прямом managed-тракте надо также проверить hops: Caddy задаёт два элемента, а shared/config.ts по умолчанию требует два доверенных hops, для чего цепочки недостаточно.

Плану нужна точная схема прямого и переходного тракта, явно выбранные hops и доверенные адреса. Входящий поддельный XFF от интернета удаляется; цепочка старого relay принимается только от его конкретного адреса. Перед переключением проверить прямой и relay-тракты: действительный клиент, поддельный XFF, rate limit, разрешённый/запрещённый IP webhook. Обычный health200 этого не доказывает.

### OPS-03 — High: webhook-test заявлен без найденного владельца маршрута

В исходниках есть `apps/web/src/app/api/webhooks/yookassa/route.ts`; `yookassa-test/route.ts` отсутствует. Поиск `yookassa-test` по apps/ops/proxy ничего не нашёл. Значит заявленный в плане существующий `/api/webhooks/yookassa-test` может быть маршрутом внешнего прокси, который не перенесён в репозиторий; его фактическое наличие этим ревью не опровергнуто.

Добавить инвентаризацию реальной внешней конфигурации и доказать, какой hostname+path направляется к какому test/prod магазину, БД и credentials. Удобный вариант для рассмотрения — штатный `/api/webhooks/yookassa` на отдельном n5 hostname; решение за планом. Проверить оба адреса до/во время/после DNS, return URL и pending-платежи. При production off ожидается 404 (таков контракт route), не выдавать его за успешный приём webhook. Нельзя механически направить test webhook в основной backend.

### OPS-04 — High: freeze загрузок/оплат не обеспечивает единый согласованный снимок

Даже при закрытых новых upload/payment продолжаются существующие multipart complete, retry/rerender, auth, referral, callbacks, watchdog/retention и worker commits. Redis и PostgreSQL нельзя копировать как независимые живые состояния; BullMQ имеет фиксированные queue names (`packages/queue/src/queues.ts`) и job IDs с fence. План не задаёт момент остановки всех writers, обработку deferred/delayed jobs и точку согласованности.

Добавить перечень писателей, drain active jobs с дедлайном и решением для зависших, fencing старых web/workers/watchdog, блокировку новых мутаций на внешней двери, порядок последнего PG/Redis backup и восстановления. Отдельно выбрать перенос согласованного Redis либо восстановление очередей из авторитетной БД по доказанному контракту; не смешивать оба произвольно. Pending webhook должен получить контролируемый ответ с последующей повторной доставкой/сверкой, а не потеряться. До GO доказать, что старые writers остановлены и могут оставаться только relay.

### OPS-05 — High: rollback после записей назван, но не превращён в процедуру

Фраза «требует их переноса» верна, однако не определяет владельца истины, freeze новой площадки, возврат всей БД/очередей и S3 effects. Частичный обратный перенос потеряет оплаты/кредиты/сессии/рефералов, а простой snapshot до cutover не содержит новых записей. Удалённые retention объекты не восстанавливаются одной БД.

Добавить два сценария: до открытия writers — возврат старой площадки с доказанным отсутствием новых записей; после — остановка всех новых writers, сохранение согласованного актуального состояния и восстановление его на старой площадке, проверка совместимости старого образа с новой схемой, смена relay/DNS только после сверки. Если обратный restore не испытан или схема несовместима — STOP и исправление на Cloud.ru, а не обещание быстрого DNS rollback. Задать RPO/RTO и критерии выбора, включая невосстановимые изменения S3.

### OPS-06 — High: backup→restore не имеет измеримого критерия успеха

«Проверить восстановление» не определяет содержимое и репетицию. Named volumes копированием на живую не гарантируют корректную согласованность; текущая неизвестная БД Cloud.ru должна сохраняться отдельно, а не заменяться без идентифицируемого restore artifact.

Включить реестр backup: источник/время/версия PG/образы/схема, PG dump или корректный physical backup, Redis persistence выбранной стратегии, нужные конфигурации и закрытое хранение секретов, медиа вне S3 если найдутся, существующая БД Cloud.ru отдельно. Репетиция в изолированном окружении: успешный restore, миграции, контрольные количества/связность ключевых сущностей и выборочная доступность объектов, CJM на отдельных тестовых данных, фактическое время восстановления; checksum и срок хранения. Не запускать restored web с production S3 deletion permissions (OPS-01). GO только при подтверждённом restore, а не наличии файла.

### OPS-07 — Medium: DNS/TLS/origin/cookie не заданы как проверяемая матрица

Managed Caddy получает один `CLIPMKR_HOST`; план не определяет `www`, c hostname, A/AAAA, TTL, сертификат для clipmkr.ru до DNS и renewal при relay. Старый TLS обязан оставаться действительным, пока клиенты приходят на старый IP. `__Host-n5_session` в `auth-handler.ts` — Secure, host-only, Path=/; переход на n5 не переносит production-cookie. `billing-handler.ts:89` и support boundary строго сравнивают Origin с publicOrigin. Проверка на c hostname с production publicOrigin сама по себе может проваливать мутации.

Добавить DNS inventory A/AAAA/CNAME/TTL, canonical hostname/редиректы, предвыдачу/доказанный способ выпуска TLS и HTTPS smoke с SNI/Host на целевой IP до cutover. Relay обязан сохранять Host, scheme, Origin и Set-Cookie; редирект на c hostname меняет пользовательский origin. Для production сохранить нужный SESSION_SECRET при переносе хэшированных сессий либо явно согласовать logout; для n5 создать отдельный SESSION_SECRET, S3/model/SMTP/support/payment credentials и отдельную БД/Redis/Compose project. Проверить login/logout, CSRF чужого Origin, multipart CORS с обоих разрешённых origins в соответствующих бакетах, reset/email/guest/referral ссылки и watermark preflight для нового n5 имени.

### OPS-08 — Medium: доступ и resize требуют отдельного STOP/GO

SSH timeout может означать сеть/SG/маршрут/OS; план не должен решать это широким открытием SSH и пересозданием ВМ. До потенциально прерывающих действий: подтвердить ID/zone/IP/диски, путь через консоль и конкретный deploy key, источник и минимальные SG правила, сохранить текущие конфигурации и независимую копию данных. Права на управление ресурсами и рабочий аварийный доступ проверяются до остановки/resize. Новый расход или resize данным черновиком не разрешён.

Официально проверено 03.11.2026: Evolution изменение конфигурации перезагружает ВМ; требуется дождаться важных процессов. Создание backup доступно для ВМ в статусе «Запущена». Следовательно порядок «остановить ВМ, затем сделать cloud backup» нельзя молча предполагать. План должен различать остановку writers/контейнеров и остановку самой ВМ, дождаться готовности резервной копии и иметь проверенный путь восстановления до resize. Cloud backup не заменяет доказанный application-consistent PG/Redis backup. Прямой web.open официальных страниц вернул Internal Error; затем их HTML успешно прочитан через curl, видимый текст извлечён локально.

Источники: [изменение конфигурации Evolution](https://cloud.ru/docs/virtual-machines/ug/topics/guides__edit-cpu-ram?source-platform=Evolution), [создание резервной копии](https://cloud.ru/docs/virtual-machines/ug/topics/guides__create-backup?source-platform=Evolution). Иные облачные платформы не использовались как доказательство Evolution.

## Минимальный набор gates для следующего плана

STOP при отсутствии SSH/консоли, проверенного restore, сохранения неизвестной БД Cloud.ru, изоляции S3/секретов/очередей, приемлемого ресурса либо проверенного proxy/webhook тракта. GO на cutover — только после rehearsal и freeze всех старых писателей. GO на открытие новых записей — после проверки единственного писателя, БД/очередей/медиа, TLS/origin/auth и критических CJM. После открытия — отдельное наблюдение ошибок, backlog, диска и платежной сверки с указанным сроком и владельцем решения. Численные RPO/RTO/дедлайны и пороги обязан определить исполнимый план; этим ревью они не выдумываются.

Ограничения: live Cloud.ru inventory, секреты, текущая конфигурация внешнего VPS reverse proxy и реальные backup artifacts не проверялись. Найденное отсутствие test-route в репозитории не доказывает отсутствие внешнего route. Это ревью плана, не выполненный переезд и не тест production.
