# N5 «КлипМейкер» — бэклог: что осталось сделать

## SUPPORT-001 — история обращений и отложенные ответы у пользователя

**Добавлено05.11.2026. Статус: бэклог; сейчас не реализовывать.**
Владелец сообщил: пользователь отправил сообщение, оператор Libredesk видит вопросы
и ответы в истории, а пользователь свою переписку не видит. Общение фактически работает
только в реальном времени, что не подходит для поддержки с отложенным ответом.
Пример конкретного аккаунта передан владельцем; адрес сохранён только в закрытом
`/root/.config/clipmkr/support-history-20261105/owner-reported-case.private.json`, без текста переписки.
В публичный Git email, visitor tokens, сообщения, session cookies и пароли не помещать.

### Наблюдение и контекст для диагностики

Это сообщение владельца, не независимо воспроизведённый браузерный инцидент.
Сохранность у оператора и отсутствие истории у клиента нужно проверять отдельно:
не объявлять удаление сообщений из БД только по пустому виджету.

Проверено чтением текущего support-кода, совпадающего с app source f55ae400:

- Публичная конфигурация ранее подтверждена как Libredesk, `identifiedEnabled=false`:
  вход Clipmkr сам не связывает пользователя с историей. См. [исследование доступа](research/support-access/README.md).
- `apps/web/src/app/support/SupportPanel.tsx` вызывает clearSupportIdentity при focus,
  visibilitychange, смене account/verified и cleanup; повторное открытие может идти как anonymous.
- `apps/web/src/lib/support-client.ts`: clearSupportIdentity вызывает native widget.logout;
  openAnonymousSupport начинает с очистки identity. Close через hide — отдельное действие.
- Уже существуют native widget bridge, опциональная проверенная identity/JWT и Libredesk
  conversation/history API. Начать с них; новый сервис тикетов и собственную БД переписки не создавать.

Связь конкретного исчезновения с очисткой identity/anonymous mode пока гипотеза:
нужно проверить фактические widget tokens/storage, жизненный цикл focus/navigation,
поддержку подтверждённой identity и режимы браузера. Просто включить identified flag
или убрать logout без проверки защиты смены аккаунта недостаточно.

### Ожидаемое поведение и критерии приёмки

1. Пользователь видит свои предыдущие вопросы и ответы оператора при повторном открытии
   чата, после закрытия/обновления страницы, ухода на другой экран и возврата фокуса.
   Отправленное сообщение не должно исчезать из его истории после перехода в другую вкладку.
2. Оператор отвечает после ухода пользователя; при возвращении пользователь получает
   ответ в соответствующем диалоге без требования одновременно находиться онлайн.
   Состояния ожидания, новых ответов и недоступности связи понятны; сеть/ошибка не изображаются пустой историей.
3. Для вошедшего пользователя история безопасно относится к его аккаунту и восстанавливается
   после повторного входа. Проверить также другой браузер/устройство; точный контракт
   гостевого режима и ограничений хранения определить в требованиях до реализации.
4. После logout или переключения A→B чужая история не показывается даже кратковременно.
   Произвольный email/visitor ID не даёт доступа к переписке; использовать штатную проверенную identity.
   При этом повторный вход A не должен уничтожать его сохранённые обращения.
5. E2E с двумя синтетическими аккаунтами и отдельным оператором: вопрос → пользователь ушёл →
   ответ оператора → возврат/новая сессия → чтение и продолжение того же диалога.
   Проверить Chrome на Windows, мобильную ширину, guest/auth, close/reopen, reload,
   focus/visibility, смену аккаунта, временный offline и повтор отправки без дублей.
   История оператора не заменяет проверку клиентского виджета. Не читать реальные сообщения
   примера и не отправлять тестовые ответы реальному пользователю при подготовке фикстур.

Уведомления о новом ответе — отдельная проверка возможностей и настроек Libredesk;
письма verify/reset через Resend не доказывают доставку ответов поддержки. Рассылку/новые
каналы без отдельного решения не включать. Перед UI изменениями согласовать конкретный
макет; далее feature-adr + pinned dz, требования/reuse/применимые ADR/план/gates,
OpenSpec, расширенный QE и независимый cross-model review. В этой задаче пока только бэклог.

## MUSIC-001 — доступная смена музыки у готового клипа

**Добавлено05.11.2026. Статус: бэклог; по этой команде не реализовывать.**
Владелец сообщает, что не может поменять музыку уже сформированного клипа на записи
[пример на clipmkr.ru](https://clipmkr.ru/dashboard/videos/f90c318a-5290-44bc-ae95-6a617d2c7ee1).
Ссылка требует авторизации; это пример проблемного пользовательского пути, а не разрешение
изменять запись, пересобирать клипы или публиковать её материалы. Точный clip_id,
состояние выбранного клипа, тема/компоновка и текст отказа пока не зафиксированы.

### Что уже есть и что нужно выяснить

Проверено чтением исходников main после публикации автоссылки, базовый app source f55ae400:

- FR-RESULT-005 / ADR-016 и `docs/features/clip-music-choice/05_completion.md` уже описывают
  смену музыки готового клипа. Сентябрьский done не доказывает работу указанной записи сейчас.
- `apps/web/src/app/clips/ClipCard.tsx` включает существующий `ClipMusicChoice` внутри
  закрытого раздела «Оценка и настройки клипа».
- `ClipMusicChoice.tsx` содержит каталог, «Авто», «Без музыки», прослушивание и вызов
  `clip.setMusic`; select отключён при unavailable/busy/rerendering.
- `apps/web/src/server/clip-music.ts` проверяет принадлежность/срок хранения, отсутствие
  активной пересборки и требует done одновременно у записи и клипа; действует квота rerender.

Причина сообщения владельца **не установлена**: возможны обнаружимость действия,
конкретное состояние/отказ, в том числе готовый клип у записи с частичным результатом.
Браузерное воспроизведение и проверка состояния этого видео в рамках добавления бэклога
не проводились. При возобновлении сначала сверить фактическую опубликованную версию,
воспроизвести путь и различить скрытый контрол, disabled и серверный отказ.
Новый редактор, каталог или механизм рендера заранее не создавать: переиспользовать существующие.

### Ожидаемое поведение и приёмка

1. Владелец доступного готового клипа находит понятное действие смены музыки,
   прослушивает существующие треки и выбирает другой трек либо «Без музыки».
   Не загромождать основной экран; перед изменением UI согласовать конкретный макет.
2. После подтверждения видны состояние пересборки и результат; по окончании
   плеер и скачивание дают новую версию со слышимым изменением. Reload сохраняет выбор.
   Исходную запись повторно загружать/расшифровывать и списывать за неё кредиты не нужно;
   применимые действующие ограничения пересборки показываются до запуска.
3. При сбое предыдущий готовый файл сохраняется и доступен; отказ/лимит/истёкший срок
   объясняются явно. Повторные клики и конкурентные запросы не создают двойную пересборку.
4. Отдельно проверить готовый клип у частично неуспешной записи: целевой контракт
   согласовать с ADR-016 и принятой механикой частичного результата, не скрывать отказ
   под общим «Клип ещё собирается». Поведение не считать реализованным заранее.
5. Проверить свой/чужой клип, обычного пользователя и блогера, обе темы/компоновки,
   мобильный/desktop, браузерное воспроизведение и скачанный файл после реального worker/S3.
   Чужое изменение запрещено; тесты только сервера или static mockup не закрывают E2E.

При старте: feature-adr + pinned dz recall, требования/reuse/применимые ADR и план/gates,
OpenSpec-дельта, extended QE и независимое cross-model review. Эта запись — достаточный
контекст отложенной задачи, не завершённая спецификация, не согласование макета и не разрешение
выкладки на Cloud.ru. Другие согласованные задачи продолжаются.

## AUTH-001 — понятная повторная регистрация и вход

**Добавлено 05.11.2026. Статус: отложено владельцем; сейчас не реализовывать и не выкладывать.**
Источник: сообщение владельца «Если аккаунт есть — то надо об этом пользователю написать и войти!»
и последующая команда сохранить задачу в бэклоге с достаточным контекстом.

### Проблема и подтверждённые наблюдения

На `https://clipmkr.ru` пользователь считал аккаунт новым, отправлял форму регистрации
и оставался на ней без понятного объяснения. Читающий запрос к фактической БД 05.11
показал, что аккаунт уже создан 28.10; также обнаружена активная сессия от 05.11.
Последнее само по себе не доказывает успешный вход именно из проблемной вкладки.
Адрес пользователя, идентификаторы, токены и пароль для воспроизведения не нужны
и в публичном бэклоге не сохраняются.

Исследованный код, база для повторной проверки — commit `24b4b4a`:

- `apps/web/src/server/auth-store.ts`, `PgAuthStore.register`: `ON CONFLICT(email) DO NOTHING`;
  при существующем адресе запись аккаунта и новая сессия не создаются.
- `apps/web/src/server/auth.ts`, `AuthService.register`: возвращает сгенерированный
  токен даже при таком конфликте; это ещё не доказательство действительной сессии.
- `apps/web/src/server/auth-handler.ts`: успешный ответ регистрации устанавливает cookie.
- `apps/web/src/app/AuthForm.tsx`: после успешного ответа считает пользователя
  авторизованным, применяет реферальный код и направляет в кабинет.

Эта цепочка установлена чтением кода; отдельного браузерного воспроизведения
повторной регистрации в рамках диагностики **не было**. Перед исправлением сверить
актуальный код/образ фактического стенда и воспроизвести на синтетическом аккаунте.

### Требуемое поведение

1. Новый адрес: создать аккаунт и действительную сессию, открыть кабинет.
2. Существующий адрес и верный пароль: сообщить «Аккаунт уже существует. Вы вошли»
   и открыть кабинет этого аккаунта. Отдельная повторная регистрация не нужна.
3. Существующий адрес и неверный пароль: сообщить, что аккаунт уже существует,
   предложить «Войти» и «Забыли пароль?», сохранить введённую почту. Доступ без
   проверки пароля не предоставлять; введённый при повторной регистрации пароль
   не должен заменять прежний. Не оставлять форму в ложном состоянии «вход выполнен».
4. Использовать существующие форму, проверку пароля, создание сессии и восстановление;
   новый экран, отдельный сервис авторизации и новые зависимости не требуются.

### Критерии приёмки и ограничения

- Реальные браузерные сценарии новой регистрации, повторной с правильным/неправильным
  паролем, перехода к входу и восстановления; обновление кабинета подтверждает сессию.
- Повторный запрос и конкурентная регистрация одного адреса оставляют один аккаунт,
  не начисляют повторный пробный бонус и не меняют баланс, роли или пароль.
- Существующему аккаунту не переписывается реферальный источник; сохраняются
  безопасный `next`, ограничения запросов, проверка Origin и защищённые cookie.
- Явное сообщение о существующем адресе меняет прежнее поведение сокрытия конфликта.
  До кода согласовать это с актуальными требованиями/ADR авторизации, зафиксировав
  прямое решение владельца; не подменять проверку пароля знанием адреса.
- Проверить на мобильной и настольной ширине, клавиатурой, при ошибке сервера/сети;
  не показывать успех при недействительной сессии и не раскрывать внутренние ошибки.

При возобновлении: feature-adr + закреплённый dz (recall, требования/переиспользование,
применимый план/ADR и gates), OpenSpec как журнал дельты, тесты и независимое
cross-model ревью. Текст/состояния формы показать в конкретном макете по AGENTS.md.
Сначала согласованный тестовый стенд, браузерная E2E и ручная приёмка владельца;
Cloud.ru — только после неё. Эта запись не разрешает реализацию, миграцию БД,
изменение аккаунтов или развёртывание. Сентябрьские/октябрьские статусы ниже —
исторические и этой записью не актуализируются.

## 1. Перенос на другой сервер — чего НЕТ в репозитории

Репозиторий переносит код и документы. Эти вещи живут только на текущей машине, их нужно перенести или
пересоздать отдельно:

| Что | Где сейчас | Что делать |
|---|---|---|
| Секреты и настройки стенда (27 переменных: пароли БД/Redis/MinIO, `SESSION_SECRET`, `OPENROUTER_API_KEY`, `N5_PUBLIC_ORIGIN`, потолки `N5_LIMIT_*`…; с фичи 30 — ещё `N5_LIMIT_PAID_USER_MINUTES` и, при включённой оплате, `N5_PAYMENTS_MODE`/`YOOKASSA_*`) | `.env.n5-demo` в каталоге проекта (вне git через `.gitignore`: правило `.env.*`); прежняя запись «`/tmp/n5-demo.env`» устарела | перенести защищённым каналом или создать заново по `.env.example`; пароли — `openssl rand -hex 24`. 15. Витрина лендинга раздаёт клип ≈ 23 МБ публично; ограничение — только 120 запросов/мин на адрес, облегчённой
    версии клипа нет (`docs/features/landing-demo/05_completion.md`).
    **Разобрано 28.09.2026, код не менялся: при нынешней схеме (302 на подпись S3 к готовому клипу) первый показ без нового объекта в бакете
    стенда не уменьшить;
    повторный трафик можно сократить кодом (вариант Д), но от массового скачивания это не защищает.**
    Что отдаётся (замер публичного `/api/showcase/CTDUUG/file`): это НЕ оригинал записи, а обычный готовый клип —
    `clips/free/…/46f99d89-…-v2.mp4`, 23 104 302 Б, 71,0 с, H.264 High 1080×1920 25 fps ≈ 2,46 Мбит/с + AAC ≈ 134 кбит/с,
    `+faststart` (рендер `-preset fast -crf 23`, `apps/worker/src/render/ffmpeg.ts:101`). `preload="none"` и постер у
    `<video>` уже стоят (`apps/web/src/app/LandingDemo.tsx`): без нажатия «играть» байты клипа не качаются.
    Точная причина расхода — две: (а) **120/мин ограничивает выдачу ПОДПИСЕЙ, а не скачивания**: ответ — 302 на
    подписанную ссылку S3 на 900 с, и одну ссылку можно качать сколько угодно раз мимо `web` (проверено: три
    Range-запроса по одной ссылке — 206/206/206); (б) у самого объекта на стенде нет `Cache-Control` (наблюдение
    стенда, из кода не следует; у ответа 302 — `private, no-store`), а ссылка меняется на каждый запрос
    (`X-Amz-Date`), поэтому повторный показ тем же браузером качает заново.
    Варианты (замеры — перекодирование ЭТОГО файла в `scratchpad`, не стенд):
    А. **Облегчённый ассет витрины** — разовое `ffmpeg` готового клипа в отдельный ключ, `SHOWCASE_CLIPS` получает
       ключ облегчённой версии, маршрут `file` отдаёт его. 720×1280 `crf 28` + AAC 96k = **6,8 МБ (−70 %)**,
       540×960 = **4,9 МБ (−79 %)**. Рендер-цепочка пользователей не меняется; нужен шаг оператора на стенде (загрузка
       объекта) и взгляд человека на читаемость субтитров и метки после второго кодирования. Оценка: ≈ 2 ч код+тесты
       + 15 мин оператора. Отсутствие облегчённого объекта — `404`, не тихий откат на 23 МБ.
    Б. **Публичная раздача витрины через Caddy** с `Cache-Control` — экономит ПОВТОРНЫЕ показы (б), но сама по себе
       скачивания не ограничивает (ревью Codex): расход переезжает с S3 на наш прокси, нужен отдельный предел
       запросов/трафика, а срок кэша надо согласовать с отзывом клипа из витрины; плюс второй путь к файлу
       (ADR-018 правится). ≈ 3–4 ч.
    В. Короче подпись для витрины (например 120 с) — сужает окно (а), но пауза дольше срока ломает перемотку; мало
       пользы.
    Д. **Только код** (предложено Codex): переиспользовать подпись по ключу объекта на её оставшийся срок после
       каждой проверки доступа и добавить `ResponseCacheControl` не длиннее этого срока — повторные показы в пределах
       окна берутся из кэша браузера. Первые 23 МБ не уменьшает, от массового скачивания не защищает; совместимость
       переопределения заголовка с Cloud.ru/MinIO и экономию в браузере надо проверить. ≈ 2 ч.
    Рекомендация — А (размер первого показа), при желании вместе с Д.
