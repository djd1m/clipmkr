# Восстановление доступа к Cloud.ru и сопровождение через Hub

Дата: 03.11.2026. Статус: административный вход через консоль подтверждён;
устойчивый SSH не восстановлен; миграция не начата.

## Цель и границы

Восстановить административный доступ к существующей ВМ и проверить, подходит ли
Cloudru Hub для дальнейшего сопровождения приложения. Базы, пользовательское медиа,
DNS и рабочие контейнеры не переносить и не переустанавливать в рамках этой операции.
Конкретные адреса, идентификаторы ресурсов, ключи, пароли и ссылки консоли хранятся
только в закрытом операторском журнале вне Git.

## Проверенный маршрут

| Шаг | Средство | Результат |
|---|---|---|
| Проверка установки | Hub 0.1.16, движок 0.2.7-20261029, self-test | 5 из 5 проверок пройдены |
| Инвентаризация | Hub `mcp-safe`: `vm_get`, `vm_list`, `disk_list`, `list_security_groups` | ВМ запущена, загрузочный диск подключён; содержимое БД этим не проверяется |
| Команда внутри существующей ВМ | Hub `vm_exec`, команда `id -u` | Защитный прокси отклонил вызов до исполнения: `vm_exec requires exactly one matching active approved VM session` |
| Проверка транспорта | TCP/SSH из текущего окружения и с действующего сервера | Порт 22 отвечает тайм-аутом; HTTPS и `/health` доступны |
| Подробная инвентаризация | Штатный Compute API Cloud.ru | Compute Agent включён, серийная консоль готова |
| Проверка облачных правил | Штатный Compute API, чтение группы и правил | Входящий TCP 22 уже разрешён; общая группа не изменялась |
| Восстановление консольного входа | Compute API: временный пароль для существующего пользователя через Compute Agent | Вход через серийную консоль подтверждён; пароль не публиковался |
| Диагностика Linux | Серийная консоль | SSH активен, слушает IPv4/IPv6:22, `sshd -t` без ошибок; UFW/fail2ban не активны; INPUT/OUTPUT разрешены |
| Проверка аутентификации | Серийная консоль, `sshd -T` | Ключи разрешены, парольная и keyboard-interactive аутентификация SSH отключены |
| Проверка сетевого пути | Ограниченный по времени `tcpdump` одновременно с попытками с действующего сервера | Пакеты TCP 22 от проверяемого источника в гостевую ОС не поступили; точный участок фильтрации пока не установлен |
| Резервный транспорт | Отдельная группа безопасности, входящий TCP 2222/8443 только с административного сервера `/32`; дополнительные временные службы SSH | Группа подключена с сохранением прежней; SSH слушает проверяемые порты, но оба подключения отвечают тайм-аутом |
| Двустороннее наблюдение | `tcpdump` на источнике и целевой ВМ | На источнике видны повторные исходящие SYN к 2222, на целевой ВМ пакетов нет. HTTPS с того же источника возвращает 200 |
| Завершение проб | Консоль + Compute API | Пробные SSH-службы остановлены, слушающих сокетов 2222/8443 нет; пароль заблокирован, выполнен `exit`; временная группа отключена и удалена, исходная группа сохранена; публичный `/health` снова 200 |
| Повторная проверка этапов подключения | OpenSSH `-vvv`, существующий ключ, строгая проверка ключа хоста | TCP не установлен, баннер сервера не получен, публичный ключ не предложен, ошибка `Permission denied` отсутствует; завершение по тайм-ауту |
| Локальная проверка пары ключей | Публичная часть выведена из закрытого ключа и сопоставлена с ранее сохранёнными метаданными ВМ без вывода ключевого материала | Совпадение подтверждено; это не проверка текущего `authorized_keys` внутри гостевой ОС |

В процессе обнаружено расхождение старой сохранённой схемы API с работающим API:
`set-password` требует также поле `login`. Ошибки валидации 422 не считаются
успешным изменением пароля. Успешный запрос вернул 204, затем вход проверен отдельно.
Ссылка консоли создаётся асинхронно; требуется повторное чтение ВМ. Разрыв WebSocket
не означает выхода из Linux: при повторном соединении проверяется текущий prompt.
Новая группа безопасности тоже создаётся асинхронно: преждевременное подключение
интерфейса вернуло 422; после готовности та же операция завершилась 200. Повторно
группа не создавалась. Общие правила не менялись. Пробные дополнительные службы
ограничены временем через systemd; затем остановлены явно. После остановки на
2222/8443 нет слушающих сокетов. Временный пароль заблокирован: `passwd -S`
показывает `L`; консольная сессия завершена командой `exit`. Для повторного
консольного входа потребуется новый временный пароль через Compute Agent.
Локальный файл временного пароля после подтверждения блокировки удалён.

## Что Hub умеет для сопровождения — и что пока не доказано

Hub уже пригоден для чтения состояния облачных ресурсов. Его `vm_exec` использует
SSH, поэтому требует и доступного сетевого пути, и активной одобренной сессии.
В установленной версии безопасный прокси создаёт ограниченную по времени сессию
после согласованного деплоя, сроком на **два часа**. В CLI не найден поддерживаемый сценарий продления
или регистрации существующей ВМ для последующего обслуживания. Наличие `vm_exec`
в списке инструментов само по себе не доказывает возможность сопровождения через
несколько дней после деплоя.

Консоль, смена временного пароля и подробные правила группы проверены через
штатный Compute API: соответствующих операций в доступном профиле Hub нет.
Это отдельный маршрут восстановления, а не успешный вызов Hub `vm_exec`.
Защитные проверки Hub не отключались, поддельные сессии не создавались,
новая ВМ для получения разрешения не создавалась.

Пока нельзя утверждать, что Hub закрывает полный цикл сопровождения. Для этого
нужны: поддерживаемая авторизация обслуживания существующей ВМ; проверенный SSH;
ограничение пользователя/команд/срока; журнал и отзыв доступа; безопасная обработка
секретов и возврата команд. Обновление кода, миграции схемы и откат приложения
должны дополнительно следовать проектным проверкам и плану миграции.

### Проверка актуального опубликованного кода и issue

По просьбе владельца дополнительно проверена версия **0.1.20** в публичном зеркале,
ревизия `f018352364ff8504f105b99be4b7ba7fd72c299d`: двухчасовой срок в
`recordDeployedVM`, проверка `approvedVM` и отсутствие отдельного режима обслуживания
сохраняются. Это проверка исходного кода, а не живой прогон установленной версии 0.1.20.
Установленная версия и инфраструктура при этой проверке не обновлялись.

Создано [issue djd1m/dz-harness#24](https://github.com/djd1m/dz-harness/issues/24):
отдельная ограниченная авторизация обслуживания точной существующей ВМ,
переиспользование SSH и защитного прокси, отзыв и аудит, критерии приёмки и QE.
Техническая реализуемость — вывод по существующей архитектуре; новый режим ещё
не реализован. Дубликатов среди доступных issues на момент проверки не найдено.
Issue не содержит конкретных адресов/UUID инфраструктуры или секретов.

## Воспроизводимый маршрут восстановления

1. Проверить установку Hub и выполнить его безопасную инвентаризацию.
   Для чтения compute/inventory в этой версии пришлось явно передать дочернему
   `mcp-safe` окружение из штатного `readCredentials()`: автоматическая загрузка
   файла учётных данных доступна не для всех профилей. Значения не выводить.
2. Проверить SSH из двух сетей, HTTPS, статус ВМ и правила безопасности.
3. Если SSH недоступен, проверить включённый Compute Agent и создать консоль через
   штатный Compute API: `POST /api/v1/vms/{vm_id}/remote-console`, протокол `serial`.
   Дождаться появления ссылки при повторном GET ВМ; ссылку считать секретной.
4. Задать случайный временный пароль существующего пользователя через
   `POST /api/v1/vms/{vm_id}/set-password` с полями `login`, `password`.
   Хранить его только в закрытом файле, не в аргументах shell и не в журнале.
5. Подключиться к консоли, проверить службу, сокеты, конфигурацию SSH, firewall,
   маршрут и поступление SYN. Временные сетевые пробы ограничивать `/32`, временем
   и отдельной группой; сохранять исходный список групп интерфейса.
6. Остановить пробные службы, вернуть исходные группы, удалить только свою пробную
   группу после фактического отключения. Заблокировать временный пароль и выйти.
7. Если SYN не доходят при корректных правилах, передать закрытые доказательства
   провайдеру. Не объявлять проблему исправленной только потому, что HTTPS работает.

## Незакрытые пункты

- Установить точный участок потери TCP между источником и гостевой ОС: известны
  исходящие SYN и отсутствие пакетов на целевой ВМ; причина на стороне конкретного
  провайдера этим ещё не доказана.
- После восстановления сетевого пути сверить ключ хоста с консольным отпечатком
  и подтвердить повторный вход существующим ключом. Пока этот вход не подтверждён.
  Текущий тайм-аут наступает до аутентификации и не объясняется неверным ключом.
  Дополнительная проблема ключевой аутентификации после восстановления TCP пока
  не исключена, поскольку этот этап ещё недостижим.
- Для полноценного сопровождения через Hub нужен поддерживаемый режим обслуживания
  существующей ВМ, отдельно от двухчасовой сессии первоначального деплоя.

Пакет для обращения к провайдеру хранить приватно: временное окно UTC, ВМ/интерфейс,
правила, адреса источника/назначения и краткий заголовочный захват SYN с обеих сторон.
Пароль, ключи и ссылки консоли в обращение не включать. Обращение из этой сессии
не отправлялось.
