# Неприменённый TEST-платёж при подготовке переноса

09.11.2026. Статус: выявлено сверкой, причина не установлена, исправление начисления не выполнялось. Это тестовый магазин; реального списания денег эта проверка не доказывает.

## Наблюдение

Перед новой QA оплатой выполнены read-only SQL и GET состояния четырёх платежей в настоящем API ЮKassa. На source все четыре намерения имеют created, таблицы payment_event иpayment пусты. Провайдер вернул200 длявсех: три canceled (два expired_on_confirmation иодин insufficient_funds), один succeeded/paid=true/test=true на990рублей. Metadata order_id успешного платежа совпадает с локальным intentID. Полные IDs иответы остаются в закрытом payment-window/source-provider-before.private.json.

Такой результат нельзя считать корректно завершённым drain. Успех провайдера не равен начислению в приложении. Не установлено, куда направлялось первоначальное уведомление, доставлялось ли оно икакой ответ получило; не приписываем сбой изменению callback, выполненному позднее при переносе.

## Выполненные действия

Владелец разрешил тестовое окно и сообщил о смене callback на QA IP. Независимо проверен минимальный source override: N5_TEST_CHECKOUT_ACCOUNT_ID очищен при неизменных остальных настройках. Применён только к sourceweb с прежним образом; поддержка и три workers не перезапускались. Authenticated negative probe под существующим тестовым пользователем: login200 → checkout503 checkout_paused → logout200. Ledger counts4/0/0 неизменны. QA callback закрыт503; новая покупка не запускалась.

Владельцу направлен запрос вернуть https://clipmkr.ru/api/webhooks/yookassa-test и повторить provider notification payment.succeeded, если кабинет предоставляет такую возможность. Подтверждения пока нет. Секреты, пароли, email, payload иsignedURL в Git не помещаются.

## Условия продолжения

1. Подтвердить callback и реальную доставку либо определить согласованный способ reconciliation.
2. Повторно прочитать provider/source данные: успешное намерение иначисление должны соответствовать, повторне создаёт второе начисление.
3. Только после drain иполного creator fence открывать ограниченное QA окно.
4. После завершения вернуть согласованные callback/allowance исверитьрезультат.

Ручной UPDATE финансовых таблиц, поддельный provider callback ивозврат средств существующего платежа не входят в эти действия. Если требуется отдельное исправление — сначала конкретный план иразрешение, затем штатный идемпотентный механизм.

## Уточнённая сверка и решение владельца

Свежая read-only сверка трёх хранилищ установила: в main есть intent, но нет payment/event; в legacy есть payment/event этого платежа, но нет intent; в Cloud соответствующих строк нет. Legacy payment имеет needs_review=true, review_reason=unknown_intent, account_id/intent_id=NULL. Проверка credit_grant по ID именно этой legacy payment вернула0. Это подтверждает разделённую историю, но не доказывает транспорт или первоначальную причину её появления.

Владелец подтвердил возврат callback на старый URL; ручной повтор не выполнен. Затем владелец установил приоритет: сначала перенести необходимые базы на этот VPS, затем проверять оплату. Поэтому эта аномалия сохраняется без исправления и **не блокирует копирование**. Основная и legacy истории не сливаются; повторная платёжная приёмка откладывается до готовности перенесённых данных.
