## ADDED Requirements

### Requirement: Код из действительного приглашения виден в форме регистрации
Публичная страница SHALL передавать в единственную форму только публичный эффективный код из подписанной, неистёкшей referral-cookie после актуальной серверной проверки активности кода и владельца. Поле «Код партнёра» SHALL быть раскрыто, заполнено и редактируемо. Рядом SHALL отображаться «Код из приглашения заполнен. Вводить его не нужно» с пояснением о проверке привязки после создания нового аккаунта. Без проверенного приглашения optional-блок SHALL оставаться свёрнутым и пустым.

#### Scenario: Новый пользователь приходит по ссылке
- **GIVEN** чистый браузер и действительная реферальная ссылка
- **WHEN** он проходит настоящий `/r/:code` и открывает страницу регистрации
- **THEN** поле раскрыто, содержит эффективный код и не требует ручного копирования
- **AND** пользователь вводит только электронную почту и пароль

#### Scenario: Проверенного приглашения нет
- **WHEN** cookie отсутствует, подпись/TTL недействительны либо код или владелец не active
- **THEN** форма не показывает проверенный код и зелёное подтверждение
- **AND** обычная регистрация остаётся доступной, optional-блок пуст и свёрнут

### Requirement: Отображение сохраняет серверную политику источника
Неизменённое автоматически заполненное значение SHALL приводить к `code.apply({})`. Сознательно введённое или изменённое непустое значение SHALL передаваться как `{code}`. Клиент SHALL NOT назначать `source`. Отображение SHALL сохранять first-touch, guest priority и действующие ограничения explicit replacement; изменение UI не меняет 404 и политику A→B.

#### Scenario: Cookie истекает после рендера
- **GIVEN** код был показан из действительной cookie
- **WHEN** cookie исчезла или истекла до submit, а пользователь код не редактировал
- **THEN** в apply уходит пустой объект, stale display не становится explicit
- **AND** UI не объявляет успешную привязку на основании одного показанного кода

#### Scenario: Другая обычная ссылка после первого приглашения
- **GIVEN** в браузере остаётся действительная cookie A
- **WHEN** пользователь открывает обычную ссылку B
- **THEN** отображается эффективная A, автоматической замены на B нет

#### Scenario: Ручное изменение
- **WHEN** пользователь сознательно меняет поле
- **THEN** прежнее уведомление о проверенном autofill убирается
- **AND** непустой ручной код применяется через существующий explicit-контракт

### Requirement: Подтверждение в кабинете зависит от результата сервера
После создания аккаунта AuthFlow SHALL показывать две строки: «Аккаунт создан. Приглашение применено.» и «Регистрация по коду CODE учтена.» — только по пригодной pending/activated атрибуции и applied_code, который сервер связал с сохранённым partner_code_id. CODE SHALL NOT браться из SSR, input или URL. Неподтверждённый результат SHALL NOT давать положительный notice.

#### Scenario: Приглашение реально применено
- **WHEN** новый аккаунт создан и сервер подтверждает применённую атрибуцию
- **THEN** открывается кабинет и отображаются обе строки подтверждения с кодом, соответствующим сохранённому partner_code_id

#### Scenario: Фактически применённый код отличается от предварительного
- **GIVEN** SSR показал A
- **WHEN** ручной ввод или актуальная cookie приводит к реально применённой B
- **THEN** ответ apply и обе строки notice подтверждают B, не A
- **AND** expiry/removal без ручного ввода либо отсутствие соответствия applied_code сохранённой атрибуции не подтверждает предварительную A

#### Scenario: Успешный HTTP без атрибуции
- **WHEN** сервер вернул HTTP200 с `null`, пустым/неподтверждённым результатом, `rejected` или без подтверждённого applied_code
- **THEN** UI может подтвердить созданный аккаунт, но не применённое приглашение
- **AND** self, partner_deleted, skip, ошибка и discard также не дают положительный notice

#### Scenario: Совместимость существующего apply
- **WHEN** существующий клиент вызывает code.apply после добавления optional applied_code
- **THEN** прежние поля, null/error/envelope и input schema сохраняются, поле является аддитивным
- **AND** source/replacement и финансовые эффекты не меняются; переиспользуется AuthFlow без второй auth pipeline

#### Scenario: Одна регистрация видна обоим потребителям
- **GIVEN** изолированные настоящие PG/HTTPS и snapshots канонических dashboard блогера и monthly report владельца по выбранному blogger/code и чужому blogger/code
- **WHEN** чистый browser проходит настоящий `/r/A → SSR → форма → новая регистрация без действий с кодом → apply`
- **THEN** persisted attribution и публичный код совпадают с A; прирост registrations в обеих выбранных проекциях ровно один
- **AND** чужой blogger/code не меняется, повторное чтение не увеличивает счётчики
- **AND** Moscow-month для owner report и all-time dashboard сохраняют действующую семантику; платежи, видео и production не используются

#### Scenario: Повторная регистрация и обычный вход
- **WHEN** register возвращает outcome `existing`
- **THEN** сохраняется существующий skip apply, notice existing и исходная атрибуция
- **AND** отдельный ordinary login сохраняет существующий вызов apply и серверные правила

### Requirement: SSR не раскрывает секреты и не увеличивает статистику
SSR SHALL NOT передавать клиенту cookie value, подпись, session secret или внутреннюю identity. Персонализированный HTML SHALL NOT разделяться через общий кэш. Проверка display-кода SHALL выполнять только чтение без `recordView`/новых growth events. Ошибка advisory display-проверки SHALL NOT превращать общую страницу регистрации в отказ или давать ложное зелёное состояние.

#### Scenario: Обновление и соседний браузер
- **WHEN** страница обновляется или открывается в другом чистом контексте
- **THEN** SSR не добавляет переходов, а код первого браузера не появляется во втором
- **AND** HttpOnly/Secure-параметры cookie сохраняются

#### Scenario: Ресурс проверки недоступен
- **WHEN** БД недоступна во время display-проверки существующей cookie
- **THEN** страница доступна без неподтверждённого кода/успеха; секреты не логируются
