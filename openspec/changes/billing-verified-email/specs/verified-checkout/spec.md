## ADDED Requirements

### Requirement: Подтверждённый адрес перед покупкой

Checkout MUST требовать активную сессию и подтверждённый текущий адрес.
Клиент выбирает пакет, подтверждает адрес через существующий токен и явно
возвращается к оплате выбранного пакета.

#### Scenario: Попытка купить до подтверждения

- **WHEN** активный аккаунт с неподтверждённым адресом запрашивает новый checkout
- **THEN** запрос получает состояние подтверждения и не создаёт платёж у провайдера
- **AND** пакет сохраняется для явного продолжения после подтверждения

#### Scenario: Старая попытка

- **WHEN** ранее созданный платёж сообщает подлинный результат
- **THEN** действующая сверка обрабатывает его по прежним правилам
- **AND** отправка новых исторических квитанций сама не запускается

#### Scenario: Ссылка от другой сессии

- **WHEN** подтверждение пришло из устаревшей или чужой сессии
- **THEN** подтверждение и checkout не переходят на другой аккаунт

### Requirement: Квитанция после подтверждённой оплаты

Для новой покупки с подтверждённым адресом сервер MUST создать одну логическую
квитанцию из зафиксированного успешного платежа. Расхождения, ожидающие платежи
и отмены не создают квитанцию успеха.

#### Scenario: Повтор доверенного события

- **WHEN** webhook, сверка или браузерный возврат повторяются
- **THEN** пакет начисляется один раз и квитанция сохраняет прежний идемпотентный ключ

#### Scenario: Неизвестный исход отправки

- **WHEN** почтовый запрос завершился без подтверждения
- **THEN** повтор использует прежние payload и ключ в допустимом окне Resend
- **AND** по истечении окна оператор видит нерешённое состояние без слепой повторной отправки
