## ADDED Requirements

### Requirement: Исключение тестовой покупки для согласованного аккаунта
При глобально закрытом checkout система MUST разрешать существующий путь покупки пакетов
только согласованному владельцем аккаунту из серверной сессии, если настроен настоящий
тестовый магазин ЮKassa, TEST mode и credits_v1. Исключение MUST NOT разрешать реальные списания.

#### Scenario: Разрешённая сессия и тестовый магазин
- **GIVEN** provider готов, testMode true, глобальный checkout false и ровно один UUID в private config
- **WHEN** активный credits_v1 аккаунт с этим UUID открывает каталог и оформляет существующий пакет
- **THEN** существующая TEST-кнопка доступна и прежний checkout применяется к этой сессии
- **AND** роль, кредиты и entitlement не меняются от самого предоставления доступа

#### Scenario: Остальные аккаунты и подмена тела
- **GIVEN** другая или отсутствующая сессия
- **WHEN** открыт каталог либо отправлен POST с подставленным account_id/email/ролью
- **THEN** покупка недоступна, новый intent и provider create не выполняются

### Requirement: Fail-closed конфигурация и общая политика UI/API
Конфигурация MUST принимать только один точный server UUID и MUST отвергать противоречивое
исключение с LIVE/testMode false, непригодным test key или глобально открытым checkout.
SSR и POST MUST использовать одну серверную политику. Private identity MUST NOT попадать в клиентский payload.

#### Scenario: Непригодная либо отсутствующая настройка
- **GIVEN** exception отсутствует или равен пустой строке при глобально закрытом checkout
- **WHEN** загружается конфигурация
- **THEN** тестовый доступ никому не предоставляется
- **AND** непустой невалидный UUID, список, пробелы либо противоречивый режим дают отказ preflight

#### Scenario: Отзыв исключения и сохранение платёжного контракта
- **GIVEN** настройка исключения удалена, глобальный checkout остаётся false
- **WHEN** повторно открыт каталог или отправлен новый POST
- **THEN** покупка снова недоступна всем
- **AND** существующие status/webhook, проверка payment.test, ownership и идемпотентность сохраняются

#### Scenario: Повторный checkout и несовпадение режима уведомления
- **GIVEN** один TEST intent и повторяющийся ключ checkout, затем исключение отозвано при сохранённом TEST provider
- **WHEN** запросы checkout перекрываются, а webhook перепроверяет payment.test=false
- **THEN** повторы относятся к одному intent и одной provider payment, неверное уведомление отвергается без нового payment/event/grant
- **AND** исправленный test=true принимается один раз, повтор не выдаёт второй grant

#### Scenario: Приватность реального HTML и RSC/Flight
- **GIVEN** разные действительные синтетические сессии разрешённого и другого аккаунтов
- **WHEN** Next.js отдаёт начальный HTML и RSC/Flight клиентской навигации в каталог
- **THEN** клиентские ответы и журнал не содержат UUID настройки исключения или credentials
- **AND** смена аккаунта сохраняет remount и запрет применения старого checkout response
