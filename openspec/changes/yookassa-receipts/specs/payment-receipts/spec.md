# Дельта требований: данные чеков при оплате

## Purpose

Передавать в ЮKassa сведения для чека одновременно с оплатой пакета Clipmkr, сохраняя точность сумм, доверенную принадлежность данных и безопасность повторных запросов.

## ADDED Requirements

### Requirement: Доверенные сведения покупателя и позиции

Система MUST брать email получателя чека из серверного аккаунта покупателя, а сведения позиции и цену — из серверного предложения. Клиент не может назначить другого получателя, цену или налоговые параметры.

#### Scenario: Попытка подменить чек

- **WHEN** клиент присылает дополнительные поля email, receipt, amount или VAT в checkout
- **THEN** запрос отклоняется до создания платежа, а доверенные данные не заменяются присланными

#### Scenario: Покупка пакета

- **WHEN** аутентифицированный активный пользователь покупает поддерживаемый пакет с включённой передачей чека
- **THEN** платёжный запрос содержит receipt с email этого пользователя и одной позицией выбранного серверного предложения

### Requirement: Точная сумма чека

Система MUST передавать сумму позиции в RUB точной десятичной строкой; при количестве1 сумма чека равна сумме соответствующего намерения оплаты. Несогласованные или непригодные значения запрещают отправку платежа.

#### Scenario: Корректная сумма

- **WHEN** создаётся платёж для пакета из серверного каталога
- **THEN** сумма receipt совпадает с payment amount и сохранённой ценой намерения без округления через float

#### Scenario: Несогласованный чек

- **WHEN** получены непригодные реквизиты или несовпадающая сумма
- **THEN** запрос к провайдеру не отправляется и клиенту не показывается успешная оплата

### Requirement: Явные фискальные настройки

Система MUST использовать явно настроенные допустимые фискальные значения без угадывания НДС. В этом блоке поддержан только полный расчёт; предоплата требует отдельного закрывающего чека и не включается. Синтетические TEST-значения не считаются подтверждёнными налоговыми параметрами бизнеса.

#### Scenario: Подготовка без подтверждения НДС

- **WHEN** владелец ещё уточняет налоговые параметры
- **THEN** код может проверяться в изолированных тестах, но реальные списания не включаются с придуманными значениями

#### Scenario: Неполная настройка

- **WHEN** попытка создания платежа требует чек, а необходимая настройка отсутствует или непригодна
- **THEN** платёж не отправляется без чека и ошибка не подменяется успехом

### Requirement: Стабильность повторной оплаты

Система MUST повторять исходные данные чека для того же намерения после неизвестного сетевого результата. Повтор не создаёт новое начисление, не пересобирает налоговые данные по изменившейся конфигурации и не меняет ранее созданный платёж.

#### Scenario: Таймаут после запроса

- **WHEN** первый запрос имеет неизвестный результат, затем меняются текущие настройки и пользователь повторяет checkout с прежним ключом
- **THEN** используется прежнее намерение и его исходные фискальные данные с тем же ключом идемпотентности провайдера

#### Scenario: Платёж уже привязан

- **WHEN** намерение уже содержит идентификатор платежа
- **THEN** повтор читает существующий платёж и не создаёт второй

#### Scenario: Истёкшее окно повторности

- **WHEN** непрояснённое намерение без идентификатора провайдера достигло возраста24часа
- **THEN** новый POST не отправляется, требуется сверка исходного платежа перед новой попыткой

#### Scenario: Старое намерение без чека

- **WHEN** передача чеков включена, а существующее намерение не содержит исходного чека и идентификатора провайдера
- **THEN** ему не добавляют чек задним числом и не отправляют изменённый запрос; требуется сверка перед новым намерением

### Requirement: Сохранение границ действующей оплаты

Система MUST сохранять проверку сессии, Origin, частоты, закрытого тела, подлинности webhook и однократного начисления. Текущий TEST-контур остаётся работоспособным; код чеков сам не открывает реальные продажи или возвраты.

#### Scenario: Обновление приложения

- **WHEN** публикуется поддержка чеков на текущем VPS
- **THEN** прежний TEST-профиль запускается без включения боевого магазина и расширения доступа к checkout

#### Scenario: Повтор уведомления

- **WHEN** подтверждённое уведомление об одном платеже доставлено повторно
- **THEN** платёж и начисление не дублируются

### Requirement: Конфиденциальность чека

Система MUST не помещать email, данные чека, пароли и ключи в публичные ответы, логи или Git. Нужные реквизиты передаются платёжному провайдеру по существующему защищённому каналу.

#### Scenario: Ошибка с чувствительными данными

- **WHEN** ошибка провайдера или входа содержит email либо секрет
- **THEN** наружу попадает только безопасная категория ошибки без содержимого чека и секретов
